# 知识库设计方案

> 这一页回答："为什么是这个结构？"以及"Obsidian 和 LLM Wiki 到底怎么分工？"

## 先厘清一个混淆

**Obsidian 是工具，LLM Wiki 是方法。** 它们不在同一个维度上，不存在"哪个更好用"。

| | Obsidian | LLM Wiki（方法） |
|---|---|---|
| 是什么 | 本地 Markdown 编辑器 + 双链 + 插件生态 | 让 LLM 持续把原始资料整理成互联知识页 |
| 解决 | **阅读、编辑、发现** | **归纳、综合、维护** |
| 擅长 | 人的浏览与思考 | 机器的大规模整理 |
| 不擅长 | 自动归纳几百篇资料 | 判断"这个结论可不可信" |
| 失败模式 | 笔记堆积如山但从不回看 | 幻觉污染、来源丢失、越整理越乱 |

**结论**：用 Obsidian 当**界面**，用 Agent 按 LLM Wiki 的方式当**维护者**。这个知识库就是这么搭的。

## 核心设计：三层物理隔离

```
10-Sources/   原始资料 —— 只读。Agent 永远不得修改。
20-Notes/     你的理解 —— 唯一记录"你怎么想"的地方。
30-Wiki/      Agent 维护的主题页 —— 综合、对比、结论。
```

> [!important] 为什么必须物理隔离，而不是靠"约定"
> LLM 维护知识库的头号失败模式是：
> **三个月后，你分不清某一句话是论文说的，还是 AI 编的。**
>
> 一旦发生，整个知识库的可信度归零——你不敢再相信任何一页，
> 于是它退化成一个"看起来很整齐但没用"的文件夹。
>
> 靠 prompt 里写"请标注来源"是不够的。**只有物理隔离 + 溯源规则 + git 历史**能防住。

### 三层各自的契约

| 层 | 谁写 | 能否修改 | 失败后果 |
|---|---|---|---|
| `10-Sources/` | 你 / Agent 起草 | ❌ **永不修改** | 失去真相锚点，无法验证任何结论 |
| `20-Notes/` | 你（Agent 可起草） | ✅ 但需你确认 | 知识库变成 AI 的自言自语 |
| `30-Wiki/` | Agent 主战场 | ✅ 需遵守溯源规则 | 幻觉污染 |

## 溯源规则：让幻觉可见

`30-Wiki/` 里每条事实性断言必须满足之一：

1. `[[10-Sources/...]]` — 有来源
2. `<!-- derived -->` — 从多条来源推导（需列推导链）
3. `> [!warning] 未验证` — 明确标记为推测
4. 公认常识 — 无需标注

**禁止**把 AI 的推理写得像文献结论。这条规则的价值在于：
**它把"可信度"从一个模糊的感觉，变成了一个可以在文件里 grep 的字段。**

## 为什么用 frontmatter 而不是文件夹分类

每个页面顶部有：

```yaml
status: stub | seed | solid | stale
confidence: low | medium | high
domain: dsp | realtime | ...
```

**理由**：文件夹只能表达一个维度，而知识有多个维度（主题、成熟度、信心）。
用 frontmatter + Dataview 查询，可以问出文件夹问不出的问题：

- "所有 `status: stub` 且 `domain: dsp` 的页面" → 我的待办队列
- "所有 `confidence: low` 的 `solid` 页面" → 需要重新核实的
- "所有 `status: stale` 的页面" → 框架 API 变更后要更新的

> [!tip] 这套设计的关键洞察
> **文件夹回答"东西放在哪"，frontmatter 回答"这东西有多可信"。**
> 后者对知识库更重要，但大多数笔记系统只做了前者。

## Agent 接入方式

| 方式 | 何时用 | 本库是否采用 |
|---|---|---|
| **A. Agent 直接读写 Vault 文件夹** | 批量整理 Markdown | ✅ **主力方式** |
| **B. Obsidian 官方 CLI** | 需要每日笔记、应用命令 | 🟠 按需 |
| **C. Local REST API + MCP** | Agent 无法访问文件系统时 | ❌ 不需要 |

**为什么选 A**：Obsidian 的 vault 就是普通文件夹，任何能读写文件的 Agent 都能工作。
不依赖 Obsidian 运行，不依赖插件，不依赖网络。**最少依赖 = 最不容易坏。**

> [!warning] 不要用云同步盘（iCloud/Dropbox/坚果云）放 git 仓库
> `.git` 目录会被同步冲突破坏，而且是**静默损坏**——你发现时历史已经乱了。
> 用 git + 私有远程仓库（GitHub/Gitee）。

## 这套方案的已知弱点

诚实列出，方便你以后改进：

| 弱点 | 影响 | 可能的缓解 |
|---|---|---|
| 依赖 Agent 遵守契约 | Agent 换了可能不守规矩 | `AGENTS.md` 是通用约定，主流 Agent 都会读 |
| `status` 字段会腐烂 | 页面标着 `seed` 但其实早该是 `solid` | 定期人工复查，或用 Agent 扫描 |
| 大音频文件不适合 git | `90-Attachments` 会膨胀 | 大文件外部存放，只留链接 |
| 三层结构对"快速记录"有摩擦 | 想随手记时不知道放哪 | 都丢 `00-Inbox/`，允许脏 |
| Dataview 需要装插件 | 状态看板失效 | 不影响核心内容，可选 |

## 与其他方案的对比

| 方案 | 优点 | 为什么没选 |
|---|---|---|
| 纯 Obsidian（手写） | 完全可控 | 整理成本高，资料一多就放弃 |
| 纯 LLM Wiki（无 Obsidian） | 全自动 | 无法有效审阅，幻觉不可见 |
| Notion / 飞书 | 协作好、界面好 | 数据在云端、格式不开放、Agent 接入受限 |
| Logseq | 大纲式、双链强 | 与 Obsidian 类似，但生态较小 |
| Zotero + 插件 | 文献管理专业 | 只解决"资料"，不解决"知识" |
