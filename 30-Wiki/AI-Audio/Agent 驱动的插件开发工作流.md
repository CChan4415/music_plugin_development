# Agent 驱动的插件开发工作流

> [!important] 一句话
> **Agent 的价值在"可验证的小步"，不在"一次做完一大块"。**
> 本知识库自己的构建过程就是证据：10 个子代理，0 个完成长任务。

> [!note] 本页的经验来源
> 本知识库（150+ 页面、100+ 提交）**大部分由 AI Agent 参与构建**。
> 本页记录的是**实际有效的做法**，包括失败的部分。

---

## 一、实测：长任务为什么失败

> [!danger] 本库的真实记录
> | 任务粒度 | 结果 |
> |---|---|
> | "写这 5 个 Wiki 页面"（长子代理任务） | **0/5 完成**（两次尝试都失败） |
> | "写这个验证脚本"（短任务） | **5/5 完成**（437–581 行，质量高） |
> | "改这一处断言"（单点修改） | ✅ 完成 |
> | "派 8 个并行子代理" | **全部失败**（模型限流） |
>
> **规律**：任务越大、步数越多，**完成率越低**。

> [!important] 为什么
> Agent 的长任务有**累积失败概率**：
> ```
> 单步成功率 90% → 10 步任务的成功率 = 0.9^10 ≈ 35%
> ```
> 而且中途失败时**往往什么都不留下**（半成品在它自己的上下文里）。

## 二、有效的工作流

### 核心原则：**小步 + 可验证 + 单点提交**

```
① 定义"可验证的产出"    ← 不是"写好这一页"，而是"这个脚本能跑通"
② Agent 做一小步
③ 人/Lead 立刻验证       ← 关键
④ 单元提交（一个逻辑改动一次 commit）
⑤ 重复
```

> [!important] 第 ③ 步不能省
> 本库的 8 个 AI 错误**全部是"验证"抓到的**（见
> [[AI 辅助 C++ 音频开发的真实效果]]）。
> 如果跳过验证直接进下一步，错误会累积。

### 任务拆分示例

| ❌ 太大 | ✅ 合适 |
|---|---|
| "实现一个压缩器插件" | "实现 transfer curve 函数 + 6 个单元测试" |
| "写 5 个心理声学页面" | "写 1 个页面，含 3 个实测数字" |
| "优化 DSP 性能" | "测出当前 CPU 占用，给出瓶颈" |
| "修好这个 bug" | "写一个能复现 bug 的最小测试" |

> [!tip] 一个好判据
> **"这一步做完，我怎么知道它对？"**
> 答不出来 → 任务还是太大，继续拆。

## 三、给 Agent 的任务模板

```
【任务】<一句话，可验证的产出>
【范围】只改 <具体文件路径>，不要动其他文件
【约束】
  - 实时安全：无分配/无锁/无 IO（见 实时音频线程契约）
  - 参数必须钳制
  - 代码必须能编译（给出验证命令）
【验收】
  - 产出：<文件路径>
  - 验证：<命令>，期望 <具体输出>
  - 如果做不到，**明确说做不到**，不要编
【不要做】
  - 不要 git commit（我来统一提交）
  - 不要改 <其他文件>
```

> [!important] 最后那条"不要做"很有用
> 本库曾出现：Agent 用 `git add -A` 提交时，
> **把另一个 Agent 的半成品一起扫进了 commit**。
>
> **明确划范围**能避免这类冲突。

## 四、多 Agent 协作的坑

> [!danger] 本库踩过的三个坑

| # | 坑 | 后果 | 解法 |
|---|---|---|---|
| 1 | **并行太多** | 模型限流，全部失败 | 一次不超过 2 个 |
| 2 | **`git add -A` 扫到别人的半成品** | 提交了未完成的东西 | 用**具体文件名**提交 |
| 3 | **两个 Agent 改同一文件** | 互相覆盖 / "file changed since read" | **划清文件范围** |

> [!warning] 第 3 条的隐蔽性
> 两个 Agent 改同一文件时，**不会报错**——
> 后写的覆盖先写的。你只在"发现内容少了"时才知道。
>
> **规则**：每个 Agent 只碰**自己那组文件**，写进任务描述里。

**文件范围划分示例**：

| Agent | 负责 |
|---|---|
| A | `30-Wiki/Music-Acoustics/*.md` |
| B | `30-Wiki/Realtime-Engineering/*.md` |
| Lead | 其余 + 统一提交 + 最终验证 |

## 五、什么时候**不要**用 Agent

> [!important] 三类任务自己做

| 类型 | 为什么 |
|---|---|
| **建立直觉的 DSP 核心** | 你必须理解原理才能调试。Agent 写完你也不会 |
| **设计决策**（选框架、选架构） | 需要你的偏好和约束，Agent 不知道 |
| **跨多步的长任务** | 实测完成率极低 |

> [!tip] 判据
> **"这件事做错了，我能立刻看出来吗？"**
> - 能 → 可以交给 Agent
> - 不能 → 自己做，或**先造一个能看出来的验证**

## 六、AI 会怎么写错

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **声称完成但实际半途而废** | 你以为好了 | 检查产出文件是否存在 |
| 2 | **用 `git add -A`** | 扫进无关文件 | 要求用具体文件名 |
| 3 | **改范围外的文件** | 冲突/覆盖 | 检查 `git status` |
| 4 | **不报告不确定性** | 你以为它很确定 | 主动问 |
| 5 | **一次改多处** | 无法定位问题 | 要求小步 |
| 6 | **不写验证方法** | 你无法验收 | 要求给出验证命令 |
| 7 | **编造"已验证"** | 假的安全感 | 自己跑一遍 |
| 8 | **不写"做不到"** | 静默失败 | 明确要求报告失败 |

> [!danger] 第 1 条是本库最实际的教训
> **子代理"完成"了很多中间产物**（脚本、实验），
> 但**目标产出（页面）是 0**。
>
> **验收时必须检查"目标产出是否存在"**，
> 而不是听"我做了什么"。

## 七、常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| Agent 说完成但文件不存在 | 半途而废 | 检查文件 |
| 提交里混入无关文件 | `git add -A` | 用具体文件名 |
| 两个 Agent 互相覆盖 | 文件范围重叠 | 划清范围 |
| 全部失败 | 并行太多 | ≤ 2 个 |
| 质量不稳定 | 任务太大 | 拆小 |
| 验证不了 | 没定义验收标准 | 先定义"怎么知道它对" |

## 八、怎么验证（Agent 工作的验收）

**四步**：

| 步 | 检查 | 命令 |
|---|---|---|
| 1 | **产出文件是否存在** | `ls <期望路径>` |
| 2 | **内容是否完整** | 检查结构（如 AGENTS.md §5 的六个小节） |
| 3 | **代码能否跑** | 编译 + 运行 |
| 4 | **数字是否可复现** | 用页面里的代码重跑 |

```bash
# 本库的验收脚本（示例）
# ① 文件存在 + 行数
for f in <期望的文件列表>; do
    [ -f "$f" ] && echo "✅ $(wc -l < "$f") 行" || echo "❌ 缺失: $f"
done

# ② 结构合规（AGENTS.md §5）
grep -c "AI 会怎么写错" "$f"    # 应为 1
grep -c "常见坑" "$f"           # 应为 1
grep -c "怎么验证" "$f"         # 应为 1

# ③ 全库健康
python3 50-Playground/tools/vault_health.py
```

> [!important] 第 4 步是唯一能抓"内容错"的
> 前 3 步只能确认"文件在、结构对、能跑"。
> **数字对不对，必须用页面里的代码重跑一遍。**
>
> 本库就靠这一步抓到了"表格数字与代码不匹配"的错误。
