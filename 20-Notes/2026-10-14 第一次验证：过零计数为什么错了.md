# 第一次验证：过零计数为什么错了

> [!note] 这是这个知识库里的第一条实验记录
> 它记录的不是"我学会了一个知识点"，而是**一次真实的、我自己的验证过程**——
> 包括我自己犯的错。**这类内容比教科书摘抄值钱得多。**

## 我做了什么

按 [[Python 优先的 DSP 学习路径]] 的第一步，用 numpy 生成 440Hz 正弦、存成 WAV。
然后想验证"生成的文件真的是 440Hz"，于是用**过零计数**：

```python
# ❌ 我最初写的方法
zc = np.sum(np.diff(np.sign(data)) != 0)
print(f"估计频率 {zc/2/DUR:.1f} Hz")
```

**结果：479.8 Hz。** 不是 440。差了 40Hz。

## 我差点得出错误结论

第一反应是"代码写错了"。但如果真是 440 写成了 480，
`np.sin(2*np.pi*480*t)` 这种错误其实很罕见——**更可能是我的验证方法有问题**。

> [!important] 这是关键的分岔口
> 遇到"结果不对"时，**先怀疑测量工具，再怀疑被测对象**。
> 尤其当你刚写了一个自己都不太确定的验证脚本时。
> 新手最常见的错误是：急着改正确的代码去迎合错误的测试。

## 真正的原因

**int16 量化后，正弦波在零点附近有多个连续的样本值恰好为 0。**

```python
np.sign(0) == 0        # ← 问题在这
```

`np.diff(np.sign(x)) != 0` 会把 `-1 → 0 → +1` 数成**两次**符号变化，
而实际上那只是**一次**过零。

实测：2 秒 440Hz 正弦（96000 样本）里，**有 160 个样本值恰好为 0**。
所以过零次数被虚增了，频率被高估。

## 正确的做法

### 方法 1：只数"上升沿"过零

```python
sign = np.sign(data)
sign[sign == 0] = 1                                    # 先把 0 归到正
zc = np.sum((sign[:-1] < 0) & (sign[1:] >= 0))         # 只数上升沿
freq = zc / DUR                                        # 每秒的上升沿数 = 频率
# → 439.50 Hz  ✅
```

### 方法 2（更好）：FFT 找主峰

```python
X = np.abs(np.fft.rfft(data))
freqs = np.fft.rfftfreq(len(data), 1/SR)
peak = freqs[np.argmax(X)]
# → 440.00 Hz  ✅ 精确
```

> [!tip] 结论：测频率就用 FFT，别用过零计数
> FFT 是**频域**方法，直接给出频率成分，不受量化、噪声、直流偏置影响。
> 过零计数是**时域**的粗糙近似，只在信号干净、且你知道它的陷阱时才好用。
> 而且 FFT 还能顺便看谐波——这是过零计数完全做不到的。

## 这个坑值得记下来的三个理由

1. **量化会制造"恰好为 0"的样本** —— 这是数字音频特有的现象，模拟思维想不到
2. **测量工具的 bug 会伪装成被测对象的 bug** —— 这个陷阱在 DSP 开发里反复出现
3. **FFT 是音频验证的主力工具** —— 越早建立"先看频谱"的习惯越好

## 顺便验证到的

| 检查项 | 结果 | 结论 |
|---|---|---|
| 采样率 / 样本数 | 48000 / 96000 | 2 秒 @ 48kHz ✅ |
| 峰值 | 0.5000 → **-6.02 dB** | 与 `20*log10(0.5) = -6.02` 完全一致 ✅ |
| 主频（FFT） | **440.00 Hz** | 精确 ✅ |

> [!note] 一个意外的收获
> `0.5 → -6.02 dB` 这个验证一次就过了，但过零计数错了。
> 说明**简单的关系式（dB↔线性）不容易错，复杂的测量方法才容易错**。
> 以后写验证脚本时，优先用最简单、最直接的关系去验证。
