# 实时音频线程契约

> [!important] 如果这个库只能留一页，留这一页
> 90% 的"新手插件爆音/卡顿/崩溃"都源于违反本页的规则。
> 而且**违反时往往在开发机上不报错**——你的 M2 很快，测试时只有 3 个音轨，
> 用户的 8 年前的老机器上跑 40 个音轨时就炸了。

## 为什么音频线程特殊

音频线程是**硬实时**的：它必须在每个 block 的截止时间前算完，否则声卡缓冲区空了 → 爆音（dropout）。

以 48 kHz、block size 256 为例：

```
256 / 48000 = 5.33 ms
```

你有 5.33 ms 算完这个 block。**没有第二次机会**——算不完不是"慢一点"，是"声音断了"。

> [!warning] 关键区别
> 普通程序慢一点用户会等；音频线程慢一点用户**立刻听到**。
> 而且这个线程由宿主/驱动调度，优先级很高，你**不能阻塞它**。

## 契约：音频线程中绝对禁止的事

| 禁止 | 为什么 | 正确做法 |
|---|---|---|
| ❌ `new` / `delete` / `malloc` | 堆分配可能触发系统调用、可能阻塞在锁上、耗时不可预测 | `prepareToPlay()` 里预分配，音频线程只读写 |
| ❌ 加锁（`mutex`、`lock_guard`） | 优先级反转：低优先级线程持锁时音频线程会**等**它 | 无锁结构，见下文 |
| ❌ 文件 I/O、`printf`、日志 | 系统调用，可能阻塞几十毫秒 | 写入无锁队列，其他线程消费 |
| ❌ 抛异常 | 栈展开 + 可能分配 | 音频路径上不用异常 |
| ❌ 调用未知的第三方代码 | 你无法保证它不分配不锁 | 自己审计，或隔离 |
| ❌ `std::function` 的隐式分配 | 捕获大的 lambda 会在堆上分配 | 用函数指针、模板、或预留的存储 |
| ❌ 字符串操作、`std::string` 拼接 | 大概率分配 | 预格式化，或用固定缓冲 |
| ❌ 等待其他线程 | 死锁风险 + 时间不可控 | 用原子标志和队列 |
| ❌ denormal 数不做处理 | 某些 CPU 上 denormal 运算慢 100 倍 | 见 [[denormal 数处理]] |

> [!tip] 一句话版本
> **音频线程里，时间必须可预测。任何"通常很快"的操作都不可接受——你要的是最坏情况。**

## `processBlock` 的隐含约定

以 JUCE 为例（其他框架类似）：

```cpp
void processBlock (juce::AudioBuffer<float>& buffer, juce::MidiBuffer& midi) override
{
    // ✅ 这里的 buffer 已经是"你的"了，可以直接改
    // ✅ midi 里的事件时间戳是相对本 block 起点的 sample 数
    // ❌ 不要在这里分配、加锁、打日志
    // ❌ 不要假设 buffer 的声道数或长度和上次一样（虽然通常是）
}
```

**常见误解**：

- ❌ "`getSampleRate()` 可以随时变" → 会变，但变化时宿主会先调 `prepareToPlay()`
- ❌ "`processBlock` 会被调用在固定 block size" → 不一定，宿主可能给 0 长度的 block
- ❌ "buffer 的声道数固定" → 会变（单声道轨 → 立体声总线）

> [!warning] `buffer.getNumSamples() == 0` 是合法的
> 很多插件忘了判断，然后除以 0 或者访问越界。
> **`processBlock` 的第一行应该是 early return 或至少处理这个情况。**

## 生命周期

```
构造函数          ← 不要做重活（会影响宿主扫描插件）
  ↓
prepareToPlay(sampleRate, blockSize)   ← 预分配、重置滤波器状态、算系数
  ↓
processBlock(...)  ×  N                ← 硬实时，遵守契约
  ↓
releaseResources()                     ← 释放
  ↓
析构
```

> [!warning] 宿主会多次调用 `prepareToPlay`
> 用户切换采样率、改 buffer size、甚至某些宿主每次播放都会调。
> **必须保证它是幂等的、可重复调用的、不会泄漏的。**

**推论**：所有依赖采样率的系数计算（滤波器系数、延迟线长度）都必须在 `prepareToPlay` 里做，不能在构造函数里做。

## 无锁：三个够用的模式

### 1. 原子参数（最简单）

```cpp
std::atomic<float> targetGain { 1.0f };

// UI 线程
targetGain.store (0.5f, std::memory_order_relaxed);

// 音频线程
const float g = targetGain.load (std::memory_order_relaxed);
```

**适用**：标量参数。**必须配合 [[参数平滑 parameter smoothing]]**，否则直接改会爆音（zipper noise）。

### 2. SPSC 队列（单生产者单消费者）

音频线程 → UI 线程传数据（波形、电平表）：

```cpp
// 音频线程（生产者）
if (! fifo.push (level)) { /* 丢弃，不要阻塞 */ }

// UI 线程（消费者）
float v;
while (fifo.pop (v)) { /* 更新显示 */ }
```

**关键**：满的时候**丢弃**，不等待。丢失一个电平值无所谓，阻塞音频线程是灾难。

### 3. 双缓冲 + 原子交换（传大块数据）

UI 线程准备好一整个新参数集/IR，原子交换指针，音频线程读。

> [!warning] 这个模式有个陷阱
> 音频线程可能正在读旧缓冲时，UI 线程把新的写进来、又交换一次。
> 需要**三重缓冲**或引用计数才能安全回收。
> JUCE 提供了 `AbstractFifo` 和 `AudioProcessorValueTreeState`，优先用现成的。

## 参数自动化：为什么不能直接用原子量

宿主可能在**每个 sample** 上改变参数（自动化）。如果你每个 sample 都直接应用：

```cpp
// ❌ 这会爆音
gain = paramValue;  // 一个 sample 内从 0.1 跳到 0.9
```

**正确做法**：平滑。见 [[参数平滑 parameter smoothing]]。

```cpp
// ✅ 每 sample 向目标值靠近
current += (target - current) * smoothingCoeff;
```

> [!note] 平滑的代价
> 平滑会引入**延迟**。极快的变化（如瞬态）会被削平。
> 所以有些参数不该平滑（如开关、滤波器类型切换），有些必须平滑（增益、频率、Q）。
> **判断标准：听感上是否会出现"咔哒声"。**

## Denormal 数：最阴险的性能陷阱

当信号衰减到极小（如混响尾音、反馈延迟的尾巴），浮点数会进入 **denormal**（非规格化）范围：约 $10^{-38}$ 以下。

**问题**：某些 CPU 处理 denormal 时慢 **10–100 倍**。你的混响在安静时突然 CPU 飙升，就是这个。

**解决方案**：

```cpp
// 方法 1：加一个极小的直流偏置（最简单，但会引入 DC）
constexpr float antiDenormal = 1.0e-20f;
y = a * x + b * yPrev + antiDenormal;

// 方法 2：检测并清零（更干净）
if (std::abs (y) < 1.0e-30f) y = 0.0f;

// 方法 3：编译选项
// -ffast-math（GCC/Clang）会把 denormal 当 0 处理
// ⚠️ 但 -ffast-math 会破坏 IEEE 语义，可能影响你的 DSP 正确性
```

> [!warning] `-ffast-math` 是个陷阱
> 它会假设没有 NaN/Inf、允许重排浮点运算。
> 对音频 DSP 通常"看起来没事"，但会让你**失去对数值行为的控制**，
> 而且在出问题时极难调试。**建议用方法 1 或 2，保留 IEEE 语义。**

## 怎么验证你没违反契约

| 工具 | 检查什么 |
|---|---|
| **AddressSanitizer** | 内存越界、use-after-free |
| **ThreadSanitizer** | 数据竞争 |
| **pluginval**（严格模式） | 宿主会做的各种恶劣调用 |
| **Xcode Instruments** | 实时线程上的系统调用、分配 |
| **`malloc` 断点** | 在 `processBlock` 里设断点，看有没有分配 |

> [!tip] 最实用的一个测试
> 在 `processBlock` 里加一行临时的断言/断点，如果它在播放中被触发，你就找到了一个违规。
> 更彻底的做法是重载全局 `operator new`，在音频线程里调用时直接 `assert`。

## AI 会怎么写错

> [!danger] 这是 AI 最容易违反的契约——它默认不知道实时约束

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **`processBlock` 里 `push_back`** | 分配内存 → 爆音 | grep `push_back` |
| 2 | **用 `std::mutex` 保护参数** | 优先级反转 | grep `mutex`/`lock` |
| 3 | **`std::string` 拼接** | 分配 | 用 `char[]` 或预分配 |
| 4 | **`printf`/日志** | IO 阻塞 | 只在非实时路径 |
| 5 | **在音频线程读文件** | 阻塞 | 预先加载 |
| 6 | **构造函数里做重活** | 宿主扫描超时 | 移到 `prepareToPlay` |
| 7 | **`new`/`delete`** | 分配 | 预分配 |
| 8 | **`try/catch`** | 异常可能分配 | 不用异常 |
| 9 | **忘记 `ScopedNoDenormals`** | 安静时 CPU 飙升 | 加上 |
| 10 | **以为"只有偶尔慢没关系"** | 实时是硬约束 | 见 [[插件验证工具]] |

> [!danger] AI 不知道的默认前提
> 它的训练数据里，**"用 `std::vector` 动态增长"是完全正常的写法**。
> 在音频线程里，这一条就是致命的。
>
> **判据**：`processBlock` 的调用链里 grep：
> `push_back` / `resize` / `new` / `malloc` / `mutex` / `printf` / `std::string`
