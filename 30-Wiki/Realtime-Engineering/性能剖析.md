# 性能剖析

> [!important] 一句话
> **先测量，再优化。** 音频性能的核心指标不是"多快"，而是
> **单核能不能在实时预算内跑完**。

## 实时预算：先算清楚你有多少余量

$$\text{每样本预算} = \frac{1}{f_s} \quad \text{秒} = \frac{10^9}{f_s} \quad \text{纳秒}$$

| 采样率 | 每样本预算 |
|---|---|
| 44.1 kHz | **22.68 ns** |
| 48 kHz | **20.83 ns** |
| **96 kHz** | **10.42 ns** |
| 192 kHz | 5.21 ns |

> [!danger] 这是**单核**预算，而且要用掉一部分给宿主和其他插件
> 一个插件占用 30% 的单核预算 = **在 96kHz 下，40 个轨道就跑不动了**。
>
> **实践目标**：核心 DSP 占 **< 5%** 预算。

## 二、实测：常见滤波器组件的开销

**测试环境**（本机实测）：Apple Silicon arm64，clang 21，`-O2`，
480000 样本 × 100 次重复，输出累加到 `sink` 防止被优化掉。

| 组件 | 耗时/样本 | **占 96kHz 预算** |
|---|---|---|
| **一阶低通** | 1.430 ns | **13.7%** |
| **Biquad 直接 I 型** | 1.575 ns | **15.1%** |
| **SVF（Chamberlin）** | 2.666 ns | **25.6%** |
| **Biquad 转置直接 II 型** | 3.067 ns | **29.4%** |

> [!warning] 怎么读这些数字
> 这是**极端敏感的微基准**（每样本只做几次运算，全部在 L1 里）。
> 它测的是**指令级开销**，不代表真实插件里的表现（那里有内存访问、分支等）。
>
> **用途**：比较**相对**开销，而不是预测绝对占用。

> [!note] 一个反直觉的结果
> **转置直接 II 型比直接 I 型慢**（3.067 vs 1.575 ns）。
>
> 但转置直接 II 型的**数值行为更好**（见 [[IIR 滤波器]]）。
> **这是一个真实的取舍**：
> - 追求速度 → 直接 I 型
> - 追求数值稳定（尤其 float32 高阶）→ 转置直接 II 型
>
> 在"单个 biquad"的规模下，差别可以忽略；
> **在级联 4-8 个 biquad 时，这个差别会累积。**

## 三、⚠️ 基准测试的第一个坑：被优化掉

> [!danger] 本库实测踩过的坑
> 我第一次写基准时，一阶低通测得 **0.00 ms**——因为：
> ```cpp
> for(int i=0;i<N;i++) f.p(buf[i]);      // ❌ 结果没被使用
> ```
> 编译器发现"没有可观察结果"，**把整个循环删掉了**。
>
> 实测输出：
> ```
> 一阶低通    0.00 ms   0.000 ns/样本    0.0% 单核    ← 明显不对
> ```

**修法**：把结果累加到一个会被使用的变量：

```cpp
double sink = 0.0;
for(int r = 0; r < reps; ++r)
    for(int i = 0; i < N; ++i)
        sink += f.p(buf[i]);          // ✅ 结果被使用 → 不会被删

// 最后要"使用" sink（打印/比较），否则前面还是会被优化
if (std::abs(sink) < -1.0) std::printf("never");   // 或者直接打印
```

> [!tip] 更稳的做法
> | 方法 | 说明 |
> |---|---|
> | **累加 + 打印** | 简单有效（本页做法） |
> | `volatile` sink | 有效但会抑制优化 |
> | `asm volatile("" ::: "memory")` | 编译器屏障，精确控制 |
> | 用真实的 benchmark 框架 | Google Benchmark / Catch2 benchmark |

> [!warning] `volatile` 的副作用
> 把 sink 声明为 `volatile` 会**阻止编译器优化累加本身**，
> 导致测出的时间包含额外的内存写入。
> **本页用"累加 + 打印"**——既防止删除，又不引入额外开销。

## 四、本机可用的剖析工具（实测）

| 工具 | 状态 | 用途 |
|---|---|---|
| `time` | ✅ 可用 | 粗粒度计时（整个进程） |
| **`dtrace`** | ✅ **可用** | macOS 的系统级追踪 |
| `perf` | ❌ 未安装（Linux 工具） | — |
| `instruments` | ❌ 未安装（需 Xcode GUI） | — |
| `std::chrono` | ✅ **标准库** | ✅ **最实用** |

> [!tip] 对插件开发，`std::chrono` 就够了
> ```cpp
> #include <chrono>
> auto t0 = std::chrono::steady_clock::now();
> // ... 被测代码 ...
> auto t1 = std::chrono::steady_clock::now();
> double ms = std::chrono::duration<double, std::milli>(t1 - t0).count();
> ```
>
> **要点**：
> - 用 `steady_clock`（不受系统时间调整影响）
> - **预热**（第一次运行有 cache miss、分支预测未训练）
> - **重复多次取平均**
> - 报告 **ns/样本**（而不是总时间）

**JUCE 的 `PerformanceCounter`**：

```cpp
juce::PerformanceCounter perf ("processBlock");
perf.start();
// ... 被测代码 ...
double ms = perf.stop();
```
⚠️ **不要在发布版里留着**（它自己也有开销）。

## 五、优化方向（按收益排序）

> [!important] 顺序很重要：先做收益大的

| # | 优化 | 典型收益 | 代价 |
|---|---|---|---|
| 1 | **算法选择**（FFT 卷积 vs 直接） | **10×+** | 复杂度和延迟 |
| 2 | **减少重复计算**（系数只在参数变化时算） | 大 | 无 |
| 3 | **避免向量化阻碍**（消除分支、对齐） | 2-4× | 代码可读性 |
| 4 | **避免伪共享**（`alignas(64)`） | 实测 **7.5×**（多核） | 内存占用 |
| 5 | **`-O3` / LTO** | 1.2-2× | 构建时间 |
| 6 | **手写 SIMD** | 2-4× | 可移植性差 |
| 7 | 减少函数调用（内联） | 小 | 代码膨胀 |

> [!danger] 最常见的"优化"是错的
> **在没测量之前优化**。
> 你会花几小时优化一个只占 2% 的部分，
> 而真正的瓶颈（比如某个隐藏的 `std::vector` 分配）没被发现。
>
> **先测，再改，再测。**

## 六、音频专属的性能陷阱

> [!important] 这些在通用性能指南里不会提

| 陷阱 | 症状 | 检查 |
|---|---|---|
| **denormal** | 静音时 CPU 飙升 10-100× | 见 [[denormal 数处理]] |
| **音频线程分配** | 偶发爆音（不是持续高占用） | 重载 `operator new` |
| **伪共享** | 多核时异常慢 | `alignas(64)` |
| **每样本重算系数** | CPU 高但"看起来没做多少事" | 检查 `sin/cos/exp` 位置 |
| **虚函数调用** | 少量开销，但在内层循环明显 | 热路径去虚化 |
| **未对齐的 SIMD 访问** | 比对齐慢很多 | 用 `alignas` |
| **错误的 block size** | 小 block 时开销比例高 | 用多种 block size 测 |

**denormal 的实测特征**：

```
正常信号：CPU 5%
安静下来（信号衰减到 denormal 区）：CPU 40%+
```

> [!tip] 这个症状非常好认
> **"安静时 CPU 反而高"** 就是 denormal。
> 见 [[denormal 数处理]]。

## 七、AI 会怎么写错

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **基准结果没被使用** | 被优化掉，测出 0 | 累加 + 打印 |
| 2 | **不预热** | 首次结果偏慢 | 先跑一轮 |
| 3 | **只跑一次** | 噪声大 | 重复取平均 |
| 4 | **用 `system_clock`** | 受系统时间影响 | 用 `steady_clock` |
| 5 | **报告总时间而非 ns/样本** | 无法比较 | 归一化 |
| 6 | **在音频线程做性能测量** | 测量本身破坏实时性 | 离线测 |
| 7 | **没考虑 denormal** | 测不出最坏情况 | 加安静段测试 |
| 8 | **只看平均不看最坏** | 偶发爆音 | 看 max/99 分位 |
| 9 | **在 Debug 构建里测** | 慢 10×，无意义 | 用 Release |
| 10 | **优化没测量的部分** | 白费力气 | 先剖析 |

> [!danger] 第 1 条是本库真实踩过的
> 我测一阶低通时得到 **0.00 ms**——
> 一开始以为是"这一阶太快了"，其实是**整个循环被删掉了**。
>
> **判据**：结果"好得不像真的"时，先怀疑测量。

## 八、常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| 测出 0 ms | 被优化掉 | 累加 + 打印 |
| 结果波动大 | 没预热/没重复 | 预热 + 多次平均 |
| Debug 里很慢 | 没开优化 | 用 Release |
| 安静时 CPU 高 | denormal | 加偏置/FTZ |
| 多核时慢 | 伪共享 | `alignas(64)` |
| 小 block 时占用高 | 固定开销比例大 | 用多种 block size 测 |
| 优化了但没变快 | 优化了非瓶颈 | 先剖析 |

## 九、怎么验证（基准测试的基准）

> [!important] 用"已知开销"校准你的测量框架

```cpp
#include <chrono>
#include <cstdio>
#include <cmath>
#include <vector>

static double now_ms() {
    return std::chrono::duration<double, std::milli>(
        std::chrono::steady_clock::now().time_since_epoch()).count();
}

// ① 先测一个"已知开销"的操作，确认测量框架有效
void calibrate (int N, int reps) {
    std::vector<float> buf (N, 0.5f);
    double sink = 0.0;
    for (int i = 0; i < N; ++i) sink += buf[i];      // 预热
    const double t0 = now_ms();
    for (int r = 0; r < reps; ++r)
        for (int i = 0; i < N; ++i)
            sink += buf[i] * 0.5f;
    const double ns = (now_ms() - t0) * 1e6 / ((double)reps * N);
    std::printf ("  校准: 单次乘加 %.3f ns/样本  (应为 0.3-2 ns)\n", ns);
    if (ns < 0.05) std::printf ("  ⚠️ 太快了，可能被优化掉了！\n");
}
```

> [!tip] 校准的意义
> **一次浮点乘加大约 0.3-2 ns**（现代 CPU）。
> 如果你的测量显示"每样本 0.001 ns"，那一定是被优化掉了。
>
> **先证明你的测量框架能看到已知的开销，再测别的。**

**完整基准模板**：

```cpp
template <typename F>
void bench (const char* name, F f, int N, int reps, double fs) {
    std::vector<float> buf (N);
    for (int i = 0; i < N; ++i)
        buf[i] = std::sin (2*3.14159f*440*i/(float)fs) * 0.5f;

    double sink = 0.0;
    for (int i = 0; i < N; ++i) sink += f.p (buf[i]);      // 预热

    const double t0 = now_ms();
    for (int r = 0; r < reps; ++r)
        for (int i = 0; i < N; ++i)
            sink += f.p (buf[i]);
    const double ns = (now_ms() - t0) * 1e6 / ((double)reps * N);

    const double budget_ns = 1e9 / fs;
    std::printf ("  %-24s %6.3f ns/样本  %5.1f%% 预算\n",
                 name, ns, ns / budget_ns * 100);

    if (std::abs (sink) < 1e-30) std::printf ("  ⚠️ 结果异常，可能被优化\n");
}
```
