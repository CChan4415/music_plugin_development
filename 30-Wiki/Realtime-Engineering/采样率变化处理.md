# 采样率变化处理

> [!important] 一句话
> **采样率是变量，不是常量。**
> 用户随时可能改（44.1k ↔ 48k ↔ 96k），而你的 DSP 必须跟着重算。

## 为什么这是"偶发爆音"的常见来源

> [!danger] 症状
> 用户在宿主设置里换了采样率 →
> **一声爆音**，或者**声音明显不对**（滤波器截止频率错）。
>
> 而你在开发时用固定 48kHz，**永远复现不了**。

---

## 一、实测：哪些东西依赖采样率

### 1. 延迟线长度（本库验证）

**延迟必须按"秒"定义**：

| 延迟 | @44.1 kHz | @48 kHz | @96 kHz |
|---|---|---|---|
| 1 ms | 44 | 48 | 96 |
| **10 ms** | 441 | **480** | **960** |
| 50 ms | 2205 | 2400 | 4800 |
| 100 ms | 4410 | 4800 | 9600 |

> [!danger] 写死采样数的后果
> ```cpp
> // ❌ 写死 480 采样
> delayLine.setSize (480);
> ```
> | 采样率 | 实际延迟 |
> |---|---|
> | 48 kHz | 10 ms ✅ |
> | **96 kHz** | **5 ms** ❌ **时间不对！** |
>
> **混响的 RT60、合唱的调制深度全都会错。**

### 2. 滤波器系数

**Biquad 的 $w_0 = 2\pi f_c/f_s$** —— $f_s$ 变了，系数必须重算。

**实测**（1 kHz 低通，Q=0.707）：

| 采样率 | $b_0$ | $a_1$ |
|---|---|---|
| 44.1 kHz | 0.00460394 | -1.79907162 |
| 48 kHz | 0.00391608 | -1.81531792 |
| 96 kHz | 0.00102321 | -1.90748889 |

> [!warning] 系数完全不同
> **用旧系数在新采样率下跑 = 截止频率完全错。**
> 而且不会报错，只是"声音不对"。

### 3. 包络/平滑的系数

```cpp
// 时间常数 → 系数
coeff = 1 - exp(-1/(tau * fs));      // ⚠️ 依赖 fs
```
采样率变了，**attack/release 的实际时间也变了**。

### 4. LFO 的相位增量

```cpp
phase += rate / sr;                   // ⚠️ 依赖 sr
```

## 二、实测：状态残留的后果

**测试**：一阶低通 `y = (1-a)x + a·y`，用 48 kHz 的系数，
但状态里留着上一次的残余（`y` 初值 = 0.5 而非 0）。

| | 前 5 个样本 |
|---|---|
| **状态干净** | `[0.1227, 0.1076, 0.0944, 0.0828, 0.0727]` |
| **状态残留** | `[0.5613, 0.4925, 0.4320, 0.3790, 0.3325]` |
| **最大差异** | **0.4387** |

> [!danger] 状态残留 = 输出从头就偏
> 表现：**换采样率瞬间的爆音/咔哒**。
>
> **所以 `prepareToPlay` 里必须重置所有 DSP 状态。**

---

## 三、正确的 `prepareToPlay`

```cpp
class MyProcessor : public juce::AudioProcessor
{
public:
    void prepareToPlay (double sampleRate, int samplesPerBlock) override
    {
        // ① ⚠️ 会被**反复调用**（换采样率/换块大小/换设备）
        //    所以整个函数必须**幂等**

        sr = sampleRate;                       // 保存
        blockSize = samplesPerBlock;

        // ② 按"秒"换算延迟线长度
        const int maxDelaySamples = (int) std::ceil (maxDelayMs * 0.001 * sr);
        delayLine.setSize (maxDelaySamples);   // resize 是幂等的

        // ③ 重算所有依赖采样率的系数
        updateFilterCoefficients();

        // ④ ⭐ 重置所有 DSP 状态
        resetState();

        // ⑤ 延迟变化要重新报告
        const int latency = computeLatency();
        if (latency != reportedLatency) {
            reportedLatency = latency;
            setLatencySamples (latency);       // ⚠️ prepare 里调用是安全的
        }
    }

    void resetState() noexcept
    {
        delayLine.clear();
        filterState = {};
        envelope = 0.0f;
        lfoPhase = 0.0;
        // ... 所有状态
    }

private:
    double sr = 48000.0;
    int blockSize = 512;
    float maxDelayMs = 100.0f;
    int reportedLatency = 0;
};
```

> [!important] 五个要点
> | # | 要点 |
> |---|---|
> | 1 | **按"秒"定义**所有时间量，在 prepare 里换算成采样数 |
> | 2 | **重算所有系数**（滤波器、包络、LFO） |
> | 3 | **重置所有状态**（否则有爆音） |
> | 4 | **重新报告延迟**（如果延迟依赖采样率） |
> | 5 | **整个函数幂等**（会被反复调用） |

## 四、⚠️ 不能在音频线程做的事

> [!danger] `setLatencySamples` 不能在 `processBlock` 里调
> 宿主内部可能要加锁 → **爆音**。
>
> **正确**：在 `prepareToPlay`（宿主明确要求准备时）里调。
> 见 [[延迟报告 latency reporting]]、[[旁路 bypass 的正确实现]]。

> [!warning] 但如果延迟**在运行中**变化呢？
> 例如用户切换过采样倍率 → 延迟变了。
>
> **正确做法**：
> 1. 音频线程只**设置一个原子标志**
> 2. 消息线程（参数回调）检测到标志 → 调用 `setLatencySamples`
>
> ```cpp
> // 音频线程
> pendingLatency.store (newLatency, std::memory_order_relaxed);
> // 消息线程（定时器或参数回调）
> if (auto v = pendingLatency.exchange (0); v > 0)
>     setLatencySamples (v);
> ```

## 五、AI 会怎么写错

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **延迟线写死采样数** | 换采样率后时间错 | 按秒定义 |
| 2 | **系数只在构造时算一次** | 换采样率后频率错 | 移到 `prepareToPlay` |
| 3 | **不重置状态** | 换采样率瞬间爆音 | 加 `resetState()` |
| 4 | **`prepareToPlay` 不幂等** | 反复调用泄漏/累积 | 检查 |
| 5 | **在 `processBlock` 里调 `setLatencySamples`** | 宿主加锁 → 爆音 | 移到消息线程 |
| 6 | **硬编码 44100 或 48000** | 换采样率就错 | 用传入的 `sampleRate` |
| 7 | **包络系数不重算** | attack/release 时间不对 | 重算 |
| 8 | **忘了重新报告延迟** | 多轨错位 | 检查 |
| 9 | **`resize` 不检查返回值** | 分配失败静默 | 检查 |
| 10 | **假设采样率是整数** | 44100.0 是 double | 用 `double` |

> [!danger] 第 1、2 条是"听起来不对但不崩"的典型
> 它们**不会崩溃**，只是声音错了。
> 用户会说"这个插件在 96k 下声音怪怪的"——
> 而你如果只在 48k 测试，**永远找不到原因**。
>
> **判据**：grep 代码里的裸数字（`44100`、`48000`、`512`）。

## 六、常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| 换采样率后爆音 | 状态没重置 | `resetState()` |
| 换采样率后频率错 | 系数没重算 | 移到 prepare |
| 96k 下混响时间不对 | 延迟线写死采样数 | 按秒定义 |
| attack 时间不对 | 包络系数没重算 | 重算 |
| 反复改设置后变慢 | prepare 不幂等 | 检查累积 |
| 多轨错位 | 延迟没重新报告 | 检查 |
| 换采样率时咔哒 | 音频线程调宿主 API | 移到消息线程 |

## 七、怎么验证

**三个必做测试**：

| # | 测试 | 判据 |
|---|---|---|
| 1 | **多种采样率** | 44.1k/48k/96k/192k 都不崩、行为一致 |
| 2 | **反复 `prepareToPlay`** | 无泄漏、无累积 |
| 3 | **运行中切换** | 无爆音 |

```bash
# ⭐ 遍历采样率（本库推荐）
clang++ -std=c++17 -O1 -g \
    -fsanitize=address,undefined -fno-sanitize-recover=all \
    test_dsp.cpp -o test_dsp_san

for sr in 44100 48000 88200 96000 192000; do
    printf "  sampleRate=%-7s " "$sr"
    ./test_dsp_san 512 "$sr" >/dev/null 2>&1 && echo "✅" || echo "❌"
done
```

> [!important] 行为一致的判据
> 不只是"不崩"——还要**行为一致**：
> - 10 ms 的延迟在**所有采样率下都是 10 ms**
> - 1 kHz 的滤波器在**所有采样率下都是 1 kHz**
>
> ```python
> # 用解析解校验（本库做法）
> for sr in [44100, 48000, 96000]:
>     # 测 -3dB 点，应始终 ≈ 1000 Hz
>     assert abs(measured_f3 - 1000) < 20, f"{sr} 下频率不对"
> ```

**运行中切换的测试**（需真实插件）：

```
在 REAPER 里：
① 播放音频
② 打开音频设备设置，切换采样率
③ 听是否有爆音/咔哒
```
