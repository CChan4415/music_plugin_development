# 插件验证工具

> [!important] 一句话
> **这些工具会模拟"恶劣宿主"对你的插件做各种事**——
> 空缓冲区、极端 block size、反复 prepare/release、参数乱改。
> 你的插件在 REAPER 里跑得好，不代表能通过这些。

## 为什么必须用它们

你自己测试时只会做"正常操作"。但真实宿主会：

| 宿主会做的事 | 你的插件可能因此 |
|---|---|
| 传 0 长度的 block | 除以 0 / 越界 |
| 反复调用 `prepareToPlay` | 状态没重置 / 内存泄漏 |
| 在播放中改变采样率 | 系数没重算 → 声音错乱 |
| 传单声道给立体声插件 | 越界访问 |
| 连续快速改参数 | 爆音 / zipper noise |
| 扫描时构造又析构 | 构造函数做重活 → 超时 |

> [!warning] 本页的工具状态（2026-10-14 实测）
> | 工具 | 状态 |
> |---|---|
> | **`auval`** | ✅ **已装**（macOS 自带，`/usr/bin/auval`，版本 1.10.0） |
> | **pluginval** | ❌ 未安装（需下载） |
> | VST3 validator | ❌ 未安装（随 VST3 SDK） |
>
> **你现在还没有插件，所以这些工具暂时用不上。** 这一页是给阶段 4 准备的。

## 一、`auval` —— macOS 自带，测 AU

**这是你唯一"零成本立即可用"的验证工具。**

```bash
# 列出系统里所有已注册的 AU
auval -a

# 验证一个特定的 AU（需要知道它的四字符代码）
auval -v aufx Gnsx Acme

# 更详细的输出
auval -v aufx Gnsx Acme -de
```

**四字符代码的含义**（`auval -v TYPE SUBT MANU`）：

| 位置 | 含义 | 例子 |
|---|---|---|
| TYPE | 插件类别 | `aufx` = 效果器，`aumu` = 乐器，`augx` = 生成器 |
| SUBT | 子类型 | 你自己定义（要和代码里一致） |
| MANU | 厂商代码 | 你自己定义 |

> [!tip] 这三个代码在 JUCE 里怎么设
> ```cmake
> juce_add_plugin(MyPlugin
>     PLUGIN_MANUFACTURER_CODE Acme    # MANU，四字符
>     PLUGIN_CODE              Gnsx    # SUBT，四字符
>     FORMATS                  AU VST3
>     ...)
> ```
> ⚠️ **必须是四字符**，且**厂商代码最好唯一**（避免和其他厂商冲突）。
> 具体字符集限制**需查官方文档确认**。

> [!warning] `auval` 的失败很常见，而且报错难懂
> 新手第一次跑 `auval` 大概率会失败。常见原因：
> - 参数范围定义不一致
> - 没处理 0 长度缓冲区
> - `prepareToPlay` 不幂等
> - 声道配置声明和实际不符
>
> **把这当作好事**——它提前发现了宿主会发现的问题。

## 二、pluginval —— 跨平台，最全面的验证

**插件开发者事实上的标准工具**（JUCE 团队维护）。

| 项 | 值 |
|---|---|
| 仓库 | <https://github.com/Tracktion/pluginval> |
| 支持 | VST3 / AU / VST2，macOS / Windows / Linux |
| 特点 | 有**严格度等级**（1–10），等级越高测试越恶劣 |

**用法**（下载后）：

```bash
# GUI 模式（推荐新手）
open pluginval.app

# 命令行模式
pluginval --strictness-level 10 --validate MyPlugin.vst3
```

> [!important] 用最高严格度
> `--strictness-level 10` 会做最恶劣的测试：
> 极端 block size、反复 prepare、参数轰炸、线程检查等。
> **发布前必须过 10 级。**

## 三、VST3 validator —— Steinberg 官方

随 **VST3 SDK** 一起提供。如果你用 JUCE，SDK 会被自动拉取，
validator 通常在 SDK 的构建产物里。

**它的作用**：验证插件是否符合 VST3 规范（比 pluginval 更偏"规范符合性"）。

> [!note] 优先级
> 对个人开发者：**pluginval（10 级）> auval > VST3 validator**。
> pluginval 覆盖面最广且最容易跑。

## 四、REAPER 本身就是验证工具

> [!tip] 一个被低估的事实
> **REAPER 是插件开发者最宽容也最透明的测试宿主。**
>
> 为什么：
> - 支持所有格式（VST3 / AU / CLAP / VST2）
> - **报错信息最清晰**（会告诉你哪个插件崩了、为什么）
> - 插件扫描有详细日志
> - 可以强制各种 block size
> - 可以加载"插件桥"来隔离崩溃

**实用操作**：

| 操作 | 位置 |
|---|---|
| 强制 block size | Preferences → Audio → Buffering |
| 重新扫描插件 | Preferences → Plug-ins → Re-scan |
| 看扫描日志 | Preferences → Plug-ins → 显示日志 |
| 只加载特定格式 | Preferences → Plug-ins → 勾选格式 |

## 五、调试工具（比验证工具更底层）

| 工具 | 用途 | 平台 |
|---|---|---|
| **AddressSanitizer (ASan)** | 内存越界、use-after-free | 全平台，`-fsanitize=address` |
| **ThreadSanitizer (TSan)** | 数据竞争 | 全平台，`-fsanitize=thread` |
| **UndefinedBehaviorSanitizer (UBSan)** | 未定义行为 | 全平台，`-fsanitize=undefined` |
| **Xcode Instruments** | CPU 剖析、内存、实时线程检查 | macOS |
| **lldb** | 断点调试 | macOS |
| **Valgrind** | 内存检查 | Linux（**Apple Silicon 上支持情况需核实**） |

> [!warning] ASan 和音频
> ASan 会让程序**慢 2–20 倍**。所以：
> - ✅ 用来跑**离线渲染测试**和**单元测试**
> - ❌ 不要在实时播放时用（会爆音，且掩盖真实性能问题）

**在 CMake 里加 sanitizer**：

```cmake
option(ENABLE_ASAN "Enable AddressSanitizer" OFF)
if(ENABLE_ASAN)
    target_compile_options(MyPlugin PRIVATE -fsanitize=address -fno-omit-frame-pointer)
    target_link_options(MyPlugin PRIVATE -fsanitize=address)
endif()
```

## 六、⚠️ 最有效的"自制"验证：重载 `operator new`

> [!tip] 这一招比任何工具都直接
> 在音频线程里分配内存是**头号违规**。
> 用一个全局 `operator new` 就能抓住它：

```cpp
// 只在 Debug 构建里启用
#if JUCE_DEBUG
#include <atomic>
#include <cstdlib>

std::atomic<bool> inAudioThread { false };

void* operator new (std::size_t size)
{
    if (inAudioThread.load (std::memory_order_relaxed))
    {
        // 在音频线程里分配了！立刻中断，看调用栈
        jassertfalse;          // JUCE 的断言，会断在调试器
        // 或者：std::abort();
    }
    if (auto* p = std::malloc (size)) return p;
    throw std::bad_alloc();
}

void operator delete (void* p) noexcept { std::free (p); }
#endif
```

**在 `processBlock` 里设置标志**：

```cpp
void processBlock (juce::AudioBuffer<float>& buffer, juce::MidiBuffer& midi) override
{
   #if JUCE_DEBUG
    inAudioThread.store (true, std::memory_order_relaxed);
   #endif

    // ... 你的处理 ...

   #if JUCE_DEBUG
    inAudioThread.store (false, std::memory_order_relaxed);
   #endif
}
```

> [!warning] 注意事项
> - 只用于 **Debug 构建**（Release 会有性能开销）
> - 有些库会在初始化时分配（那是合法的，不在音频线程里）
> - 更严谨的做法是**记录音频线程 ID**，而不是用布尔标志

## 七、发布前的验证清单

- [ ] `pluginval --strictness-level 10` **通过**
- [ ] `auval -v` **通过**（AU 格式）
- [ ] 在 **REAPER** 里：正常播放、改 block size、改采样率
- [ ] 在 **Ableton** 里：正常播放、参数自动化、保存/重开工程
- [ ] **0 长度 block** 不崩
- [ ] **反复 prepare/release** 不泄漏
- [ ] **参数自动化** 不爆音
- [ ] **旁路** 时完全无染色（用 null test 验证）
- [ ] Debug 构建下**没有触发 `operator new` 断言**
- [ ] 单声道 / 立体声 / 多声道输入都正确
- [ ] 极端参数不爆炸（f0、Q、feedback 都钳制了）
- [ ] 状态保存/恢复正确（关掉宿主再打开，参数还在）
- [ ] ASan 构建跑离线渲染无报错

## 八、AI 会怎么写错

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **不处理 0 长度 block** | 除以 0 或越界 | 检查 `processBlock` 开头 |
| 2 | **`prepareToPlay` 里累积分配** | 反复调用 → 内存泄漏 | 检查是否有 `resize` 无上限增长 |
| 3 | **参数不钳制** | 用户能调出爆炸 | 检查所有参数范围 |
| 4 | **构造函数里做重活** | 宿主扫描超时 | 检查构造函数只做轻量初始化 |
| 5 | **不声明 latency** | 宿主补偿错误，录音不同步 | 检查 `setLatencySamples` |
| 6 | **旁路时仍处理** | 旁路有染色 | 检查 `isBypassed` 处理 |
| 7 | **状态保存漏参数** | 重开工程参数丢失 | 对比参数列表和 `getStateInformation` |

> [!tip] 让 AI 自查的提示词
> ```
> 检查这个 processBlock 实现：
> 1. 有没有内存分配、加锁、文件 IO？
> 2. 如果 numSamples == 0 会怎样？
> 3. 如果声道数变成 1 会怎样？
> 4. 所有参数都钳制了吗？
> ```
> 然后**自己核对**它的回答——AI 经常会说"没问题"但实际有问题。

## 常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| sanitizer 报一堆无关错误 | 第三方库也插桩了 | 用抑制文件 |
| ASan 和 TSan 一起开 | 不兼容 | 分开构建 |
| 检测不到问题 | 参数没遍历 | 见 [[AddressSanitizer]] |
| CI 上跑不了 sanitizer | 环境/权限 | 用容器 |
| 性能测试结果波动大 | 没预热/没多次 | 见 [[性能剖析]] |
| TSan 通过但仍有问题 | 内存序不足 | 见 [[ThreadSanitizer 与内存序]] |
| 忘了测极端 block size | 只测了 512 | 遍历 0/1/…/4096 |
