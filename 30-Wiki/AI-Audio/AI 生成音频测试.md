# AI 生成音频测试

> [!important] 一句话
> **让 AI 写测试脚本，是本知识库里 AI 性价比最高的用法。**
> 但有个前提：**你必须先验证测试脚本本身是对的**——否则它会把正确的代码判成错的。

## 为什么测试脚本特别适合交给 AI

| 特征 | 说明 |
|---|---|
| **逻辑明确** | "喂脉冲，看频响是否和公式一致"——意图清晰 |
| **容易验证** | 用已知答案就能校准 |
| **错了立刻看得出来** | 不像 DSP 核心，测试错了不会静默 |
| **省大量时间** | FFT、绘图、文件 IO 的 API 你不想查 |
| **可复用** | 写一次，以后每个插件都能用 |

> [!tip] 判断标准
> 问自己：**"如果这个脚本写错了，我能发现吗？"**
> 能 → 交给 AI。
> 不能 → 自己做，或者先写一个能验证它的东西。

## 一、⚠️ 第一步：用已知答案校准脚本本身

> [!danger] 这是本页最重要的内容
> 本库有**七次**"测量方法错、代码没错"的记录（见 [[2026-10-14 测量工具会骗你 —— 八次踩坑记录]]）。
> **AI 写的测试脚本同样会错**，而且错得很像真的。

### 三步校准法

拿到任何音频测试脚本，**先用一个答案已知的信号跑一遍**：

```python
import sys; sys.path.insert(0, '50-Playground/tools')
from audio_io import sine, spectrum, peak_db, dominant_freq, dominant_freq_autocorr
import numpy as np

x = sine(440, 1.0, amp=0.5)          # 已知：440Hz，幅度 0.5

# 1. 频率对不对
f, mag = spectrum(x, 48000)
assert abs(f[np.argmax(mag)] - 440) < 1, "峰值位置错"

# 2. 幅度对不对 ← 这一步能抓出 6dB 陷阱
assert abs(peak_db(x) - (-6.02)) < 0.1, "幅度错"

# 3. 两种独立方法是否一致（交叉验证）
assert abs(dominant_freq(x, 48000) - 440) < 1
assert abs(dominant_freq_autocorr(x, 48000) - 440) < 1

print("✅ 测试脚本校准通过")
```

**实测输出**：

```
1. 频率: FFT 峰值 440.00 Hz (期望 440)   ✅
2. 幅度: -6.02 dBFS (期望 -6.02)         ✅
3. 交叉验证: FFT 440.00 / 自相关 440.00  ✅
```

> [!important] 第 2 步是关键
> 本库的工具库曾经有个 bug：**加窗后没补偿相干增益**，
> 导致所有幅度测量**差 6.02 dB**——而这是个"看起来完全合理"的数字，藏了好几天。
>
> 如果当时有这个断言，一秒就能发现。

### 一个真实的反例

**过零计数测频率**（AI 很爱用这个）：

```python
# ❌ AI 常写的版本
x = np.sin(2*np.pi*440*np.arange(48000*2)/48000)   # 440Hz，2 秒
q = (x * 0.5 * 32767).astype(np.int16)             # int16 量化（关键）
zc = np.sum(np.diff(np.sign(q)) != 0)
freq = zc / 2 / 2.0
print(freq)          # → 479.8   ❌ 错了 40 Hz！
```

**实测**（440Hz 正弦，int16 量化）：

| 方法 | 结果 |
|---|---|
| ❌ `np.diff(sign)` | **479.8 Hz** |
| ✅ 只数上升沿 | 439.5 Hz |
| ✅ FFT 主峰 | **440.00 Hz** |

**原因**：int16 量化后**有 160 个样本恰好为 0**，
`np.sign(0) = 0` 会产生额外的符号变化，把一次过零数成多次。

> [!warning] 这个错误的可怕之处
> 479.8 Hz **看起来像个合理的频率**。
> 如果你不知道正确答案是 440，你会以为"代码有点小误差"然后继续。
> **结果就是：你去改正确的代码，去迎合错误的测试。**

## 二、让 AI 写什么测试

### 按价值排序

| # | 测试类型 | 为什么适合 AI | 怎么验证 |
|---|---|---|---|
| 1 | **测试信号生成** | 脉冲/扫频/白噪声/粉噪声 | 看波形、看频谱 |
| 2 | **频谱分析与绘图** | FFT、加窗、dB 转换 | 用已知正弦校准 |
| 3 | **与解析解对比** | 给定公式，生成对照曲线 | 本库 `check_response()` |
| 4 | **Null test** | 两个信号相减 | 相同信号应得 -inf |
| 5 | **边界用例** | 喂 0 长度/NaN/极值 | 看是否崩 |
| 6 | **批量回归** | 跑多个参数组合 | 看报告是否合理 |
| 7 | **性能测量** | CPU 占用、实例数 | 用已知负载校准 |

### 提示词模板

```
写一个 Python 脚本，验证我的 [滤波器/效果器] 实现：

1. 用**脉冲响应 + FFT** 测频率响应（不要用白噪声，有随机起伏）
2. 和**解析解**逐点对比，报告最大偏差（dB）
3. 用 440Hz 正弦校准脚本本身（期望峰值 440Hz、幅度 -6.02 dBFS）
4. 如果校准失败，先报错退出，不要继续测
5. 测试信号用确定性信号，不要用随机信号（除非测噪声）
6. 报告要包含：通过/失败、具体偏差数字、可能的原因
```

> [!tip] 第 3、4 条是关键
> **让脚本自检**。如果校准不过，后面的测试结果全不可信。

## 三、三个必备的测试信号

| 信号 | 代码 | 测什么 |
|---|---|---|
| **脉冲** | `x[0]=1, 其余 0` | **脉冲响应**——完全描述 LTI 系统；测频响的最佳选择 |
| **对数扫频** | 20Hz→20kHz | 频率响应（适合实测硬件，抗噪好） |
| **白噪声** | `randn` | 宽带整体影响（⚠️ 有随机起伏，不适合精确测频响） |

> [!warning] 为什么不用白噪声测频响
> 单次实现的白噪声 FFT 有**很大方差**——你会看到起伏的曲线，
> 以为是自己的代码有问题，其实是测量方法的问题。
>
> **脉冲响应是确定性的**，结果可复现。见 [[音频测量基础]]。

## 四、Null Test：把"听起来差不多"变成"数值一致"

```python
def null_test(a, b, label="null test"):
    a, b = np.asarray(a, float), np.asarray(b, float)
    n = min(len(a), len(b))
    d = a[:n] - b[:n]
    peak = 20*np.log10(np.max(np.abs(d)) + 1e-12)
    rel = peak - 20*np.log10(np.max(np.abs(a[:n])) + 1e-12)
    verdict = "✅ 等价" if rel < -100 else ("🟠 接近" if rel < -60 else "❌ 有差异")
    print(f"{label}: 最大差异 {peak:.1f} dB (相对 {rel:.1f} dB)  {verdict}")
```

**典型用途与期望**：

| 场景 | 期望结果 |
|---|---|
| C++ 实现 vs Python 参考实现 | < -100 dB |
| 优化前 vs 优化后 | < -100 dB（证明优化没改变行为） |
| **旁路时 vs 原始信号** | **-inf**（完全无染色） |

> [!warning] 取整陷阱：会让你停在 -90dB
> Python 的 `astype(int16)` 是**截断**，C 的 `lround` 是**四舍五入**。
> 差 1 LSB ≈ -90 dB——听感上无关，但会让 null test **停在 -90dB 而非 -inf**。
>
> **解法**：比浮点（不经过 WAV 编解码），或两边统一取整方式。
> 否则你会花几小时找"为什么不是 -inf"，而代码完全正确。

## 五、怎么发现 AI 的测试脚本有 bug

> [!important] 四个信号

| # | 信号 | 可能的原因 |
|---|---|---|
| 1 | **结果"恰好"是个整数或常见值** | 可能没测到真实信号（如测到噪声底、缓冲区末尾） |
| 2 | **所有参数组合结果完全相同** | 参数没真正生效 |
| 3 | **误差是 -6 dB 的倍数** | 窗函数相干增益没补偿 |
| 4 | **误差是 1 LSB 量级（-90dB）** | 取整约定不同 |

### 本库踩过的真实例子

| 现象 | 我以为 | 实际是 |
|---|---|---|
| 测出 479.8 Hz（期望 440） | 生成代码错了 | 过零计数被量化的 0 值骗了 |
| Q=30 的 ringing 比 Q=5 短 | 滤波器有 bug | 用了绝对阈值；高 Q 峰值更大 |
| 频谱幅度差 6.02 dB | 代码错了 | 加窗没补偿相干增益 |
| 全通增益 2.49 倍 | 稳态期不够 | **这次真的是实现错了** |
| 5kHz 增益 0.988 | 还是实现错 | 这次是稳态期不够 |

> [!tip] 归纳出的规则
> **结果反常时，先怀疑测量，再怀疑代码。**
> 但要记住第 4 行——**有时候真的是代码错**。
> 所以最终手段是：**与解析解逐点对照**。

## 七、AI 会怎么写错（测试脚本本身）

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **不加窗** | 频谱全是毛刺 | 检查有没有 `* window` |
| 2 | **加窗不补偿相干增益** | 幅度差 6 dB | 除以 `sum(w)` 而非 `N` |
| 3 | **用白噪声测频响** | 结果有随机起伏 | 改用脉冲响应 |
| 4 | **用过零计数测频率** | 被量化的 0 值骗 | 用 FFT 或自相关 |
| 5 | **用绝对阈值测衰减** | 高 Q 器件误判 | 用相对峰值 |
| 6 | **FFT 长度不够** | 截断泄漏 | 确认 >> 脉冲响应长度 |
| 7 | **`20*log10` 和 `10*log10` 混用** | 差一倍 | 幅度用 20，功率用 10 |
| 8 | **不校准脚本就下结论** | 用错误的测试改正确的代码 | **三步校准法** |
| 9 | **零填充后声称"分辨率提高"** | 概念错误 | 分辨率只由 N 决定 |
| 10 | **测量对象已衰减完还在测** | 测的是噪声底 | 先看包络 |

## 八、常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| 脚本报错但代码看着对 | 脚本本身有 bug | 三步校准法 |
| 结果每次不同 | 用了随机信号 | 用确定性信号 |
| 误差恰好 6 dB | 窗增益没补偿 | 除以 `sum(w)` |
| 误差恰好 1 LSB | 取整约定不同 | 统一，或比浮点 |
| 所有参数结果相同 | 参数没生效 | 检查参数传递 |
| 测出的衰减时间是整数 | 取到数组末尾 | 加长信号，或先看包络 |

## 九、怎么验证（测试的测试）

| 层次 | 方法 |
|---|---|
| **L1 脚本自检** | 三步校准法（已知正弦） |
| **L2 解析对照** | 和数学公式逐点比（`check_response`） |
| **L3 交叉验证** | 两种独立方法测同一个量 |
| **L4 回归** | 用历史 bug 案例测（本库有 8 个） |
| **L5 变异测试** | 故意改坏代码，看测试是否能抓到 |

> [!tip] L5 是最强的一招
> 故意把实现改错一点（比如符号反过来），**看测试是否失败**。
> 如果测试仍然通过，说明**测试没有真正覆盖那个行为**。
>
> 这就是"测试的测试"，AI 通常不会主动做这一步。
