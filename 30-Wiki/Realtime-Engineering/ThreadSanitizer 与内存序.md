# ThreadSanitizer 与内存序

> [!important] 一句话
> **TSan 能抓非原子的数据竞争，但抓不到"内存序不足"。**
> 而内存序错误**会真的产生撕裂数据**——本页有实测证据。

## 为什么音频开发必须懂这个

音频线程与其他线程通信靠**无锁结构**（见 [[SPSC 队列]]）。
无锁结构的正确性**完全依赖内存序**。
而内存序错误：
- 编译器不会报错
- 单元测试通常通过
- **TSan 也不报**（本页实测）
- 但**真的会出错**

---

## 一、实测：TSan 能抓什么（本库验证）

**测试**（Apple Silicon arm64，clang 21，`-fsanitize=thread -O1`）：

| 场景 | TSan 报告 |
|---|---|
| **① 非原子共享变量**（两个线程 `g_plain++`） | **2 条 data race** ✅ |
| **② relaxed 原子**（两个线程 `fetch_add`） | **0 条**（正确——原子不是 race） |
| **③ relaxed 索引 + 非原子 payload** | **0 条** ⚠️ |

> [!important] ①② 是**正确行为**
> - ① 非原子访问 → 确实是数据竞争 → 应该报
> - ② 原子操作 → **不是**数据竞争 → 不应该报（内存序再弱也是原子的）
>
> **TSan 抓的是"非原子访问"，不是"内存序不足"。**

---

## 二、⚠️ 场景 ③：TSan 沉默，但数据真的撕裂

**这是本页最重要的发现。**

**结构**（一种常见的"看起来对"的写法）：

```cpp
struct Msg { uint32_t a,b,c,d,e,f,g,h; };     // 32 字节，非单指令存储
std::atomic<uint64_t> g_w{0}, g_r{0};          // 索引用 relaxed
Msg g_buf[256];

// 生产者
auto w = g_w.load (std::memory_order_relaxed);
auto& m = g_buf[w & 255];
m.a = m.b = /* ... */ = (uint32_t) i;
g_w.store (w + 1, std::memory_order_relaxed);  // ⚠️ relaxed！
```

**实测结果**：

| 指标 | 数值 |
|---|---|
| **TSan 报告的 data race** | **0 条** |
| **实际撕裂次数**（200 万次，3 次运行） | **2708 / 4996 / 4672** |

> [!danger] 这就是最危险的情形
> **TSan 说"没问题"，但数据每次运行都撕裂几千次。**
>
> 如果你只依赖 TSan，你会认为代码是对的——
> 而用户那边会听到**偶发爆音**。

**为什么会撕裂**：
- 32 字节的 `Msg` 不是单指令存储 → 写入分多条指令
- `relaxed` 索引**不保证**"数据先于索引可见"
- 消费者可能看到"索引已更新，但数据只写了一半"

**修法**：索引用 `release`/`acquire`（见 [[SPSC 队列]]）。

---

## 三、内存序速查

| 内存序 | 保证 | 音频里用在哪 |
|---|---|---|
| `relaxed` | 只保证原子性，**无顺序保证** | ✅ **只读自己的索引** |
| `acquire` | 后续读不会重排到它前面 | ✅ **读对方的索引** |
| `release` | 之前的写不会重排到它后面 | ✅ **写自己的索引** |
| `acq_rel` | 兼有 | 读-改-写操作（如 `fetch_add`） |
| `seq_cst` | 全局单一顺序（最强） | 🟠 音频里通常不必要（更慢） |

> [!important] 配对规则（背下来）
> ```
> 生产者：写数据 → store(release) 索引
> 消费者：load(acquire) 索引 → 读数据
> ```
>
> **release 和 acquire 必须配对**，才能建立 happens-before 关系。

> [!tip] 什么时候 `relaxed` 够用
> **只有自己写的变量**（如"我只读我自己写的 writeIndex"）。
> 一旦这个原子量**保护其他数据**，就必须用 release/acquire。

## 四、怎么用 TSan

```bash
# 编译（⚠️ 用 -O1，不要 -O2）
clang++ -std=c++17 -O1 -g -fsanitize=thread mytest.cpp -o mytest_tsan

# 运行
./mytest_tsan
```

> [!warning] 三个注意事项
> | # | 注意 |
> |---|---|
> | 1 | **不能与 ASan 同时用**（两者不兼容，见 [[AddressSanitizer]]） |
> | 2 | 用 `-O1`（`-O2` 可能掩盖问题） |
> | 3 | **有竞争时 TSan 才报**——时序不对就不报，多跑几次 |

> [!danger] TSan 的检测是**概率性**的
> 它靠运行时插桩观察实际发生的访问。
> **没报 ≠ 没有竞争**——只是这次没触发。
>
> 所以：**TSan 通过只是必要条件，不是充分条件。**

## 五、正确的验证策略

> [!important] 三层组合，缺一不可

| 层 | 手段 | 抓什么 |
|---|---|---|
| 1 | **TSan** | 非原子数据竞争 |
| 2 | **压力测试**（多跑、多核、高负载） | 时序相关的撕裂 |
| 3 | **代码审查** | 内存序是否配对 ⭐ **唯一能抓内存序不足的** |

```cpp
// ⭐ 第 3 层：一个能自动检查内存序的断言
// 撕裂检测（本库实测有效）
bool ok = (m.a==m.b && m.b==m.c && m.c==m.d &&
           m.d==m.e && m.e==m.f && m.f==m.g && m.g==m.h);
if (!ok) ++tornCount;      // 撕裂计数 > 0 就是内存序不足
```

> [!tip] 这个"撕裂检测"是本库验证内存序的实用手段
> 把 payload 的所有字段写成同一个值，消费者检查是否全相等。
> **不等 = 撕裂 = 内存序不足。**
>
> 实测（2 万次内就能看出来）：200 万次里出现 **2708–4996 次**。

## 六、AI 会怎么写错

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **索引全用 relaxed** | 撕裂（实测每次几千次） | 检查 store/load 内存序 |
| 2 | **以为 TSan 通过就安全** | 漏掉内存序问题 | 见第二节 |
| 3 | **同时开 ASan 和 TSan** | 编译/运行失败 | 分开构建 |
| 4 | **用 `seq_cst` 到处** | 不必要地慢 | 按需选（多数场景 release/acquire 够） |
| 5 | **release/acquire 不配对** | 没有 happens-before | 检查两侧 |
| 6 | **用 `volatile` 代替 atomic** | ❌ 完全无效 | 用 `std::atomic` |
| 7 | **payload 是 `std::string`** | 拷贝时分配 | 用 POD |
| 8 | **以为"原子 = 线程安全"** | 忽略复合操作 | 原子只保证单次操作 |
| 9 | **只跑一次 TSan** | 概率性漏报 | 多次运行 |
| 10 | **用 `-O2` 配 TSan** | 可能掩盖问题 | 用 `-O1` |

> [!danger] 第 1、2 条是一对致命组合
> AI 写 relaxed 索引（看起来"用了原子所以安全"），
> 你用 TSan 验证（报告 0 竞争），
> **两者都指向"没问题"** —— 但实测每次运行撕裂几千次。
>
> **唯一能发现它的是**：显式检查 payload 的一致性。

## 七、常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| TSan 说没事但偶发爆音 | 内存序不足（TSan 抓不到） | 用 release/acquire |
| TSan 编译失败 | 与 ASan 同时开 | 分开构建 |
| TSan 报一堆竞争 | 真的有非原子共享 | 改用原子或加锁（非实时路径） |
| TSan 有时报有时不报 | 概率性检测 | 多跑几次 |
| 多核才出问题 | 时序相关 | 压力测试 |
| 单核测试通过 | 没有真并发 | 用多核机器测 |

---

## 八、怎么验证

**三个必做测试**：

| # | 测试 | 判据 |
|---|---|---|
| 1 | **TSan** | 无非原子竞争报告 |
| 2 | **撕裂检测** | payload 一致性检查，撕裂数 = 0 ⭐ |
| 3 | **压力**（多核 + 高负载） | 长时间运行无异常 |

```cpp
// ⭐ 撕裂检测（本库验证有效）
// 生产者：把 payload 所有字段写成同一个值
Msg m;
m.a = m.b = m.c = m.d = m.e = m.f = m.g = m.h = (uint32_t) i;
// 消费者：检查是否全部相等
if (!(m.a==m.b && m.b==m.c && m.c==m.d &&
      m.d==m.e && m.e==m.f && m.f==m.g && m.g==m.h))
    ++tornCount;      // > 0 → 内存序不足
```

> [!important] 为什么这个检测比 TSan 更有用
> TSan 报告 **0 条** race，而这个检测在**同样代码**上报告
> **2708–4996 次撕裂**（200 万次运行）。
>
> **它是唯一能自动发现"内存序不足"的实用手段。**
