# 参数自动化与线程安全

> [!important] 一句话
> **参数在 UI 线程被改、在音频线程被读。**
> 这是一个**跨线程数据竞争**——而 `std::mutex` 在这里是错的解法。

## 为什么不能用 mutex

> [!danger] 优先级反转（priority inversion）
> ```
> 音频线程（高优先级，硬实时）
>     ↓ 想拿锁
> UI 线程（低优先级）正持着锁，且被操作系统抢占
>     ↓
> 音频线程被迫等待 → 错过截止时间 → 爆音
> ```
>
> **音频线程必须无阻塞。** 见 [[实时音频线程契约]]。

> [!note] 那用什么？**`std::atomic` + 参数平滑**
> 参数值用原子变量传递（无锁），再用**平滑**消除跳变。
> 见 [[参数平滑 parameter smoothing]]。

---

## 一、实测：原子操作几乎不花钱（本库验证）

**测试**（Apple Silicon arm64，clang 21，`-O2`，5000 万次）：

| 操作 | 耗时 | 相对 |
|---|---|---|
| 普通 `float` 数组读 | **0.609 ns** | 1.00× |
| **`atomic<float>` relaxed load** | **0.727 ns** | **1.19×** |
| `atomic<float>` seq_cst load | 0.625 ns | 1.03× |

> [!important] 怎么读
> - 原子读约 **0.6–0.7 ns**
> - 48 kHz 每样本预算 = **20833 ns**
> - → 原子读占预算 **0.0035%**（可忽略）
>
> **结论：不要因为"性能"而不用原子。** 它比一次浮点乘加还便宜。

> [!warning] 但 `seq_cst` 的**写**和 `fetch_add` 会贵得多
> 本页测的是**单线程读**（无竞争）。
> 有竞争时（多个核心同时写同一缓存行）成本会显著上升——
> 那是**伪共享**问题，用 `alignas(64)` 解决（见 [[SPSC 队列]]，实测慢 7.5×）。
>
> ⚠️ 真实多核竞争下的成本**未在本机实测**。

## 二、正确的模式

### 模式 1：原子值 + 平滑（最常用）

```cpp
class GainProcessor
{
public:
    // ---- UI 线程调用 ----
    void setGain (float newGain) noexcept
    {
        targetGain.store (newGain, std::memory_order_relaxed);
    }

    void prepare (double sampleRate)
    {
        smoothed.reset (sampleRate, 0.02);        // 20ms 平滑
        smoothed.setCurrentAndTargetValue (
            targetGain.load (std::memory_order_relaxed));
    }

    // ---- 音频线程调用 ----
    float process (float x) noexcept
    {
        // 每采样或每块取一次目标值
        smoothed.setTargetValue (targetGain.load (std::memory_order_relaxed));
        return x * smoothed.getNextValue();
    }

private:
    std::atomic<float> targetGain { 0.5f };
    juce::SmoothedValue<float> smoothed;
};
```

> [!important] 三个要点
> | # | 要点 |
> |---|---|
> | 1 | **写用 `store`，读用 `load`**——不要在音频线程写 |
> | 2 | **`relaxed` 通常够用**（单个值，不需要与其他内存操作建立顺序） |
> | 3 | **必须平滑**——否则参数突变会产生 zipper noise |
>
> ⚠️ 什么时候需要 `acquire/release`：当原子量**保护其他数据**时
> （如"指针 + 它指向的数据"）。见 [[SPSC 队列]]。

### 模式 2：只在 block 边界更新（更省）

```cpp
void processBlock (juce::AudioBuffer<float>& buffer, juce::MidiBuffer&) override
{
    // ⭐ 每块只读一次，块内用局部变量
    const float g = targetGain.load (std::memory_order_relaxed);
    smoothed.setTargetValue (g);

    for (int i = 0; i < buffer.getNumSamples(); ++i)
        // 用 smoothed，不再碰原子量
        // ...
}
```

> [!tip] 为什么这更省
> 原子读本身很便宜，但**每采样读一次**会让编译器难以优化循环
> （它必须假设值可能变）。
>
> **每块读一次 → 块内用寄存器** → 优化器可以做向量化。

## 三、开关类参数：不要平滑

> [!danger] 布尔/枚举参数**不该平滑**
> | 参数类型 | 平滑吗 |
> |---|---|
> | 增益、频率、Q | ✅ **要** |
> | **旁路、算法选择、滤波器类型** | ❌ **不要** |
>
> **原因**：平滑一个开关会让它"拖泥带水"——
> 用户点"旁路"却发现声音慢慢变化。
>
> **正确做法**：开关用原子量直接读，然后**在切换点做交叉淡化**（crossfade）。

```cpp
// 开关：不平滑值，而是交叉淡化
std::atomic<bool> bypassed { false };
// ...
const bool byp = bypassed.load (std::memory_order_relaxed);
// 用 5-20ms 的 crossfade 在 wet/dry 之间过渡
```

见 [[旁路 bypass 的正确实现]]。

## 四、宿主自动化（Automation）

> [!important] 自动化 = 宿主在**音频线程**写参数
> 宿主按自动化曲线，每个 block（或更频繁）调用你的参数设置函数。
>
> **这意味着：`setValue` 可能从音频线程被调用！**

> [!danger] 所以参数设置必须是线程安全的
> | 你的实现 | 后果 |
> |---|---|
> | `setValue` 里加锁 | ❌ 音频线程可能死锁 |
> | `setValue` 里分配内存 | ❌ 违反实时契约 |
> | `setValue` 里只 `store` 原子量 | ✅ **正确** |
> | `setValue` 里做重活（如重建滤波器） | ❌ 音频线程被阻塞 |
>
> **规则：`setValue` 只写一个原子值，其他什么都不做。**
> 重活（重算系数）放到音频线程的 block 边界，或做平滑。

**JUCE 的处理方式**：

```cpp
// AudioProcessorValueTreeState 会处理大部分线程问题
// ⚠️ 但"参数变化 → 重算系数"仍要你自己保证实时安全
```

> [!warning] ⚠️ `AudioProcessorValueTreeState` 的细节需核实
> 它内部用了锁和 `ValueTree`（不是无锁的）。
> **不要在音频线程直接访问 `ValueTree`**——用它的原子缓存
> （如 `getRawParameterValue()`）。
>
> ⚠️ 具体 API 与线程保证需对照你的 JUCE 版本。

## 五、AI 会怎么写错

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **用 `std::mutex` 保护参数** | 优先级反转 → 爆音 | grep `mutex` |
| 2 | **参数不平滑** | zipper noise | 见 [[参数平滑 parameter smoothing]] |
| 3 | **平滑了开关参数** | 旁路切换"拖泥带水" | 开关用 crossfade |
| 4 | **音频线程写原子量** | 不必要，且可能造成竞争 | 只在 UI 线程写 |
| 5 | **`setValue` 里做重活** | 自动化时爆音 | 只写原子值 |
| 6 | **每采样读原子量** | 阻碍优化 | 每块读一次 |
| 7 | **用 `volatile` 代替 `atomic`** | ❌ 不是线程安全的 | 用 `std::atomic` |
| 8 | **以为原子量能保护其他数据** | 数据竞争 | 需要时用 acquire/release |
| 9 | **在音频线程访问 `ValueTree`** | 内部加锁 → 爆音 | 用 `getRawParameterValue` |
| 10 | **参数范围不钳制** | 用户/自动化能给极值 | `std::clamp` |

> [!danger] 第 1 条是最经典的错误
> AI 写"共享数据"时的第一反应就是加 `std::mutex`。
> 在音频线程里，**这会直接导致爆音**——而且**只在低性能机器/高负载时出现**，
> 你本地测不出来。
>
> **判据**：`processBlock` 调用链里 grep `mutex` / `lock`。

> [!danger] 第 7 条：`volatile` 不是线程安全
> ```cpp
> volatile float gain;        // ❌ 不保证原子性，不保证内存序
> std::atomic<float> gain;    // ✅
> ```
> `volatile` 只阻止编译器优化掉访问，**不提供任何同步保证**。

## 六、常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| 偶发爆音（高负载时） | mutex 优先级反转 | 用原子 |
| 参数变化有"滋滋"声 | 没平滑 | 加平滑 |
| 旁路切换有拖尾 | 平滑了开关 | 用 crossfade |
| 自动化时卡顿 | `setValue` 做重活 | 只写原子值 |
| CPU 占用比预期高 | 每采样读原子量 | 每块读一次 |
| 数据偶尔错乱 | 用 `volatile` | 用 `std::atomic` |
| 多核下更慢 | 伪共享 | `alignas(64)` |

## 七、怎么验证

**四个必做检查**：

| # | 检查 | 判据 |
|---|---|---|
| 1 | **音频线程无锁** | grep 不到 `mutex`/`lock` |
| 2 | **参数已平滑** | 快速拖动无 zipper noise |
| 3 | **自动化不爆音** | 宿主里画极端自动化曲线 |
| 4 | **无数据竞争** | TSan（⚠️ 注意局限） |

```bash
# ① 检查音频线程里的锁
grep -rn "mutex\|lock_guard\|scoped_lock\|critical_section" Source/
# 应只在非实时路径出现（如加载文件）

# ② 检查参数设置函数是否只写原子量
grep -n "setValue\|setParameter" -A 5 Source/PluginProcessor.cpp
```

> [!danger] ⚠️ TSan 在这里的局限（本库实测发现）
> **TSan 不会把 `relaxed` 原子索引报成 data race**——
> 原子操作本身不是 race。
>
> 它能抓**非原子访问**的竞争。
> 所以：**TSan 通过 ≠ 参数线程安全**。
>
> 见 [[SPSC 队列]]、[[ThreadSanitizer 与内存序]]。

**最有效的验证：在宿主里画极端自动化**

```
在 REAPER 里：
① 给参数画一条"方波"自动化（瞬间从 0 跳到 1）
② 播放，听是否有咔哒/zipper
③ 加大轨道数到 30+，看是否出现爆音
```

> [!important] 为什么这比单元测试有效
> 线程问题**只在真实调度下出现**。
> 宿主的高负载 + 自动化 = 最容易暴露问题的场景。
