# 浮点确定性与可复现性

> [!important] 一句话
> **同样的源码，不同的编译选项/平台，浮点结果可能不同。**
> 这不是 bug——是 IEEE 754 允许的自由度。**你要知道哪些自由度在影响你。**

## 为什么音频开发要关心

| 场景 | 需要确定性吗 |
|---|---|
| **回归测试**（bit-exact） | ✅ 需要 |
| 优化前 vs 优化后对比 | ✅ 需要 |
| **跨平台一致** | ❌ **做不到**（本页解释原因） |
| 用户听到的声音 | 🟠 微小差异听不出，但**不要依赖** |

见 [[Null Test 与 bit-exact 对比]]。

---

## 一、实测：结合律不成立（本库验证）

**测试**（10 万个 `1/(i+1)` 的求和，只改顺序）：

| 求和顺序 | 结果 |
|---|---|
| 正序 | `12.090146129863335` |
| 逆序 | `12.090146129863408` |
| **差异** | **7.283e-14**（相对 **6.024e-15**） |

> [!important] 浮点加法**不满足结合律**
> $$(a+b)+c \ne a+(b+c)$$
>
> **所以编译器可以自由重排**（在允许的范围内），
> 而不同的重排给出不同结果。
>
> **这就是为什么"并行化/向量化"会改变结果**——
> SIMD 把 4 个元素一起加，等于换了求和顺序。

---

## 二、实测：float vs double 累加

**测试**（100 万个 `1/(i+1)` 的累加）：

| 累加类型 | 结果 | 差异 |
|---|---|---|
| **float** | `14.35735798` | — |
| **double** | `14.392726788474306` | **3.537e-02** |

> [!danger] 差异达 **0.035**（相对误差约 0.25%）
> **长累加必须用 `double`**，即使输入是 `float`。
>
> 这是音频里很实际的一条：**滤波器内部状态、包络积分器**等
> 长时间累加的量应该用 `double`。

---

## 三、实测：唯一会改变结果的编译选项是 `-ffast-math`

**测试**（点积 `Σ a[i]*b[i]`，10 万项，`float` 输入 `double` 累加）：

| 编译选项 | 结果 |
|---|---|
| `-O0` | `0.99999001628019868` |
| `-O1` | `0.99999001628019868` |
| `-O2` | `0.99999001628019868` |
| `-O3` | `0.99999001628019868` |
| `-O2 -ffp-contract=off` | `0.99999001628019868` |
| **`-O2 -ffast-math`** | **`0.99999001628020801`** ⚠️ |
| `-O2 -march=native` | `0.99999001628019868` |

> [!important] 怎么读
> - **`-O0` 到 `-O3` 结果完全一致**（本机 clang 21 / arm64）
> - **`-ffp-contract=off` 没有改变结果**（这个测试里没有 FMA 机会）
> - **`-ffast-math` 改变了结果** ⚠️
>
> **`-ffast-math` 是最危险的选项。**

> [!danger] `-ffast-math` 放弃了 IEEE 语义
> 它启用一系列激进的假设，包括：
> - 假定没有 NaN / Inf
> - 假定结合律成立（可自由重排）
> - 假定没有符号零
>
> **对音频代码是灾难**：
> - NaN 检测失效（见 [[浮点音频表示]]）
> - denormal 处理被改变
> - 结果不可复现
>
> **绝对不要在音频插件里用 `-ffast-math`。**

> [!note] ⚠️ 本机实测的局限
> - 只有 **arm64**（Apple Silicon），x86-64 的 FMA 行为可能不同
> - `-ffp-contract=off` 在这个测试里没体现差异，
>   **不代表它在别的代码里也没影响**
> - 结论是"在这台机器 + 这段代码上"的观察

## 四、实测：位模式的坑

**测试**（`+0.0f` vs `-0.0f`，NaN）：

| 检查 | 结果 |
|---|---|
| `+0.0f` 位模式 | `0x00000000` |
| `-0.0f` 位模式 | `0x80000000` |
| **`+0.0f == -0.0f`** | **`true`** |
| **`memcmp(+0.0f, -0.0f)`** | **`false`** ⚠️ |
| **`NaN == NaN`** | **`false`** ⚠️ |

> [!danger] 两条必须记住的
> 1. **`-0.0 == 0.0` 为 true，但位模式不同** → bit-exact 比较会判为不同
> 2. **`NaN != NaN`** → 用 `==` 比较 NaN 会失败
>
> **所以 bit-exact 比较必须用 `memcmp`，不能用 `==`。**
>
> 见 [[Null Test 与 bit-exact 对比]]。

## 五、跨平台为什么做不到 bit-exact

| 原因 | 说明 |
|---|---|
| **FMA 指令** | x86/ARM 的融合乘加与"先乘后加"结果不同 |
| **x87 80 位中间精度**（旧 x86） | 中间结果精度更高 |
| **编译器优化重排** | 浮点不满足结合律，但优化器可以按"允许"的规则重排 |
| **`-ffast-math`** | 完全放弃 IEEE 语义 |
| **denormal 处理**（FTZ/DAZ） | 不同 CPU 模式不同 |
| **向量化顺序** | SIMD 归约的求和顺序不同 |
| **数学库实现** | `sin`/`exp` 在不同平台有微小差异 |

> [!important] 结论
> **不要跨平台要求 bit-exact。**
> 应该要求 **null test < -100 dB**。
>
> | 对比对象 | 判据 |
> |---|---|
> | 同平台，优化前 vs 优化后 | **bit-exact** ✅ 可行 |
> | 同平台，不同编译选项 | 通常 bit-exact（除 `-ffast-math`） |
> | **macOS vs Windows** | **< -100 dB**（不要要求 bit-exact） |

## 六、怎么最大化可复现性

> [!tip] 实用清单

| # | 做法 | 效果 |
|---|---|---|
| 1 | **禁用 `-ffast-math`** | ⭐ 最重要 |
| 2 | 用 `-ffp-contract=off` | 禁用 FMA 融合（如需跨平台一致） |
| 3 | 避免 `-march=native` | 不同 CPU 指令集不同 |
| 4 | 固定编译器**版本** | 不同版本优化策略不同 |
| 5 | **长累加用 `double`** | 减少误差累积 |
| 6 | 固定**求和顺序** | 不要依赖编译器重排 |
| 7 | 记录编译选项到构建产物 | 出问题能复现 |
| 8 | 用 `-fno-fast-math` 显式声明 | 防止上游 CMake 偷偷开启 |

> [!warning] CMake 里的陷阱
> 有些第三方 CMake 配置会**默认加 `-ffast-math`**（为了性能）。
> 它会通过 `INTERFACE` 传播到你的 target。
>
> **检查方法**：
> ```bash
> cmake --build build --verbose 2>&1 | grep -i "fast-math"
> ```
> 见 [[CMake 基础]]。

## 七、AI 会怎么写错

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **建议用 `-ffast-math` 提速** | ❌ 音频代码不能用 | grep 编译选项 |
| 2 | **跨平台要求 bit-exact** | 永远失败 | 改成 < -100 dB |
| 3 | **用 `==` 做 bit-exact 比较** | NaN/-0.0 判定错 | 用 `memcmp` |
| 4 | **用 `float` 做长累加** | 误差 0.035（实测） | 用 `double` |
| 5 | **以为 `-O3` 会改变结果** | 本机实测不会 | 实测确认 |
| 6 | **忽略 FMA 的跨平台差异** | macOS/Windows 不一致 | `-ffp-contract=off` |
| 7 | **用 `-march=native` 做发布构建** | 换 CPU 就崩/变结果 | 用基线指令集 |
| 8 | **不记录编译选项** | 无法复现 | 写进构建产物 |

> [!danger] 第 1 条是本页最实用的警告
> AI 看到"性能优化"就会推荐 `-ffast-math`——
> 在通用数值代码里它可能没问题，
> **在音频插件里它会破坏 NaN 检测和可复现性**。
>
> **判据**：`grep -r "fast-math" CMakeLists.txt cmake/`

## 八、常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| 优化后结果变了 | 用了 `-ffast-math` | 去掉它 |
| 跨平台结果不同 | FMA / 数学库差异 | 接受 < -100 dB |
| 长累加误差大 | 用了 `float` | 用 `double` |
| bit-exact 比较失败 | 用了 `==` | 用 `memcmp` |
| 并行化后结果变 | 求和顺序变了 | 固定顺序 |
| 换 CPU 后行为变 | `-march=native` | 用基线指令集 |
| 无法复现 bug | 没记录编译选项 | 记录下来 |

## 九、怎么验证

**三个必做测试**：

| # | 测试 | 判据 |
|---|---|---|
| 1 | **不同优化等级** | 结果应一致（除 `-ffast-math`） |
| 2 | **长累加精度** | `float` vs `double` 的差异 |
| 3 | **位模式比较** | 用 `memcmp` 而非 `==` |

```bash
# ① 检查编译选项里有没有 -ffast-math
grep -rn "fast-math" CMakeLists.txt cmake/ 2>/dev/null || echo "✅ 没有 -ffast-math"

# ② 对比不同优化等级的结果（应完全一致）
for opt in "-O0" "-O1" "-O2" "-O3"; do
    clang++ -std=c++17 $opt mydsp.cpp -o /tmp/t 2>/dev/null && \
        printf "  %-6s " "$opt" && /tmp/t | head -1
done
# 期望：四行完全相同

# ③ 检查 bit-exact 比较是否用了 memcmp
grep -rn "bit_exact\|bitexact" Source/ | head
```

> [!important] 第 ② 条是最实用的自检
> **如果 `-O0` 和 `-O3` 结果不同**，说明你的代码里有
> 依赖未定义行为或浮点自由度的地方——值得查一查。
