# AI 生成代码的审查清单

> [!important] 这一页怎么用
> 让 AI 写完代码后，**不要直接跑**。按下面的清单过一遍。
> 每条都给出「**查什么**」和「**怎么查**」——后者是 grep 命令或测试方法。
>
> 这些不是凭空想的：**121 条错误模式是从本库 15 个页面的「AI 会怎么写错」表归纳出来的**。

## 为什么需要清单

AI 写音频代码有一个特定的危险模式：

```
能编译 ✅   能出声 ✅   常见参数下听起来对 ✅
极端参数下爆音 / 失真 / 发散 ❌
```

**它不会告诉你这一点**，因为它不知道。
而音频 bug 的特点是：**90% 的情况下听起来"差不多"，只在极端条件下暴露**。

---

## 一、实时安全（最高优先级）

> [!danger] 这一类违反会导致爆音，而且**只在用户机器上复现**
> 你的 M2 跑 3 个轨道没问题，用户的老机器跑 40 个轨道就炸。

| # | 查什么 | 怎么查 |
|---|---|---|
| 1 | **音频线程里的内存分配** | grep `new`、`delete`、`malloc`、`push_back`、`resize`、`reserve`、`std::string` 在 `processBlock` 调用链里 |
| 2 | **加锁** | grep `mutex`、`lock_guard`、`scoped_lock`、`critical_section` |
| 3 | **文件 / 网络 IO** | grep `fopen`、`ifstream`、`printf`、`std::cout`、`DBG` |
| 4 | **构造函数里做重活** | 看构造函数是否分配大缓冲、读文件、建 FFT |
| 5 | **`prepareToPlay` 不幂等** | 检查是否有 `resize` 无上限增长、状态没重置 |
| 6 | **0 长度 block** | 检查 `processBlock` 开头是否处理 `numSamples == 0` |
| 7 | **假设固定 block size / 声道数** | grep 硬编码的 `512`、`2`（声道）；只用传入的 `numSamples` |
| 8 | **denormal 未处理** | 看反馈路径有没有偏置或 FTZ，见 [[denormal 数处理]] |

**一键检查**（本库已实现）：

```bash
bash 50-Playground/tools/check_crossplatform.sh Source/     # 跨平台部分
# 实时安全用这个 C++ 工具：
# 50-Playground/tools/cpp/audio_thread_alloc_detector.cpp
```

**最有效的自动化**：重载全局 `operator new`，在音频线程里调用时直接断言。
见 [[插件验证工具]] 第六节（已验证能抓到）。

## 二、参数边界

> [!warning] 这一类会导致**用户能调出爆炸声**
> 你在测试时只会用"正常"参数，用户会拧到极限。

| # | 查什么 | 怎么查 |
|---|---|---|
| 9 | **滤波器频率未钳制** | 检查 `f0 < fs*0.45`（接近 Nyquist 时公式失效） |
| 10 | **Q 值无上限** | 检查 `Q` 有 clamp（高 Q 会导致 ringing 甚至失稳） |
| 11 | **反馈增益未钳制** | 检查 `feedback < 0.999`（浮点误差会累积） |
| 12 | **增益 / 输出未钳制** | 检查最终输出有 `clamp(-1, 1)` 或 limiter |
| 13 | **参数变化未平滑** | 见 [[参数平滑 parameter smoothing]]（zipper noise） |
| 14 | **枚举 / 开关被"平滑"** | 开关**不该**平滑（会变得拖泥带水） |

**测试方法**：写一个脚本，把所有参数扫到极值，看输出是否 NaN/Inf/发散。

## 三、数值稳定性

| # | 查什么 | 怎么查 |
|---|---|---|
| 15 | **NaN / Inf 未检测** | grep `isfinite`；在 `processBlock` 末尾加检查 |
| 16 | **反馈回路可能发散** | 喂脉冲跑 10 秒，看是否衰减到 0 |
| 17 | **`float` 用于长累加** | 滤波器内部状态、长时间累加用 `double` |
| 18 | **符号约定混用** | 差分方程的 `a1/a2` 正负号（不同教材不同） |
| 19 | **dB 公式用错** | `20*log10`（幅度）vs `10*log10`（功率）；峰值 EQ 的 `A = 10^(dB/40)` 不是 `/20` |
| 20 | **归一化约定混用** | `int16` 除以 32767 还是 32768；FFT 是否除以 N |

**测试方法**：和**解析解**逐点对照。本库的 `audio_io.check_response()` 能做到 0.0021 dB 的精度。

## 四、生命周期

| # | 查什么 | 怎么查 |
|---|---|---|
| 21 | **系数算在构造函数里** | 采样率还没确定 → 必须在 `prepareToPlay` |
| 22 | **延迟线长度写死样本数** | 应按**秒**定义，在 prepare 里乘采样率 |
| 23 | **`prepareToPlay` 反复调用** | 宿主会调多次（改采样率/缓冲区），必须幂等 |
| 24 | **状态保存漏参数** | 对比参数列表和 `getStateInformation` |
| 25 | **状态版本号没升** | 旧工程打开新插件要能工作 |
| 26 | **延迟未报告** | grep `setLatencySamples`（过采样、lookahead 都需要） |
| 27 | **旁路时仍处理** | 见 [[旁路 bypass 的正确实现]] |

## 五、跨平台

> [!note] 你**必须**兼容 Windows（见 [[跨平台开发 macOS 与 Windows]]）

| # | 查什么 | 怎么查 |
|---|---|---|
| 28 | **`#include` 大小写不符** | macOS 不敏感、Windows 敏感 → **本地永远发现不了** |
| 29 | **用了 `long`** | Windows 上是 4 字节 → 改用 `int32_t`/`int64_t` |
| 30 | **`M_PI`** | MSVC 默认不定义 → 自己定义常量 |
| 31 | **手拼路径** | 用 `juce::File` 或 `std::filesystem::path` |
| 32 | **平台 API 散落** | grep `_WIN32`、`__APPLE__`、`windows.h` |

**一键检查**（本库已实现）：

```bash
bash 50-Playground/tools/check_crossplatform.sh Source/
```

它检查 6 类问题，包括**只差大小写的重名文件**（macOS 磁盘上创建不出来，但 git 能跟踪）。

## 六、DSP 正确性

| # | 查什么 | 怎么查 |
|---|---|---|
| 33 | **非线性处理没过采样** | 见 [[过采样 oversampling]]（混叠） |
| 34 | **插值用了线性但场景需要全通** | 高频衰减，见 [[插值]] |
| 35 | **延迟时间被直接平滑** | 会产生多普勒变调（除非那是想要的） |
| 36 | **立体声左右共用状态** | 会产生串音 → 每声道独立实例 |
| 37 | **混响延迟成整数比** | 会产生强共振（实测 77 个峰 vs 互质 6 个） |
| 38 | **全通实现写错** | 缓冲区应存 `x + g*y`（用输出），不是 `x + g*bufOut` |
| 39 | **窗函数对称 / 周期性混用** | OLA 要用周期性版本 |
| 40 | **反馈路径没阻尼** | 混响尾巴会太亮、不自然 |

## 七、把清单变成自动化

> [!tip] 别指望每次人工过 40 条
> 前 6 条（实时安全）和前 5 条（参数边界）最容易自动化。

### 立即可用的三道防线

| 防线 | 工具 | 抓什么 |
|---|---|---|
| 1 | **重载 `operator new`** | 音频线程里的分配（头号违规） |
| 2 | **`check_crossplatform.sh`** | 大小写、类型宽度、平台 API |
| 3 | **`audio_io.check_response()`** | DSP 是否和解析解一致 |

### 让 AI 自查的提示词

```
检查这个 processBlock 实现：
1. 有没有内存分配、加锁、文件 IO？（包括间接调用的）
2. 如果 numSamples == 0 会怎样？
3. 如果声道数从 2 变成 1 会怎样？
4. 所有参数都钳制了吗？极值下会怎样？
5. 反馈路径会发散吗？
6. 采样率变化时哪些状态需要重算？
```

> [!warning] 但必须核对 AI 的回答
> AI 经常会说"没问题"而实际有问题。
> **它的自查只能当"提醒你想到了什么"，不能当验证。**

## 八、AI 会怎么写错（元层面）

| # | 元错误 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **声称"已处理"但实际没处理** | 你以为安全了 | **永远自己验证**，不要信声明 |
| 2 | **给过时的 API** | 编译失败或行为不对 | 对照你锁定的版本文档 |
| 3 | **在注释里写"这里不会分配"** 但代码分配了 | 注释骗人 | 看代码，不看注释 |
| 4 | **测试脚本本身有 bug** | 你以为是实现错了 | 用**已知答案**校准测试脚本 |
| 5 | **改 A 弄坏 B** | 回归 | 每次改完跑全套测试 |
| 6 | **过度自信地编造 API** | 浪费时间 | 编译验证 |

---

## 九、怎么验证这份清单本身有效

| 测试 | 方法 |
|---|---|
| **清单能抓到已知错误** | 故意写一段违规代码，看能否发现 |
| **清单不过度报警** | 对干净代码不应报错 |
| **覆盖率** | 本库 121 条错误模式，看有多少被清单覆盖 |

```bash
# 用本库的历史 bug 回归测试清单
# 已知案例：
#   1. 全通缓冲区写错（x+g*bufOut）→ 检查第 38 条
#   2. 频谱幅度差 6dB（没补偿窗增益）→ 检查第 20 条
#   3. 文件名大小写 → 检查第 28 条
```
