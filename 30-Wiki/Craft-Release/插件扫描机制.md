# 插件扫描机制

> [!important] 一句话
> **宿主靠"扫描"发现插件**：遍历固定目录 → 加载二进制 → 询问元数据。
> 你的插件在扫描时**崩溃或超时**，就会"不出现"——而且用户不会知道为什么。

## 为什么这一页重要

"插件装了但宿主里找不到"是最常见的问题。
**大部分原因在扫描阶段**，而不是你的 DSP 代码。

| 症状 | 可能原因 |
|---|---|
| 完全找不到插件 | 目录不对 / 扫描崩溃 |
| 第一次扫描后不见了 | 扫描时崩溃，被宿主**拉黑** |
| 宿主启动变慢 | 你的插件在扫描时做重活 |
| 改了代码但行为没变 | 宿主用了缓存 |

---

## 一、扫描流程（以 VST3 为例）

```
① 遍历插件目录         /Library/Audio/Plug-Ins/VST3/ 等
② 对每个 .vst3 目录     加载二进制（dlopen / LoadLibrary）
③ 调用元数据接口        GetPluginFactory() → 插件名、参数、IO 配置
④ 缓存结果              下次启动直接读缓存
⑤ 实例化（可能延迟）    真正创建 processor/editor
```

> [!danger] 步骤 ③ 会**构造**你的插件类
> 这就是为什么**构造函数不能做重活**：
> - 读文件（IR、采样、预设）
> - 分配大缓冲区
> - 建 FFT 对象
> - 网络请求
>
> **宿主扫描时只想要元数据，不想要你的初始化。**

## 二、macOS 上的目录（本机实测）

| 格式 | 系统级 | 用户级 | 本机状态 |
|---|---|---|---|
| **AU** | `/Library/Audio/Plug-Ins/Components/` | `~/Library/...` | ✅ 存在 |
| **VST3** | `/Library/Audio/Plug-Ins/VST3/` | `~/Library/...` | ❌ **不存在** |
| **VST2** | `/Library/Audio/Plug-Ins/VST/` | `~/Library/...` | ✅ 存在 |
| CLAP | `/Library/Audio/Plug-Ins/CLAP/` | `~/Library/...` | ❌ 不存在 |

> [!note] VST3 目录不存在是正常的（本机实测）
> macOS **不会预建** VST3 目录——它由第一个安装 VST3 插件的程序创建。
> 你还没装任何 VST3 宿主，所以目录不存在。
>
> **这本身是个提示**：安装包应该**自己创建目录**，而不是假设它存在。
>
> 见 [[插件安装路径规范]]。

## 三、AU 的注册机制（实测）

AU 比 VST3 多一层：**系统注册表**。

```bash
auval -l        # 列出所有 AU 及位置（不实例化，快）
```

**实测输出**（本机）：

```
aufx bpas appl  -  Apple: AUBandpass
   (file:///System/Library/Components/CoreAudio.component/) [AUv2]
aufx dcmp appl  -  Apple: AUDynamicsProcessor
   (file:///System/Library/Components/CoreAudio.component/) [AUv2]
aufx dely appl  -  Apple: AUDelay
   ...
```

> [!important] 输出格式说明
> `aufx bpas appl` 就是 **TYPE SUBT MANU** 三个四字符代码。
> 括号里是**实际文件路径**——这是排查"装到哪了"的最快方法。
>
> `auval -l` **不实例化**（快且安全），`auval -a` 会实例化（慢，可能挂起）。
> 见 [[auval 与 AU 验证]]。

**AU 的注册流程**：

```
① 放入 Components/ 目录
② 系统扫描（AudioComponentRegistrar 进程）
③ 写入注册缓存
④ 宿主从注册表读取
```

> [!warning] AU 缓存是"改了没生效"的头号原因
> 你重新构建了 AU，但宿主仍用旧版。
>
> **排查顺序**：
> 1. `auval -l | grep 你的插件`——先确认**系统注册表**里是什么
> 2. 重启宿主
> 3. 删除插件后重新添加，强制重扫
> 4. 严重时清系统 AU 缓存并重启

## 四、宿主怎么决定"扫不扫"

| 宿主 | 行为 |
|---|---|
| **REAPER** | ✅ 有详细扫描日志，能看每个插件的加载结果；崩溃的会被隔离 |
| **Ableton Live** | 有"Rescan"按钮；偏好里可指定额外 VST 路径 |
| Logic | 用 AU 注册表；`auval` 能提前发现问题 |
| 大多数宿主 | 首次扫描慢，之后用缓存 |

> [!tip] REAPER 是最适合排查的宿主
> 它的日志会告诉你：
> - 扫了哪些路径
> - 哪个插件失败、为什么
> - 崩溃的插件会被**加入黑名单**（避免每次启动都崩）
>
> 对插件开发者来说这是很大的优势。见 [[插件验证工具]]。

## 五、扫描期间的禁忌

> [!danger] 扫描时做的事 = 用户每次启动宿主都要等的事

| 禁忌 | 后果 |
|---|---|
| **构造函数读文件** | 扫描变慢，可能超时 |
| **构造函数分配大内存** | 内存峰值 |
| **扫描时弹 UI** | 有些宿主会当作异常 |
| **扫描时崩溃** | 被拉黑 |
| **扫描时联网** | 无网络时卡住 |
| **静态初始化做重活** | 在 `main` 之前就跑，更难排查 |

**正确做法**：

```cpp
class MyProcessor : public juce::AudioProcessor
{
public:
    MyProcessor()
        : AudioProcessor (BusesProperties()...)   // ⚠️ 只做轻量初始化
    {
        // ✅ 只做参数创建等必须的事
        addParameter (gainParam = new juce::AudioParameterFloat (...));
        // ❌ 不要：loadImpulseResponse()、分配大缓冲、建 FFT、读文件
    }

    void prepareToPlay (double sampleRate, int samplesPerBlock) override
    {
        // ✅ 重活都在这里（宿主明确要求准备播放时）
        convolution.prepare ({ sampleRate, (juce::uint32) samplesPerBlock, 2 });
        fft = std::make_unique<juce::dsp::FFT> (11);
        // ...
    }
};
```

> [!important] 一个实用的判据
> **问自己：这个操作在"只想要元数据"时是必要的吗？**
> 不是 → 移到 `prepareToPlay`。

## 六、缓存带来的开发困扰

> [!warning] "我改了代码但行为没变"
> 可能原因（按概率排序）：
> 1. **没重新构建**（或构建失败但你没看）
> 2. **构建产物没复制到插件目录**（`COPY_PLUGIN_AFTER_BUILD` 没开）
> 3. **宿主缓存**（用了旧的插件信息）
> 4. **AU 注册缓存**
> 5. 宿主加载的是**另一个位置**的同名插件（系统级 vs 用户级）

```bash
# 快速排查：确认插件目录里的文件时间戳
ls -la /Library/Audio/Plug-Ins/VST3/MyPlugin.vst3/Contents/MacOS/
ls -la ~/Library/Audio/Plug-Ins/VST3/MyPlugin.vst3/Contents/MacOS/
# ⚠️ 两个位置都可能存在——宿主加载哪个取决于它的搜索顺序
```

> [!tip] 开发时的建议
> 1. 开启 `COPY_PLUGIN_AFTER_BUILD`
> 2. 只往**一个位置**装（避免两个同名版本）
> 3. 改完在宿主里"重新扫描"而不是重启

## 七、AI 会怎么写错

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **构造函数里读 IR / 建 FFT** | 扫描超时 | 移到 prepareToPlay |
| 2 | **构造函数里分配大缓冲** | 内存峰值 | 同上 |
| 3 | **假设 VST3 目录已存在** | 安装失败 | 安装时创建目录 |
| 4 | **不处理"扫描时无音频设备"** | 崩溃 | 构造函数不做设备相关的事 |
| 5 | **在静态初始化阶段做重活** | 加载即慢 | 用懒初始化 |
| 6 | **以为"装了就能看到"** | 不排查扫描问题 | 看宿主日志 |
| 7 | **扫描时弹 UI** | 宿主异常 | 不要在构造时创建编辑器 |
| 8 | **不提供元数据就返回** | 宿主看不到插件 | 检查 `getPluginFactory` |
| 9 | **同名插件装两个位置** | 加载了旧的那个 | 只装一个位置 |

> [!danger] 第 1 条是最常见的"插件开发新手坑"
> 你的插件在你机器上"能用"（因为文件都在），
> 但在用户机器上扫描超时 → **插件根本不出现**。
>
> 而且症状是"没出现"，不是"崩溃"——**很难联想到构造函数**。

## 八、常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| 宿主里找不到 | 装错目录 | 见 [[插件安装路径规范]] |
| 首次能用，重启后消失 | 扫描时崩溃被拉黑 | 看宿主日志，检查构造函数 |
| 宿主启动变慢 | 扫描时做重活 | 移到 prepareToPlay |
| 改了代码没变化 | 缓存 / 装了两个位置 | 重新扫描，检查两个目录 |
| AU 不出现 | Info.plist 的 AudioComponents 不对 | 对照 JUCE 模板 |
| 只有某些宿主能找到 | 格式没启用 / 架构不匹配 | 检查宿主设置与架构 |
| 扫描时弹窗 | 构造函数创建了编辑器 | 移到 `createEditor` |

## 九、怎么验证

```bash
#!/bin/bash
# 插件可见性排查（本机实测可用）

echo "=== ① 检查所有可能的安装位置 ==="
for dir in /Library/Audio/Plug-Ins/VST3 \
           ~/Library/Audio/Plug-Ins/VST3 \
           /Library/Audio/Plug-Ins/Components \
           ~/Library/Audio/Plug-Ins/Components; do
    echo "--- $dir ---"
    if [ -d "$dir" ]; then
        ls -la "$dir" 2>/dev/null | grep -i "yourplugin" || echo "  （无你的插件）"
    else
        echo "  （目录不存在）"
    fi
done

echo ""
echo "=== ② AU 是否注册到系统 ==="
auval -l 2>/dev/null | grep -i "yourplugin" || echo "  ❌ AU 未注册"

echo ""
echo "=== ③ 签名与 Gatekeeper（macOS 会拦截未签名插件）==="
PLUGIN="/Library/Audio/Plug-Ins/VST3/MyPlugin.vst3"
if [ -e "$PLUGIN" ]; then
    codesign -v --verbose=2 "$PLUGIN" 2>&1
    spctl -a -vv "$PLUGIN" 2>&1
fi
```

**AU 专用验证**：

```bash
# 列出所有 AU 及位置（不实例化，安全快速）
auval -l

# 只列效果器
auval -s aufx

# 验证指定的 AU（会实例化）
auval -strict -v aufx YourSubt YourManu
```
