# 立体声感知

> [!important] 一句话
> 人耳判断"声音在左边还是右边"靠**两种机制**：到达时间差（ITD）和强度差（ILD）。
> **任何"加宽"处理都在操纵这两者之一，而代价是单声道兼容性。**

## 为什么做插件必须懂这个

| 场景 | 你必须知道 |
|---|---|
| 做 **chorus / flanger** | 左右延迟差会产生相位抵消 |
| 做 **混响** | 左右去相关决定宽度，也决定 mono 兼容性 |
| 做 **立体声增强器** | 这整页就是它的设计依据 |
| 做**任何**插件 | 用户可能在 mono 系统上听、可能被 mono 化 |

> [!warning] 单声道兼容性是发布前的必检项
> DJ 系统、俱乐部低音炮、手机扬声器、某些流媒体——**都可能是单声道**。
> 如果你的插件在 mono 下某些频率消失，用户会觉得"这个插件有毛病"。

## 一、人耳如何定位声音

| 机制 | 全称 | 有效范围 | 说明 |
|---|---|---|---|
| **ITD** | Interaural Time Difference（双耳时间差） | **低频**（< 1.5kHz） | 声音到达两耳的时间差，最大约 0.6ms |
| **ILD** | Interaural Level Difference（双耳强度差） | **高频**（> 1.5kHz） | 头部的声影效应，高频被遮挡 |
| **HRTF** | Head-Related Transfer Function | 全频段 | 耳廓、头形的滤波效应，也提供**前后/上下**信息 |

> [!note] 为什么分频段
> 低频波长长，能绕过头部 → **强度差不明显，靠时间差**。
> 高频波长短，被头部遮挡 → **时间差模糊（相位歧义），靠强度差**。
>
> 这解释了为什么"低频加宽"和"高频加宽"要用**不同**的技术。

## 二、M/S 编码：立体声处理的坐标系

**Mid/Side** 是立体声处理的**自然坐标系**：

$$M = \frac{L + R}{2}, \qquad S = \frac{L - R}{2}$$

反变换：

$$L = M + S, \qquad R = M - S$$

> [!important] 为什么 M/S 比 L/R 好用
> | 操作 | L/R 坐标系 | M/S 坐标系 |
> |---|---|---|
> | 调"宽度" | 要同时改两个值 | **只改 S 的增益** |
> | 调"位置" | 复杂 | 改 M/S 的比例 |
> | 检查 mono 兼容 | 要相加 | **直接看 M**（mono 就等于 M） |
>
> **关键洞察**：**mono 化 = 丢掉 S，只保留 M。**
> 所以：**任何只作用于 S 的处理，都不影响 mono 兼容性。**

## 三、⚠️ 加宽方法的代价（**本页核心**）

**实测对比**（48kHz，相同输入信号）：

| 方法 | 单声道损失 | 说明 |
|---|---|---|
| 左右完全相同 | **0.00 dB** | 无宽度，mono 完美 |
| **侧链（M/S）增强 ×2** | **0.00 dB** | ✅ **mono 完全不受影响** |
| Haas 延迟 1–20ms | -3.0 dB（宽带） | ⚠️ 见下 |
| 失谐 3Hz | -3.0 dB（宽带） | ⚠️ 见下 |
| 左右极性反转 | -200 dB | ❌ mono 完全消失 |

> [!tip] 上表的 -3 dB 是**误导性的平均值**
> 用白噪声测，时间差/失谐造成的损失看起来是恒定的 -3 dB。
> **但对有音高的素材，损失是频率相关的**——这才是真正的危险。

### 时间差造成的梳状滤波（真正的危险）

**实测**：左右相差 $d$ 秒的同一正弦，mono 相加后的损失：

| 频率 | d=0.5ms | d=1ms | d=2ms | d=5ms |
|---|---|---|---|---|
| 50 Hz | -0.0 | -0.1 | -0.4 | -3.0 |
| 100 Hz | -0.1 | -0.4 | -1.8 | **-200** ⚠️ |
| 200 Hz | -0.4 | -1.8 | **-10.2** | 0.0 |
| 400 Hz | -1.8 | **-10.2** | -1.8 | 0.0 |
| 800 Hz | **-10.2** | -1.8 | -10.2 | 0.0 |
| 1600 Hz | -1.8 | **-10.2** | -1.8 | 0.0 |

> [!danger] 第一个零点：$f_0 = \dfrac{1}{2d}$
>
> **实测验证**（损失 -200 dB = 完全抵消）：
>
> | 延迟 d | 理论零点 $1/(2d)$ | 实测 |
> |---|---|---|
> | 0.5 ms | 1000 Hz | **-200 dB** ✅ |
> | 1 ms | 500 Hz | **-200 dB** ✅ |
> | 2 ms | 250 Hz | **-200 dB** ✅ |
> | 5 ms | 100 Hz | **-200 dB** ✅ |
>
> **这意味着**：用 Haas 效应加宽时，**某些频率会在 mono 下完全消失**。
> 而且零点位置取决于延迟量——**你调宽度旋钮时，消失的频率在移动**。

> [!warning] 失谐（detune）有同样的问题
> 两个略微失谐的信号，相位差**随时间周期变化** →
> 抵消的频率**周期性移动** → 听起来像"飘忽的梳状滤波"。
>
> 这是很多"立体声增强"插件在 mono 下听起来很糟的原因。

## 四、加宽方法的选择

| 方法 | 宽度感 | mono 兼容 | 适合 |
|---|---|---|---|
| **M/S 侧链增益** | 中 | ✅ **完美** | **首选** |
| **互补 EQ**（左右不同频段） | 中 | 🟠 尚可 | 温和加宽 |
| **Haas 延迟**（< 30ms） | 强 | ❌ 梳状抵消 | 特殊效果，慎用 |
| **失谐 / chorus** | 强 | ❌ 梳状抵消 | 创意效果 |
| **立体声混响** | 强 | 🟠 取决于设计 | 空间感 |
| **极性反转** | 极强 | ❌❌ 消失 | 不要用 |

> [!tip] 实践建议
> 1. **优先用 M/S**——它是唯一"免费"的宽度
> 2. 用时间差/失谐时，**降低侧链的高频内容**（高通 S 信号），
>    因为抵消主要发生在中低频
> 3. **发布前一定在 mono 下试听**（宿主里都有 mono 按钮）

## 五、在插件里怎么实现

### 立体声宽度控制

```cpp
// width: 0 = mono, 1 = 原始, 2 = 加宽一倍
void setWidth (float width)
{
    // M/S 编码 → 缩放 S → 解码
    const float M = (L + R) * 0.5f;
    const float S = (L - R) * 0.5f * width;
    L = M + S;
    R = M - S;
}
```

> [!warning] width > 1 会放大 S，可能超出范围
> 加宽后 L/R 可能超过 ±1。要么钳制（会失真），要么降低总增益。
> 专业插件通常做**自动增益补偿**。

### 检查 mono 兼容性（内置）

```cpp
// 在插件里加一个 mono 检查按钮
if (monoCheck)
{
    const float m = (L + R) * 0.5f;
    L = R = m;
}
```

### 相关度表（correlation meter）

很多插件会显示"相位相关度"：

```
+1 = 完全相关（mono）
 0 = 完全不相关（最宽）
-1 = 反相（mono 消失）
```

```cpp
float correlation (const float* L, const float* R, int n)
{
    float sumLR = 0, sumLL = 0, sumRR = 0;
    for (int i = 0; i < n; ++i)
    {
        sumLR += L[i] * R[i];
        sumLL += L[i] * L[i];
        sumRR += R[i] * R[i];
    }
    const float denom = std::sqrt (sumLL * sumRR);
    return (denom > 1e-20f) ? (sumLR / denom) : 1.0f;
}
```

> [!tip] 相关度表的正确用法
> - **> 0**：mono 安全
> - **接近 0**：很宽，但 mono 下会损失能量
> - **< 0**：危险，mono 下会抵消
>
> **但相关度是平均值**——它**看不出**上面的频率相关抵消。
> 所以还需要**频谱上的 mono 检查**。

## 六、AI 会怎么写错

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **用 Haas 延迟做加宽但不检查 mono** | 某些频率在 mono 下消失 | 检查是否有 mono 兼容性处理 |
| 2 | **左右共用处理状态**（如滤波器、延迟线） | 串音、宽度异常 | 检查是否 per-channel 实例 |
| 3 | **width > 1 不补偿增益** | 加宽后削波 | 检查是否有增益补偿 |
| 4 | **用 `rand()` 做去相关** | 每次运行结果不同，无法测试 | 用确定性方法或固定种子 |
| 5 | **相关度计算除以 0** | NaN | 检查 `denom` 保护 |
| 6 | **忘了 mono 输入的处理** | 单声道轨上行为错误 | 检查声道数变化的处理 |
| 7 | **混响左右完全独立** | mono 兼容性差 | 检查是否有 mono 化路径 |

> [!tip] 第 1 条最值得警惕
> AI 很擅长写"听起来很宽"的代码，但**不会主动考虑 mono**。
> 让 AI 写立体声处理时，**明确要求它说明 mono 兼容性**。

## 七、常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| mono 下某些频率消失 | 时间差/失谐的梳状抵消 | 改用 M/S，或高通侧链 |
| mono 下整体变小声 | 左右去相关 | 检查相关度 |
| 加宽后削波 | S 被放大没补偿 | 加增益补偿或限幅 |
| 宽度旋钮有"台阶" | 参数不平滑 | 见 [[参数平滑 parameter smoothing]] |
| 左右声道不一致 | 共用状态 | 每声道独立实例 |
| 相关度表跳变剧烈 | 计算窗口太短 | 加平滑 |
| 立体声混响在 mono 下变窄 | 设计问题 | 见 [[混响的原理]] |

## 八、怎么验证

| 测试 | 方法 | 期望 |
|---|---|---|
| **mono 兼容性** | 左右相加，对比频谱 | 不应有频率消失 |
| **相关度** | 计算相关系数 | > 0 |
| **宽度感** | 听感 + 侧链能量 | 主观 |
| **无削波** | 加宽后看峰值 | ≤ 0 dBFS |
| **声道独立性** | 只给左声道信号 | 右声道应无输出（除非是混响） |

```python
import numpy as np
def mono_compat(L, R):
    """检查 mono 兼容性：返回每倍频程的能量损失"""
    m = (L + R) / 2
    # 用 FFT 比较 L 和 m 的频谱
    FL = np.abs(np.fft.rfft(L * np.hanning(len(L))))
    Fm = np.abs(np.fft.rfft(m * np.hanning(len(m))))
    return 20 * np.log10((Fm + 1e-12) / (FL + 1e-12))

# 找出被抵消的频率
loss = mono_compat(L, R)
f = np.fft.rfftfreq(len(L), 1/48000)
bad = f[loss < -6]
if len(bad):
    print(f"⚠️ mono 下衰减超过 6dB 的频率: {bad[:10]}")
```
