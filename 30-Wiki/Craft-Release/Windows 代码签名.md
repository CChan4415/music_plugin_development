# Windows 代码签名

> [!warning] ⚠️ 本页置信度：低（未实测）
> 本机是 macOS，**没有 `signtool`、没有 Windows 证书、没有 Windows 环境**。
> 本页所有命令**均未在本机验证**。
>
> **计划**：等有 Windows 环境时逐条实测并升级本页。
> 见 [[_meta/open-questions]]。

> [!important] 一句话
> **Windows 签名 = 用代码签名证书给 exe/dll 盖章**，
> 目的是通过 **SmartScreen**（那个"未知发布者"警告）。

## 与 macOS 的根本区别

| | macOS | Windows |
|---|---|---|
| 工具 | `codesign`（系统自带） | **`signtool`**（需装 Windows SDK） |
| 证书格式 | keychain 里的证书 | `.pfx` 文件 / 证书存储 |
| 审核环节 | **公证**（提交苹果） | ❌ **没有对应环节** |
| 信任机制 | 公证 + Gatekeeper | **SmartScreen 信誉** |
| 时间戳 | `--timestamp` | `/tr` + `/td` |
| **能否本机验证** | ✅ 可以 | ❌ **需要 Windows** |

> [!important] 最大的区别：**Windows 没有"公证"**
> - **macOS**：签名 → **公证（苹果审核）** → staple → Gatekeeper 放行
> - **Windows**：签名 → 完事。但 **SmartScreen 仍可能警告**
>
> 所以 Windows 侧的"用户看到警告"问题**更难彻底解决**。

---

## 一、SmartScreen：真正的门槛

> [!danger] 签名了**不等于**没有警告
> SmartScreen 的判定依赖**信誉**（reputation），不只是"有没有签名"。

| 证书类型 | SmartScreen 行为 |
|---|---|
| **无签名** | ❌ 立即警告"未知发布者" |
| **标准代码签名证书** | 🟠 仍然警告，直到累积足够下载量 |
| **EV 证书**（扩展验证） | ✅ **通常立即获得信誉** |

> [!warning] ⚠️ 以下均需自行核实（本页不写死）
> - EV 证书的**当前价格**
> - SmartScreen 信誉的**具体机制**（微软未完全公开）
> - 标准证书需要多少下载量才能"洗白"
> - 是否需要注册微软开发者账号
>
> **这些会变，做决策前查微软官方文档。**

> [!note] 对独立开发者的现实
> EV 证书通常比标准证书贵不少，且需要**硬件令牌**（见下）。
> 如果预算有限，接受"初期有警告"是常见选择——
> 在下载页面上写清楚"为什么会有警告、怎么继续"。

## 二、⚠️ 2023 年后的重大变化：密钥必须硬件保护

> [!danger] 这是**最重要**的一条（也是最容易踩的）
> 大约 2023 年起，主流 CA 要求代码签名私钥**必须存储在
> 硬件安全模块（HSM）或硬件令牌**中，**不能再是普通的 `.pfx` 文件**。
>
> **这直接改变了 CI 的做法。**

| 方式 | 说明 | 对 CI 的影响 |
|---|---|---|
| **硬件 USB 令牌**（如 YubiKey） | 插在机器上 | ❌ **CI 无法用**（除非自建 runner + 插令牌） |
| **云 HSM 服务** | CA 提供的云签名服务 | ✅ **CI 友好**（推荐） |
| 本地 HSM | 机架设备 | 🟠 需自建 runner |

> [!warning] ⚠️ 具体规则需核实
> 上述变化的**确切生效时间、适用范围、CA 差异**我**没有核实**。
> **购买证书前必须问清楚 CA**：
> 1. 私钥能不能导出？
> 2. 支持哪些云的签名服务？
> 3. CI 里怎么用？
>
> 这是**买之前就要问清**的问题——买到不能用于 CI 的证书会很麻烦。

## 三、基本命令（⚠️ 未实测）

> [!warning] 以下命令**未经本机验证**（本机无 signtool）

```
signtool sign /f cert.pfx /p <password> ^
              /tr http://timestamp.digicert.com ^
              /td sha256 ^
              /fd sha256 ^
              MyPlugin.vst3
```

| 参数 | 作用 | 备注 |
|---|---|---|
| `/f cert.pfx` | 证书文件 | ⚠️ 新规下可能不可用 |
| `/p <password>` | 证书密码 | CI 里要用 secrets |
| `/tr <url>` | **RFC3161 时间戳服务器** | ⚠️ URL 需自行核实 |
| `/td sha256` | 时间戳摘要算法 | 用 sha256 |
| `/fd sha256` | 文件摘要算法 | 用 sha256 |
| `/as` | 附加签名（不覆盖已有） | 多签名场景 |

> [!tip] 为什么必须加时间戳
> 和 macOS 一样：**证书过期后，没有时间戳的签名会失效**。
> 有时间戳时，签名永久有效。
>
> **不加 `/tr` 的话，证书到期后用户会突然打不开你的插件。**

**验证签名**：

```
signtool verify /pa /v MyPlugin.vst3
```

| 参数 | 作用 |
|---|---|
| `/pa` | 使用默认的认证策略 |
| `/v` | 详细输出 |
| `/all` | 验证所有签名 |

## 四、签名哪些文件

> [!important] Windows 的 VST3 是**目录**，但签名对象是**里面的 exe/dll**

```
MyPlugin.vst3/
└── Contents/
    └── x86_64-win/
        └── MyPlugin.vst3        ← 这是一个 **DLL**（不是目录！）
```

> [!danger] Windows 和 macOS 的 VST3 结构不同
> | | macOS | Windows |
> |---|---|---|
> | `.vst3` 是什么 | **目录**（bundle） | **文件**（DLL） |
> | 内部结构 | `Contents/MacOS/...` | `Contents/x86_64-win/...` |
> | 签名对象 | bundle | **那个 DLL 文件本身** |
>
> **跨平台脚本必须处理这个差异。**

**需要签名的文件**：

| 文件 | 需要吗 |
|---|---|
| 插件 DLL（`.vst3` 文件） | ✅ |
| 独立程序（`.exe`） | ✅ |
| 安装程序（`.exe` / `.msi`） | ✅ **尤其是这个**（用户先看到它） |
| 额外的 `.dll` 依赖 | ✅ |

> [!warning] 顺序很重要
> **先签内部的 DLL，再签安装程序**——
> 否则安装程序里的哈希对不上。

## 五、CI 里怎么做（⚠️ 高度不确定）

> [!danger] 这部分**变化最快**，请以 CA 和微软的文档为准
> 由于"密钥必须硬件保护"的新规，CI 的做法**和几年前完全不同**。

**常见方案（按推荐度）**：

| 方案 | 说明 |
|---|---|
| **CA 提供的云签名服务** | ✅ 最推荐（Azure Trusted Signing、DigiCert KeyLocker 等） |
| 自建 runner + USB 令牌 | 🟠 可行但麻烦（机器必须物理安全） |
| 本地签名后上传产物 | ✅ 简单（人工参与，不适合频繁发布） |

> [!note] Azure Trusted Signing
> 微软推出了自己的签名服务，据称对**个人开发者更友好**（门槛比 EV 证书低）。
> ⚠️ **具体条件、价格、是否对中国区开发者开放，我没有核实。**
> 值得你自己查一下——如果适用，可能是当前最省事的路。

## 六、AI 会怎么写错

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **给过时的 `/f cert.pfx` 流程** | 新规下不可用 | 确认 CA 的要求 |
| 2 | **编造证书价格** | 决策错误 | 查官方页面 |
| 3 | **忘了 `/tr` 时间戳** | 证书过期后签名失效 | 检查命令 |
| 4 | **把 Windows VST3 当目录** | 签名脚本失败 | Windows 上是 DLL 文件 |
| 5 | **只签了 DLL 没签安装程序** | 用户装的时候仍警告 | 两者都签 |
| 6 | **以为签名就没警告了** | SmartScreen 仍会拦 | 需要信誉/EV |
| 7 | **不知道密钥硬件化新规** | CI 方案完全跑不通 | 见第二节 |
| 8 | **时间戳服务器 URL 写错** | 签名失败 | 从 CA 文档确认 |
| 9 | **在 CI 日志里打印证书密码** | 安全事故 | 用 secrets 并遮蔽 |

> [!danger] 第 1 和第 7 条是**这个领域最大的坑**
> AI 的训练数据里有大量**几年前**的签名教程（`/f cert.pfx` 那一套）。
> 在"密钥必须硬件保护"的新规下，**那套流程可能根本用不了**。
>
> **不要相信 AI 给的 Windows 签名流程。** 直接问你的 CA。

## 七、常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| CI 签名失败：无法导入证书 | 密钥在硬件里 | 用云签名服务 |
| 用户仍看到"未知发布者" | SmartScreen 信誉不足 | EV 证书，或等信誉累积 |
| 证书到期后签名失效 | 没加时间戳 | `/tr` + `/td` |
| `signtool` 找不到 | 没装 Windows SDK | 安装 SDK |
| 签名后文件损坏 | 签了错误的文件 | 确认签的是 DLL/exe |
| 安装后插件被拦 | 只签了安装程序 | 内部 DLL 也要签 |

## 八、怎么验证（⚠️ 需要 Windows）

```
:: 验证单个文件
signtool verify /pa /v MyPlugin.vst3

:: 查看签名详情
signtool verify /pa /v /all MyPlugin.vst3

:: PowerShell 查看签名
Get-AuthenticodeSignature MyPlugin.vst3 | Format-List
```

> [!tip] 最可靠的验证：**找一台干净的 Windows**
> 你自己的开发机装了证书和信任设置，**测不出真实用户体验**。
> 理想情况是在一台**从没装过你东西**的 Windows 上测。

**检查清单**（⚠️ 待实测）：

- [ ] 所有 DLL/exe 都已签名
- [ ] 安装程序也已签名
- [ ] 有可信时间戳
- [ ] 在干净的 Windows 上测过
- [ ] SmartScreen 的实际行为（首次下载时）
