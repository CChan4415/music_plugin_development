# 动态处理的原理

> [!important] 这一页解决什么问题
> 压缩器的 DSP 部分**极其简单**——一个检测器、一个增益计算、一个平滑器，不到 50 行。
> 但市面上的压缩器插件有几千个，好用的只有那么几个。
> 差别不在算法复杂度，在于**每个参数背后对应哪一个音乐决策**。
>
> 你调了十年压缩器。这一页把你手上的动作翻译成代码里的变量，
> 以及——为什么"照抄硬件参数"做出来的插件往往不对。

## 1. 压缩器到底在做什么

**一句话**：压缩器在**降低信号的动态范围**，让"响的地方"和"轻的地方"差距变小。
它**不是**在提升响度——这两件事经常被混为一谈，但工程上是完全分开的两步：

```
输入 → [检测器] → [增益计算] → [增益平滑] → × → [makeup gain] → 输出
         ▲                                      │
         └────── 侧链信号（通常 = 输入）─────────┘
```

| | 压缩（compression） | 响度（loudness） |
|---|---|---|
| 改变什么 | 动态范围 / 峰均比（crest factor） | 平均能量 |
| 谁做的 | 增益计算 + 平滑 | **makeup gain** |
| 结果 | 输出的**峰值变低**了 | 整体被推高了 |
| 极端例子 | ratio = ∞、threshold 很低 → 输出几乎恒定，但**很安静** | 不压缩，只把推子拉高 → 响，但会削波 |

> [!important] 关键认识
> **一个不加 makeup gain 的压缩器，只会让声音变安静。**
> 你觉得"压缩之后更响了"，是因为 ① 峰值被压低了 → 有 headroom 把整体推高
> ② 轻的部分被相对抬高了 → 感知上的"密度"增加。
> **"更响"来自 ①，"更好听/更结实"来自 ②。** 混淆这两件事，就会做出"参数都对但用户觉得没用"的插件。

**静态曲线（static curve）** 决定压缩器的全部"性格"（dB 域，$T$ = threshold，$R$ = ratio）：

$$\text{out}_{dB} = \begin{cases} \text{in}_{dB} & \text{in}_{dB} \le T \\[4pt] T + \dfrac{\text{in}_{dB} - T}{R} & \text{in}_{dB} > T \end{cases}
\qquad
\text{GR}_{dB} = \left(\frac{1}{R} - 1\right)\left(\text{in}_{dB} - T\right)$$

增益衰减量（gain reduction, GR）就是输入减输出。注意 $\frac{1}{R} - 1$ 是**负数**——衰减量是负的 dB。

| Ratio | GR（输入超出阈值 12 dB 时） | 听感 |
|---|---|---|
| 1.5 : 1 | −4 dB | 几乎只是"扶着"，很难听出在压 |
| 2 : 1 | −6 dB | 总线胶水的常用值 |
| 4 : 1 | −9 dB | 明显的控制感，人声常用 |
| 8 : 1 | −10.5 dB | 很强的控制，接近限制 |
| 20 : 1 | −11.4 dB | 已经是限制器行为 |
| ∞ : 1 | −12 dB | 硬限制：超出阈值的一律砍平 |

> [!tip] 这张表解释了一个常见困惑
> "为什么 ratio 从 4 拧到 8，听起来变化不大？"因为超出阈值 12 dB 时，
> 4:1 给 −9 dB，8:1 只给 −10.5 dB——**差 1.5 dB**；而 1.5:1 到 2:1 只差 2 dB，听感变化却很明显。
> **ratio 的感知是非线性的，在高 ratio 区趋于饱和。** 这就是为什么很多插件的
> ratio 旋钮用非线性刻度，或直接给档位。

## 2. 四个时间参数的听感含义

### Attack：瞬态保不保留

| Attack | 结果 | 听感 | 音乐用途 |
|---|---|---|---|
| 极快（< 1 ms） | 瞬态**在发生前/同时**就被压掉 | "平"、"控制住了"、"没有棱角" | 消除爆破音、控制不可预测的源、限制器 |
| 快（1–10 ms） | 瞬态的**峰值**被削掉一点 | 结实、紧凑，但可能失去"空气感" | 人声、贝斯的稳定控制 |
| 中（10–30 ms） | 瞬态**通过**，之后才压 | **冲击力保留**，身体被压住 | 鼓组、贝斯（保留指弹的 attack） |
| 慢（> 30 ms） | 整个音头都通过了 | 明显的"先响后压"，有"呼吸" | 总线胶水、慢速电平骑乘 |

> [!important] 为什么"慢 attack 更有冲击力"——反直觉但正确
> 压缩器**降低**了电平。瞬态被压掉 = 声音的"第一下"变小了。
> 慢 attack 让瞬态完整通过，压缩器只对**之后的持续部分**做功，
> 于是"音头 vs 音身"的比例被**放大**了。
> **冲击力不是被创造出来的，是被"相对抬高"出来的。**

### Release：呼吸感

Release 是压缩器里**最难调**的参数，因为正确值取决于音乐的速度和节奏型。

| Release | 结果 | 听感 | 什么时候用 |
|---|---|---|---|
| 极快（< 30 ms） | 增益跟着波形抖动 | **抽吸（pumping）**、"抽气"声、失真感 | 几乎从不（除非刻意做效果） |
| 快（50–150 ms） | 每个瞬态后立刻恢复 | 有力、紧凑，但可能在低频上产生失真 | 鼓组、打击乐 |
| 中（150–400 ms） | 跟得上音乐但不过度 | 自然 | 人声、贝斯、大多数情况 |
| 慢（> 500 ms） | 增益被"按住" | 平滑、"压住不放"、失去生命力 | 总线、需要极度平滑的场合 |
| 自动 / 程序相关 | 跟随音乐 | "有音乐性" | 总线、母带（见 §7） |

> [!warning] Release 太快 = 失真，不只是"抽吸"
> 增益在低频的一个周期内就恢复，等于**用一个音频速率的信号去调制音频本身**——
> 这是**调制**，会产生原始信号里没有的边带（谐波失真）。50 Hz 低频的一个周期是 20 ms；
> release 在 20 ms 量级时，你就是在每个低频周期上做一次增益变化。
> **经验法则：release 至少要长于你希望处理的频段的几个周期。**
> 这是很多压缩器"低频听起来脏"的真正原因。

### Threshold / Ratio

Threshold 决定"从哪里开始"以及有多少素材被处理；Ratio 决定"处理多狠"。
**调参的顺序**（也是你的 UI 应该引导的顺序）：
① **先设 ratio**（决定性格：2:1 是胶水，4:1 是控制，8:1+ 是限制）
② **再设 threshold**，直到 GR 表在**最响的部分**有 2–4 dB（总线）或 4–8 dB（单轨）
③ **最后调 attack / release**（决定听感）

**很多插件把 threshold 放在最显眼的位置，这是对的。**
反过来，如果 UI 让用户先调 attack/release，他们永远调不出能用的声音。

### 典型参数区间

> [!note] 这是惯例，不是定律
> 下面的区间来自混音工程领域的普遍做法，属于 **craft 常识**而非推导出的结论。
> 它应该作为你插件**默认值和参数范围**的依据，而不是硬性规则。

| 音源 | Attack | Release | Ratio | 目标 GR | 为什么 |
|---|---|---|---|---|---|
| **人声** | 5–15 ms | 100–250 ms | 3:1–4:1 | 4–8 dB | 保留辅音（清晰度），压住元音（稳定度）。release 太慢会让句子之间"喘不上气" |
| **鼓组** | 10–30 ms | 80–200 ms | 4:1–8:1 | 4–8 dB | 慢 attack 放过音头保留冲击力；快 release 让下一个鼓点前恢复 |
| **贝斯** | 10–30 ms | 100–300 ms | 4:1–6:1 | 4–8 dB | 慢 attack 保留指弹 attack；release 必须长于低频周期 |
| **总线 / 母带** | **30–100 ms** | **300 ms–2 s / 自动** | **1.5:1–2:1** | **1–3 dB** | 慢 attack 不动瞬态；低 ratio 只做"轻微统一"；GR 必须小 |
| **限制器** | 最快（lookahead 决定） | 50–200 ms | 10:1–∞:1 | 只在峰值上 | 目标不是"塑形"而是"保证不超过 0 dBFS"，见 §5 |

> [!warning] 为什么总线的 GR 必须小
> 总线上每个音源都已经被单独压过了。如果总线再压 6 dB，
> 你实际上是在**对已经压扁的东西再压一次**——动态范围被吃两次，结果就是"扁"。
> **总线压缩的目的是"统一"，不是"控制"。1–3 dB 就够，且要在最响的段落才到 3 dB。**

## 3. 为什么"胶水"（glue）会发生

"glue" 不是玄学，它是一个**可以精确描述的机制**：

> **当所有音源共享同一个增益信号时，它们的电平起伏会变成"同一次起伏"。**

人耳把"一起起伏的声音"归为同一个事件（[[听觉场景分析]] 的共同命运原则）。
单独压缩每个音轨时各音源的增益信号**互不相关**——各自呼吸；
总线压缩时检测器看到**混音总和**，所有音源被**同一个**增益曲线调制。

| 配置项 | 值 | 为什么这样能产生胶水 |
|---|---|---|
| 检测器输入 | **混音总和**（不是每声道各自看） | 所有音源共享一个增益信号 → "共同命运"；同时保证声像不摇摆 |
| Attack | 慢（30–100 ms） | 不改变各音源之间的**瞬态平衡**（谁先谁后保持不变） |
| Ratio / GR | 低（1.5:1–2:1）/ 小（1–3 dB） | 只做轻微的相对调整，不重塑音色；只在最响处介入 |
| Release | 慢 / 程序相关 | 增益变化比音乐**慢** → 听成"整体在呼吸"而不是"某个音源被压" |
| 膝 / 检测器前高通 | 软 6–12 dB / 100–200 Hz | 避免阈值附近的抓取感；避免 kick/bass 把整个混音按下去 |

> [!important] 为什么慢 attack 是胶水的关键
> attack 很快时，压缩器会**按各音源的先后顺序**分别压——鼓先到就被压，人声后到也被压，
> 但压的时间和量不同。结果是"每个音源都被单独塑形了"，反而更分离。
> **慢 attack 让增益信号落后于所有瞬态**，于是它只反映"整体的能量水平"，
> 这才是"一个整体"的感知来源。

## 4. 检测器设计：Peak vs RMS

检测器（detector）是压缩器的**传感器**。它做错了，后面的增益计算再精确也没用——
这也是 [[MOC - DSP]] 把 [[包络跟随器 envelope follower]] 列进"最重要 5 个概念"的原因。

| | Peak 检测 | RMS 检测 |
|---|---|---|
| 测什么 | 瞬时绝对值 `|x[n]|` 的包络 | 短时均方根 |
| 响应对象 | **单个采样点** | 一段时间窗内的**能量** |
| 与感知响度的关系 | 弱 | **强** |
| 优点 | 能抓住任何越界，适合限制器 | 增益变化"有理由"，听感自然 |
| 缺点 | 被孤立尖峰主导，产生"没有理由的压缩" | 对极短瞬态反应不够快，可能放过峰值 |
| 典型用途 | 限制器、数字峰值保护、de-esser | **所有"听得见的"音乐性压缩** |

> [!important] 为什么"听得见的压缩"通常用 RMS
> 一个复杂波形的**采样峰值**和**它的响度**关系很弱——一个相位对齐的瞬间可能让某个采样点
> 飙高 6 dB，但那一瞬间耳朵听不出任何变化。Peak 检测器会**为这个听不见的尖峰压掉整个信号**
> → 用户听到增益在动，但不知道为什么动。**这就是"这个压缩器很神经质"的技术原因。**
> RMS（或带快 attack 的峰值 + 长 release）跟随的是**波形的包络**，与感知响度相关性高得多。

```cpp
// 指数平均：对 x² 做一阶低通，再开方
void  prepare (double sr, float windowMs)
{ coeff = 1.0f - std::exp (-1.0f / (float) (sr * windowMs * 0.001)); }

float process (float x)
{
    meanSquare += (x * x - meanSquare) * coeff;
    return std::sqrt (std::max (0.0f, meanSquare));   // max 防浮点误差产生负数
}
```

> [!warning] "RMS 窗口"和"时间常数"不是一回事
> 上面用的是**指数**平均，不是矩形滑动窗：等效积分时间约是时间常数的 **2 倍**，
> 且旧数据永远有一点点权重。所以不同压缩器标称的 "RMS window = 10 ms" 实际响应可能差别很大，
> 取决于它用指数平均、滑动平均、还是双时间常数。**在你的文档里写清楚你用的是什么定义。**

### 侧链滤波与立体声链接

低频能量天然比中高频大得多，检测器直接看宽带信号时，
每次 kick 或贝斯音符都会把整个混音按下去——这是"pumping"的另一个来源。
解法是在**检测器之前**加高通（**只改变检测，不改变音频路径**）。

| 侧链滤波 | 效果 | 什么时候用 |
|---|---|---|
| 无 | 低频主导检测 | 想要"整个混音跟着 kick 呼吸"（做效果时） |
| 高通 100–200 Hz | 低频不再触发压缩 | **总线压缩的默认做法** |
| 高通 20–50 Hz | 只去掉直流和次声 | 安全网，几乎所有压缩器都该有 |
| 带通 / 高频提升 | 只被某个频段触发 | de-esser、去齿音、频率选择性压缩 |

> [!warning] 侧链滤波器的相位
> 高通会引入相位失真和**群延迟**。这不影响音频路径（音频没被滤），
> 但会影响**检测的时序**——增益到达的时间会晚一点点。
> 在追求精确的 lookahead 限制器里，这个延迟必须算进去。

**立体声链接必须做**：左右各自独立检测会导致**声像摇摆**（左声道响的时候左被压，声音左右晃动）。

| 检测量 | 评价 |
|---|---|
| `max(|L|, |R|)` | ✅ 推荐。左右被同一个增益调制，声像稳定 |
| `sqrt((L²+R²)/2)` | ✅ 推荐。不受反相影响；稍贵 |
| `0.5*(L+R)` | ⚠️ **不要用**。左右有反相成分时检测电平偏低，压缩器会"听不见"它，该压的时候没压 |

## 5. 前瞻（lookahead）：为什么限制器必须用它

**没有 lookahead 的限制器一定会有过冲（overshoot）**，原因是因果性：
检测器**只能在瞬态到达之后**才知道它来了，而 attack 平滑需要时间，
两者相加 = 瞬态的前几个采样**没被压到** → 削波。
**解法**：把**音频延迟**一段固定时间，让检测器先看到未来。

```cpp
for (int i = 0; i < n; ++i)
{
    lookahead.write (x[i]);                          // 音频进延迟线
    const float grDb     = gainComputer.compute (std::abs (x[i]));  // 检测看"现在"
    const float smoothed = smoother.process (grDb);

    // 读出的是 lookaheadSamples 之前写进去的音频（= 过去），
    // 但增益已经根据"现在"（= 输出的未来）算好了
    x[i] = lookahead.read (lookaheadSamples) * dbToGain (smoothed);
}
```

> [!important] lookahead 时间和 attack 时间必须匹配
> 如果 lookahead 是 5 ms，但 attack 需要 10 ms 才能到达满衰减，
> 峰值出来时增益只降了一半——**仍然过冲**。
> **规则：attack 斜坡必须在 lookahead 时间内完成。**
> 通常做法是让 attack 时间 ≈ lookahead 时间，或直接用 lookahead 时间作为 attack 时间。

lookahead **就是**延迟：你把音频推后了 N 个采样，**必须报告给宿主**。

```cpp
// prepareToPlay() 里
const int lookaheadSamples = (int) std::round (lookaheadMs * 0.001 * sampleRate);
setLatencySamples (lookaheadSamples);     // JUCE；VST3 是 setInitialDelay
```

| 不报告的后果 | 说明 |
|---|---|
| 宿主做延迟补偿（PDC） | 不知道你的延迟 → 其他轨道不会对齐 → 整个混音错位 |
| 用户录音时监听 | 监听有延迟，演奏会"跟不上" |
| 离线导出（bounce） | 导出结果和实时播放**不一致** |
| 多实例串联 | 延迟累积，宿主补偿错误 |

> [!warning] 延迟是"契约"，不是"性能指标"
> 报告错误的延迟比不报告更糟——宿主会按错误的值补偿，产生**固定但错误的错位**，
> 而用户很难诊断。另外 `setLatencySamples` **必须在音频线程之外调用**，
> 且改变它会让宿主重新计算延迟补偿（可能有短暂的静音或爆音）。
> 见 [[实时音频线程契约]]、[[延迟报告 latency reporting]]、[[旁路 bypass 的正确实现]]。

## 6. 软膝 vs 硬膝

**硬膝**：输入一旦超过阈值，增益立刻按 ratio 下降，静态曲线在阈值处有一个**拐点**。
**软膝**：在阈值附近的一个区间（膝宽 $W$，单位 dB）内，增益**渐进**地介入。

```cpp
// xDb: 检测器电平(dB)  T: 阈值  R: ratio  W: 膝宽(dB)，W=0 即硬膝
inline float computeGainDb (float xDb, float T, float R, float W)
{
    const float slope = 1.0f / R - 1.0f;                  // 负值
    if (W <= 0.0f) return (xDb > T) ? slope * (xDb - T) : 0.0f;   // 硬膝
    if (2.0f * (xDb - T) < -W) return 0.0f;                       // 膝下：不压
    if (2.0f * std::abs (xDb - T) <= W)                           // 膝内：二次插值
    { const float d = xDb - T + W * 0.5f; return slope * d * d / (2.0f * W); }
    return slope * (xDb - T);                                     // 膝上：正常压缩
}
```

> [!tip] 验证软膝实现是否正确
> 在膝的**两个边界**上，软膝公式必须和相邻段**连续**：
> - 在 $x = T - W/2$ 处，膝内公式给出 0 ✓（与"膝下"段连续）
> - 在 $x = T + W/2$ 处，膝内公式给出 $\text{slope} \cdot W/2$，"膝上"公式也给同一个值 ✓
>
> **这两个等式就是你单元测试的断言。** 不连续 = 增益曲线有台阶 = 听得见的"抓取"声。

| 膝宽 | 听感 | 什么时候用 |
|---|---|---|
| 0 dB（硬膝） | 明确的"介入点"，有抓取感 | 限制器、效果性压缩、需要精确控制的场合 |
| 3–6 dB | 轻微过渡 | 单轨压缩的常见默认值 |
| 10–20 dB | 极其平滑，几乎听不出介入点 | 总线、母带、需要"透明"的场合 |


> [!warning] 软膝会改变"有效阈值"
> 膝宽 $W$ 意味着**从 $T - W/2$ 开始就已经在压缩了**。把硬膝插件换成软膝插件、参数照抄，
> 得到的 GR 会**更多**。**用户会抱怨"你这个压缩器比那个压得狠"**，而其实是膝宽不同。
> 做法：在 UI 上明确显示膝宽，或把 threshold 定义为膝的**中心**并在文档里写清楚。

## 7. 程序相关 release：为什么经典硬件"跟音乐走"

固定 release 有一个根本困境：**真实音乐的速度是变化的。**
release 短 → 快节奏段落跟得上，但慢段落会抽吸；release 长 → 慢段落平滑，但快节奏段落一直压着。
经典硬件压缩器用**多个时间常数**或**自适应**的方式让 release 跟音乐走，
这就是"模拟味"的一个**具体、可实现**的来源。

```cpp
// 方式 1：双时间常数（two-stage release）—— 经典硬件最常见的做法
// 先快速恢复前 2 dB，之后转慢速。releaseStartDb 在 attack 阶段记下来
float twoStageRelease (float cur, float target, float releaseStartDb)
{
    const float delta = target - cur;                        // >0 表示在恢复
    if (delta <= 0.0f) return cur;                           // 在压缩，交给 attack
    const float c = (cur < releaseStartDb + 2.0f) ? fastCoeff : slowCoeff;
    return cur + delta * c;
}

// 方式 2：release 随 GR 量变化 —— 压得越狠，放得越慢
float grDependentRelease (float grDb, float baseMs, float scaleMs)
{ return baseMs + scaleMs * std::clamp (-grDb / 12.0f, 0.0f, 1.0f); }

// 方式 3：双包络并联 —— 一个快一个慢，取较大者（或加权）
// 快包络抓住瞬态，慢包络决定整体恢复速度
```

> [!note] 这三种都是"模拟味"的具体来源
> [[从音乐制作人到插件开发者]] 里那张翻译表说
> "压缩器有粘性 glue → 通常是慢 attack + 程序相关 release"。
> **这一节就是那句话的实现。** "模拟味"不是一个算法，是一组可分解的工程选择。

> [!warning] 待验证：经典硬件的具体实现细节
> 不同厂商用的方案不同（双时间常数、GR 相关的可变 release、多级包络、光耦/场效应管的
> 非线性恢复曲线……）。上面三种是**通用的实现模式**，不是对任何具体硬件的逆向结论。
> 想精确复刻某个硬件，需要**实测它的 release 曲线**（喂阶跃信号，记录 GR 随时间的变化）。

## 8. 增益补偿（makeup gain）：为什么自动补偿很难做好

**最简单的做法**（也是最糟的）：

```cpp
// ❌ 假设输入电平总是 0 dBFS，根据静态曲线反推补偿量
const float autoMakeupDb = -computeGainDb (0.0f, T, R, 0.0f);
```

它假设"输入峰值总是满刻度"，但实际素材的峰值电平千差万别——
输入峰值只有 −12 dBFS 时，这个补偿量会**过度补偿 12 dB**。

| 为什么本质上很难 | 说明 |
|---|---|
| 感知响度不是线性的 | 3 dB GR 在中频听起来"轻微"，在低频听起来"少了一大块"（见 [[等响曲线与频率加权]]） |
| 依赖素材与时间 | 峰均比随素材变化巨大；压缩器的介入比例也在变化，平均值 ≠ 瞬时值 |
| 依赖频段 | 宽带 GR 对不同频段影响不同，感知响度加权也不同 |
| 反馈回路 | 补偿后的信号若又进入检测器会形成反馈（除非检测器看压缩前） |

> [!important] 一个诚实的设计建议
> **把 makeup gain 做成手动的，但提供好的辅助：** ① 显示**实时的输入/输出电平表**
> （不只是 GR 表），用户自己就能对齐 ② 提供一个 "auto" 按钮，但让它基于**实际的 RMS 测量**
> （比较压缩前后的短时 RMS），而不是基于阈值和 ratio 反推 ③ 明确标注 auto 的行为，允许关掉。
>
> **不要偷偷做自动补偿。** 用户会以为"这个压缩器不压缩"，因为 GR 表在动但音量没变化。
> 这也是 [[MOC - UI & UX]] 里"压缩器增益衰减表是最重要的可视化"的原因——
> **用户需要看到 GR 和输出电平是两个独立的量。**

## 设计决策表

| 音乐人想要的 | 算法上要实现什么 |
|---|---|
| "让它更结实，但别听出来在压" | 软膝 10–15 dB + 低 ratio（2:1）+ 慢 attack + RMS 检测 |
| "人声要稳，但不能失去清晰度" | attack 5–15 ms（放过辅音）+ release 100–250 ms + 检测器前高通 |
| "鼓要更有冲击力" | **慢 attack（10–30 ms）** 让音头通过 + 快 release（80–200 ms）+ peak/RMS 混合检测 |
| "整个混音要粘在一起" | 检测器看**总和** + 慢 attack（30–100 ms）+ 1.5:1 + GR ≤ 3 dB + 程序相关 release |
| "不要被 kick 触发" | 检测器前加 100–200 Hz 高通（**只滤检测路径**） |
| "绝对不能削波" | lookahead（attack 斜坡在 lookahead 内完成）+ 高 ratio + peak 检测 + `setLatencySamples()` |
| "release 要跟着音乐走" | 双时间常数或 GR 相关的可变 release |
| "低频不要抽吸/失真" | release 长于目标频段的几个周期；或做多段压缩 |
| "立体声不能晃" | 检测 `max(|L|,|R|)` 或 `sqrt((L²+R²)/2)`，**不要**用 `(L+R)/2` |
| "压缩前后音量要对得上" | 手动 makeup + 输入/输出双电平表；auto 模式要基于实测 RMS |
| "要有模拟味" | 程序相关 release + 检测器/增益级的轻微非线性 + 元件容差式的不一致 |
| "看得见的 GR" | 从音频线程通过无锁队列把 GR 值送到 UI，见 [[实时音频线程契约]] |

## 常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| 抽吸（pumping）、"抽气"声 | release 太快；或检测器被低频主导 | 加长 release；检测器前加高通 |
| 低频听起来"脏"/失真 | release 短于低频周期 → 音频速率调制 | release 至少长于目标频段几个周期；或分频段处理 |
| 增益在动，但听不出为什么 | Peak 检测被孤立尖峰主导 | 改用 RMS 检测，或给 peak 检测器加慢 attack |
| 压缩器"很神经质" | 同上；或膝宽为 0 | 加软膝；检查检测器类型 |
| 鼓失去冲击力 | attack 太快，音头被削 | 放慢 attack 到 10–30 ms |
| 总线压缩后整体"扁"了 | GR 太大；或 ratio 太高 | GR 压到 1–3 dB；ratio 降到 2:1 以下 |
| 立体声声像左右摇摆 | 左右声道独立检测 | 用 `max(|L|,|R|)` 或 `sqrt((L²+R²)/2)` 链接 |
| 侧链压缩"没反应" | 侧链信号是反相的 / 检测器用了 `(L+R)/2` | 改用不受反相影响的检测方式 |
| 限制器仍有 overshoot | lookahead 时间 < attack 时间；或没做 intersample peak | 让 attack ≈ lookahead；考虑 true-peak 检测 |
| 导出和实时播放不一样 | 没报告延迟，或离线渲染时 lookahead 未生效 | 正确 `setLatencySamples`；离线渲染测试 |
| 压缩器爆音/咔哒 | 增益变化没有平滑（一个 block 内直接跳变） | 平滑**增益**（不是平滑电平）；见 [[参数平滑 parameter smoothing]] |
| 静音时 CPU 飙升 | 检测器/平滑器的状态进入 denormal | 见 [[denormal 数处理]] |
| bypass 时音量跳变 | makeup gain 没被旁路，或状态残留 | 见 [[旁路 bypass 的正确实现]] |
| "和别的插件设一样参数但不一样" | 检测器类型、膝宽定义、attack/release 定义不同 | 在文档里写清定义；见下 |

> [!warning] attack / release 的"时间"有至少三种定义
> - **时间常数（time constant）**：达到目标变化的 63% 所需时间
> - **10% → 90%**：达到 90% 所需时间（约是时间常数的 2.3 倍）
> - **到达满衰减的时间**
>
> 三者可以差 2–3 倍。**你和别的插件对比时参数一样但听感不同，很可能就是这个原因。**
> 你的插件必须在文档里写明用哪一种。建议用**时间常数**（它直接对应一阶低通的数学），
> 但在 UI 上可以标注得模糊一些（"Fast / Medium / Slow"）。

## 怎么验证

**听感测试**

1. **瞬态**：鼓循环，attack 从最快扫到最慢，应听到"平 → 结实 → 有冲击力"。
   听不到"冲击力"= attack 范围不够慢。
2. **抽吸**：release 从最短扫到最长（持续低频 + 稳定 pad），应听到"抽气 → 自然 → 压住不放"。
   **最短的 release 不产生抽吸 = release 范围不够。**
3. **胶水**：鼓 + 贝斯 + 人声送总线压缩器，GR 从 0 加到 3 dB，应在 1–2 dB 时听到"变成一个整体"。
   **听不到 = 检查检测器是否看总和、attack 是否够慢。**
4. **限制器过冲**：喂突然出现的满刻度瞬态，输出**绝不能**超过 0 dBFS。
5. **声像**：只给左声道响信号，右声道电平**不应**变化（变了说明检测器没链接）。

**数值测试**

```cpp
// 1. 静态曲线 —— 最高杠杆的一个，先写它再写插件
//    喂稳态正弦扫 -60 → 0 dBFS，画输出 vs 输入：应是一条折线
//    折点在 threshold 处，斜率 = 1/R，膝内曲线单调、连续、可导
// 2. 软膝连续性：断言 T±W/2 两侧的 computeGainDb 值相等（膝下处 == 0）
// 3. 时间常数：喂阶跃，GR 从 0 到最终值 63% 的时间 == 设定的 attack
// 4. 无过冲：喂 10 秒白噪声 + 随机瞬态，ratio = ∞，threshold = -1 dBFS
//    断言 max(|output|) <= 1.0
// 5. 增益平滑：喂直流 1.0，threshold 从 -20 跳到 -40
//    断言输出的一阶差分最大值小于阈值
// 6. 立体声链接：左满刻度、右 -20 dBFS
//    断言右声道的 GR == 左声道的（差值 < 0.01 dB）
```

> [!tip] 测试 1 能在 30 秒内抓出
> 阈值定义错、ratio 公式错、膝宽符号错、dB 换算用了 /20 而不是 /10（功率 vs 幅度）。
> **先写这个测试，再写插件。**
