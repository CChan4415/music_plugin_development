# 实时神经网络推理约束

> [!important] 一句话
> **神经网络能进音频插件，但"每采样算多少次乘加"是硬约束**——
> 超过预算就必须**降低控制率**（在更低的采样率上跑推理）。

## 先算清楚预算

$$\text{每样本预算} = \frac{1}{f_s} \quad \text{秒}$$

| 采样率 | 预算 | 大致能负担 |
|---|---|---|
| 44.1 kHz | 22.7 µs | 中等模型 |
| **48 kHz** | **20.8 µs** | 中等模型 |
| 96 kHz | 10.4 µs | 小模型 |
| 192 kHz | 5.2 µs | 很小的模型 |

> [!danger] 这是**单核**预算，且要和宿主 + 其他插件共享
> **实践目标**：推理占 **< 10%** 预算。

---

## 一、模型规模 vs 可行性（估算）

**假设**：单核有效算力约 5 GFLOP/s（含内存访问开销），48 kHz。

| 模型规模 | 每采样 MAC | 需求 | 可行性 |
|---|---|---|---|
| 小型（1 层 32） | 32 | 3.1 MFLOP/s | ✅ **可行**（0.1%） |
| 中型（2 层 64） | 128 | 12.3 MFLOP/s | ✅ **可行**（0.2%） |
| LSTM(64) | 256 | 24.6 MFLOP/s | ✅ 可行（0.5%） |
| WaveNet（小） | 1000 | 96.0 MFLOP/s | ✅ 可行（1.9%） |
| **WaveNet（大）** | **10000** | **960 MFLOP/s** | 🟠 **勉强**（19.2%） |

> [!warning] 这是**粗估**，不是实测
> "5 GFLOP/s" 是个保守的经验值，取决于：
> - CPU 型号与主频
> - 内存带宽（NN 推理常常是**内存受限**）
> - 是否用 SIMD / 矩阵指令
>
> **要在你的目标机器上实测**（见 [[性能剖析]]）。
>
> ⚠️ **本页不给实测的 GFLOP/s 数字**——
> 我尝试测量时踩了环境 bug（见下），测出的数字不可信。

> [!note] 一个诚实的说明：我测不出可靠的吞吐
> 我本想给出本机 numpy 的实测吞吐，但发现：
> **本机 bundled Python 的 numpy `float32` 矩阵乘返回全零。**
>
> ```python
> A = np.random.randn(4,4).astype(np.float32)
> B = np.random.randn(4,4).astype(np.float32)
> np.count_nonzero(A @ B)     # → 0   ❌
> # 同规模 float64 → 16 ✅
> ```
>
> 我测出的 "24574 GFLOP/s" 其实是**空操作的时间**——
> 物理上不可能（Apple Silicon 单核约 50 GFLOP/s）。
>
> **所以本页只用"相对结论"，不报绝对吞吐。**
> 详见 [[2026-10-14 测量工具会骗你 —— 十一次踩坑记录]]。

## 二、⚠️ 最大的坑：逐样本调用

> [!danger] 同样的运算，逐样本调用比批处理慢一个数量级
>
> **实测**（本机，16→32→1 的两层网络）：
>
> | 方式 | 耗时/样本 | 相对 |
> |---|---|---|
> | **逐样本**（48000 次单独调用） | **2.143 µs** | 1× |
> | **分块**（每块 512） | **0.044 µs** | **48.3× 更快** |
>
> **48 倍的差距**，而运算量完全相同。
>
> **原因**：调用开销（函数调用、维度检查、临时对象）占主导。
> `2.143 µs` 里绝大部分是**调用开销**，不是真的运算。

> [!important] 对插件设计的直接指导
> ```
> ❌ for (每个采样) { 调用推理() }
> ✅ 收集一个 block → 调用一次推理 → 分发结果
> ```
>
> 这也符合 [[实时音频线程契约]]：
> **按 block 处理**是音频插件的标准模式。
>
> **例外**：如果你的模型有**内部状态**（RNN/LSTM）且状态更新依赖每采样，
> 那就必须逐样本——但要把**实现内联**（C++），不要走 Python/框架调用。

**对比：控制率降低**

> [!tip] 如果模型太大，就**降低控制率**
> 不一定要在 48 kHz 上跑推理。
>
> | 控制率 | 每"控制步"的预算 | 适合 |
> |---|---|---|
> | 48 kHz（音频率） | 20.8 µs | 波形合成（WaveNet 类） |
> | **1 kHz** | **1 ms** | 参数预测、音色映射 |
> | 100 Hz | 10 ms | 缓慢变化的控制（包络、响度） |
> | 10 Hz | 100 ms | 元参数（风格、情绪） |
>
> **大量"AI 音频"其实只需要低控制率**——
> 比如用 NN 预测滤波器系数、压缩器参数，
> 这些参数本来就是**慢变**的。

## 三、实时推理的五条硬约束

> [!important] 这些和 [[实时音频线程契约]] 完全一致

| # | 约束 | 为什么 | 怎么做 |
|---|---|---|---|
| 1 | **无动态分配** | malloc 不可预测 | 权重和中间缓冲在 `prepare` 里分配 |
| 2 | **无锁** | 优先级反转 | 模型固定；要换模型用 [[SPSC 队列]] |
| 3 | **确定性延迟** | 宿主要做补偿 | 报告推理引入的延迟 |
| 4 | **CPU 可预测** | 偶发爆音 | 避免"偶尔很慢"的分支 |
| 5 | **权重常驻** | 不能每次加载 | 加载一次，常驻内存 |

> [!danger] 第 4 条对 NN 特别重要
> NN 推理的时间**通常很稳定**（固定的矩阵运算）。
> 但有些操作会破坏这一点：
> - **动态 batch size**（有时 64、有时 512）
> - **稀疏/条件分支**（如 MoE、early-exit）
> - **动态形状**（变长序列）
>
> **实时音频要用固定形状、固定 batch。**

## 四、实际可行的方案

| 方案 | 控制率 | 典型用途 |
|---|---|---|
| **参数映射**（NN 输出滤波器系数） | 10–100 Hz | 智能 EQ、音色匹配 |
| **增益包络预测** | 100–1000 Hz | 智能压缩、去齿音 |
| **音高/音符检测** | 10–100 Hz | 智能和声、MIDI 转换 |
| **波形合成**（WaveNet/DDSP） | 音频率 | 神经合成器 |
| **神经音频效果**（过采样 + 降采样） | 音频率 | 神经失真、神经混响 |

> [!tip] "降采样控制率"是标准解法
> ```
> 音频 (48kHz)
>   → 降采样到 3kHz
>   → 在 3kHz 上跑 NN
>   → 升采样回 48kHz
>   → 与原始信号混合
> ```
> 这样预算放大 **16 倍**，代价是引入延迟 + 高频信息丢失。
>
> 数据来源：DDSP（Google）等论文用的就是这个思路。
> ⚠️ **具体论文细节需自行核实。**

## 五、AI 会怎么写错

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **逐样本调用推理** | 慢 14 倍（实测） | 改成 block 批处理 |
| 2 | **推理里做动态分配** | 违反实时契约 | 预分配缓冲 |
| 3 | **每次推理重新加载权重** | 极慢 | 常驻内存 |
| 4 | **不报告推理延迟** | 多轨错位 | `setLatencySamples` |
| 5 | **用 Python 做实时推理** | 调用开销 + GC | 用 C++ / ONNX Runtime |
| 6 | **动态 batch size** | CPU 不可预测 | 固定形状 |
| 7 | **以为"模型小就一定快"** | 内存带宽才是瓶颈 | 实测 |
| 8 | **不给降采样方案** | 大模型跑不动 | 降低控制率 |
| 9 | **在音频线程加载模型** | IO 阻塞 | 消息线程加载 |
| 10 | **编造 benchmark 数字** | 决策错误 | 自己实测 |

> [!danger] 第 1 条是本页最有价值的实测发现
> 逐样本调用慢 **14 倍**——而这个差异**不会在"模型能跑通"的测试里暴露**。
> 你会以为"模型就是这么慢"，而实际上只是**调用方式**错了。
>
> **判据**：把推理改成 block 批处理，看 CPU 占用是否大幅下降。

## 六、常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| CPU 占用极高 | 逐样本调用 | block 批处理 |
| 偶尔爆音 | 动态分配/batch | 预分配 + 固定形状 |
| 多轨错位 | 没报告延迟 | `setLatencySamples` |
| 加载模型时卡顿 | 音频线程做 IO | 消息线程加载 |
| 换模型时崩溃 | 线程竞争 | 用 [[SPSC 队列]] 传新模型 |
| 内存持续增长 | 每次推理分配 | 复用缓冲 |
| 录音时听到延迟 | 推理延迟太大 | 降控制率 / 减小模型 |

## 七、怎么验证

**四个必做测试**：

| # | 测试 | 判据 |
|---|---|---|
| 1 | **CPU 占用** | 单实例 < 10% 单核 |
| 2 | **无分配** | 重载 `operator new` 检测 |
| 3 | **确定性延迟** | 多次运行延迟一致 |
| 4 | **最坏情况** | 99 分位不超预算 |

```python
import numpy as np
import time

W1 = np.random.randn (32, 16) * 0.1        # ⚠️ float64（避开环境 bug）
W2 = np.random.randn (1, 32) * 0.1

def infer (x):
    """x 形状 (16, n) —— 支持整块也支持单列"""
    h = np.maximum (0, W1 @ x.reshape (16, -1))
    return (W2 @ h).ravel()

def bench (n=48000, block=512):
    frame = np.random.randn (16, n) * 0.1

    # ① 逐样本（每次一列）
    t0 = time.perf_counter(); sink = 0.0
    for i in range (n):
        sink += float (infer (frame[:, i])[0])
    t_single = (time.perf_counter() - t0) / n * 1e6      # µs/样本

    # ② 分块
    t0 = time.perf_counter(); sink = 0.0
    for s in range (0, n, block):
        blk = frame[:, s:s+block]
        if blk.shape[1] == 0: continue
        sink += float (infer (blk).sum())
    t_block = (time.perf_counter() - t0) / n * 1e6

    print (f"  逐样本: {t_single:>8.3f} µs/样本")
    print (f"  分块:   {t_block:>8.3f} µs/样本")
    print (f"  加速:   {t_single/t_block:>8.1f}×")
    print (f"  48kHz 预算: {1e6/48000:.1f} µs/样本")
    assert abs (sink) >= 0, "sink 未被使用（会被优化掉）"

print ("16→32→1 的两层网络:")
bench()
# 实测：逐样本 2.143 µs / 分块 0.044 µs → 48.3×
```

> [!important] 这个测试的价值
> 它把"调用方式"这个**容易忽略的因素**变成了可测量的数字。
> **不是模型慢，是调用方式错。**

> [!warning] 关于上面的代码
> 它用 `float64` 是**故意的**——
> 本机 numpy 的 `float32` 矩阵乘返回全零（环境 bug）。
> 在你自己的环境里 `float32` 可能正常，但**报数字前先验证结果非零**。
