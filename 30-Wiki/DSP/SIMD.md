# SIMD

> [!important] 一句话
> **SIMD = 一条指令处理多个样本**（如 4 个 float 一起算）。
> 但对音频来说，**最大的收益往往不是"手写 SIMD"，而是"别阻碍编译器自动向量化"**。

## 为什么音频适合 SIMD

| 特征 | 说明 |
|---|---|
| **数据并行** | 同样的运算施加到每个样本 |
| **连续内存** | 音频缓冲区是连续的 |
| **循环次数多** | 每个 block 几百到几千次 |

> [!note] 术语
> - **SIMD**：Single Instruction, Multiple Data
> - **NEON**：ARM 的 SIMD 指令集（Apple Silicon 用这个）
> - **SSE/AVX**：x86 的 SIMD 指令集
> - **自动向量化**：编译器自动把标量循环变成 SIMD

---

## 一、实测：什么在阻碍向量化（本库验证）

**测试**：每样本 8 次乘加的循环（模拟滤波器级联），16384 样本 × 5000 次。

| 编译选项 | 无分支 | **带饱和分支** | 分支的代价 |
|---|---|---|---|
| `-O2` | 0.3156 ns | **1.1626 ns** | **3.7×** |
| `-O3` | 0.2980 ns | 1.1685 ns | 3.9× |
| `-O2 -march=native` | **0.2113 ns** | 1.0412 ns | **4.9×** |

> [!important] 三个结论
> 1. **带分支的代码慢 3.7–4.9 倍** —— 因为分支**阻止了向量化**
> 2. **`-O3` 相比 `-O2` 几乎没有提升**（0.3156 → 0.2980）
> 3. **`-march=native` 有实际收益**（0.3156 → 0.2113，**约 1.5×**）

> [!danger] 第 1 条是最有价值的发现
> 你不需要手写 SIMD——**只要把分支去掉**，编译器就能向量化，
> 白拿 **3.7 倍**。
>
> 而"去掉分支"通常是**算法层面**的改动（见下）。

> [!warning] 本机实测的局限
> - 只有 **arm64**（Apple Silicon），x86-64 的 AVX 行为可能不同
> - `-march=native` 的收益**依赖具体 CPU**
> - 上面的绝对数字**不能跨机器比较**，只有**相对关系**有意义

## 二、什么会阻止自动向量化

| # | 阻碍 | 例子 | 解法 |
|---|---|---|---|
| 1 | **数据依赖**（循环携带） | `y[i] = a*y[i-1] + x[i]`（IIR） | 无法向量化（本质串行） |
| 2 | **分支** | `if (x > 1) ... else ...` | 改成分支无关写法 |
| 3 | **指针别名** | 编译器不确定 `a` 和 `b` 是否重叠 | `__restrict` |
| 4 | **非对齐访问** | 缓冲区未按 SIMD 宽度对齐 | `alignas(16/32)` |
| 5 | **函数调用** | 循环里调用非内联函数 | 内联 / 手动展开 |
| 6 | **浮点结合律** | 编译器默认不重排浮点加法 | `-ffast-math`（⚠️ 危险） |

> [!danger] 第 1 条是音频的根本限制
> **IIR 滤波器有反馈 → 循环携带依赖 → 无法向量化。**
> ```cpp
> y[n] = b0*x[n] + b1*x[n-1] - a1*y[n-1] - a2*y[n-2];
> //                 ↑ 依赖 y[n-1] → 串行
> ```
>
> **所以 IIR 本质上不能 SIMD 并行**（除非用特殊技术，见下）。
>
> **FIR 可以**（无反馈）。

> [!tip] 第 2 条的解法：分支无关写法
> ```cpp
> // ❌ 有分支 → 阻止向量化
> if (x > 1.0f) y = 1.0f; else y = x;
>
> // ✅ 分支无关（用 min/max，编译成 SIMD 指令）
> y = std::min (x, 1.0f);
> ```
> 见 [[非线性处理]]。

## 三、能做什么（实用清单）

### 1. 优先：消除阻碍（零成本）

| 做法 | 收益 |
|---|---|
| **用 `std::min/max/clamp` 代替 if** | ⭐ 最大 |
| 加 `__restrict`（或 `restrict`） | 中 |
| `alignas(16)` 对齐缓冲区 | 中 |
| 循环内避免函数调用 | 中 |
| **用 `-march=native`**（⚠️ 仅本地构建） | **实测 1.5×** |

```cpp
// ⭐ 分支无关的软削波（可向量化）
for (int i = 0; i < n; ++i)
    out[i] = std::tanh (in[i] * drive);     // tanh 通常可向量化

// 或者用 clamp（最简单）
for (int i = 0; i < n; ++i)
    out[i] = std::clamp (in[i] * drive, -1.0f, 1.0f);
```

> [!warning] `__restrict` 是承诺，不是请求
> 它告诉编译器"这两个指针**不会**重叠"。
> **如果你撒谎了，结果是未定义行为。**
>
> ⚠️ 跨平台写法：MSVC 用 `__restrict`，GCC/Clang 用 `__restrict__` 或 `restrict`。

### 2. 次选：结构层面的 SIMD

| 做法 | 说明 |
|---|---|
| **多声道并行** | 立体声的 L/R 可以一起算（天然的 SIMD 宽度 2） |
| **多实例并行** | 处理 4 个样本块（用"块处理"而非逐样本） |
| **FIR 的块卷积** | 可以向量化 |
| **向量化数学库** | 如 `juce::dsp::SIMDRegister` |

```cpp
// ⭐ 多声道是最自然的 SIMD（不用手写指令）
// 立体声：同时处理 L 和 R
for (int i = 0; i < n; ++i)
{
    const float l = L[i], r = R[i];
    L[i] = process (l);
    R[i] = process (r);      // 两次独立调用 → 编译器可能合并成 SIMD
}
```

### 3. 最后：手写 SIMD

> [!warning] 手写 SIMD 的代价
> | 代价 | 说明 |
> |---|---|
> | **不可移植** | NEON ≠ SSE ≠ AVX |
> | 难维护 | 可读性差 |
> | 容易出错 | 边界处理、对齐 |
> | **编译器常常做得更好** | 它知道目标 CPU |
>
> **建议**：先用 `juce::dsp::SIMDRegister`（JUCE 的跨平台封装），
> 而不是手写 `_mm_*` 或 `vld1q_*`。

## 四、IIR 真的不能向量化吗

> [!note] 有条件可以
> | 技术 | 说明 |
> |---|---|
> | **块处理 + 矩阵形式** | 把 IIR 的递推展开成矩阵运算 |
> | **多声道/多实例** | 并行处理多个独立信号 |
> | **状态空间 + SIMD** | 一次算多个滤波器实例 |
>
> ⚠️ 这些技术的实际收益**本机未实测**。
> 对**单个** IIR 滤波器，串行依赖是本质限制。

> [!important] 所以音频优化的顺序是
> 1. **算法选择**（FFT 卷积 vs 直接卷积）—— 收益最大
> 2. **消除向量化阻碍**（去分支、对齐）
> 3. **多声道/多实例并行**
> 4. 手写 SIMD —— 收益最小、代价最大

## 五、AI 会怎么写错

| # | AI 常犯 | 后果 | 怎么查 |
|---|---|---|---|
| 1 | **在热循环里用 `if`** | 阻止向量化，慢 3.7× | 用 `min/max/clamp` |
| 2 | **建议手写 SIMD 优化** | 不可移植、难维护 | 先试去分支 |
| 3 | **用 `-ffast-math` 换向量化** | 破坏 NaN/可复现性 | ❌ 禁用 |
| 4 | **忘了 `alignas`** | 非对齐访问慢 | 对齐缓冲区 |
| 5 | **对 IIR 做向量化尝试** | 本质串行，白费 | 改多声道并行 |
| 6 | **`__restrict` 用错（撒谎）** | 未定义行为 | 确认不重叠 |
| 7 | **以为 `-O3` 一定更快** | 实测几乎无差别 | 实测 |
| 8 | **在发布构建用 `-march=native`** | 换 CPU 就崩 | 用基线指令集 |
| 9 | **手写 `_mm_*`** | 不可移植到 ARM | 用 JUCE 封装 |
| 10 | **不测就优化** | 优化了非瓶颈 | 先剖析 |

> [!danger] 第 3 条是最危险的建议
> AI 看到"想向量化"就会推荐 `-ffast-math`——
> 因为浮点结合律不成立会阻止向量化，而 `-ffast-math` 解除了这个限制。
>
> **但它同时破坏了 NaN 检测和可复现性**（见 [[浮点确定性与可复现性]]）。
>
> **对音频插件：绝对不要。**

> [!danger] 第 1 条是最实用的
> 你的 DSP 代码里可能有这样的分支：
> ```cpp
> if (std::abs(x) < 1e-20f) x = 0.0f;      // denormal 防护
> ```
> 这个**每个样本都有分支** → 阻止向量化。
>
> **解法**：用无分支写法（如加一个极小的直流偏置），
> 见 [[denormal 数处理]]。

## 六、常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| 加了 SIMD 反而更慢 | 数据太小/内存受限 | 先剖析 |
| 优化没效果 | 瓶颈不在计算 | 见 [[性能剖析]] |
| 换 CPU 后崩溃 | `-march=native` | 用基线指令集 |
| ARM 上编不过 | 手写了 x86 指令 | 用 JUCE 封装 |
| 结果不对 | `__restrict` 撒谎了 | 检查别名 |
| 音质变差 | 用了 `-ffast-math` | 去掉 |
| 小 buffer 时反而慢 | SIMD 有启动开销 | 块处理 |

## 七、怎么验证

**四个必做检查**：

| # | 检查 | 判据 |
|---|---|---|
| 1 | **是否向量化** | 看汇编里有 SIMD 指令 |
| 2 | **实测加速比** | 改前后对比 |
| 3 | **结果一致** | bit-exact 或 < -100 dB |
| 4 | **小 buffer 性能** | 不能退化 |

```bash
# ① 看编译器是否向量化（Clang/GCC）
clang++ -std=c++17 -O2 -Rpass=loop-vectorize -c mydsp.cpp -o /dev/null 2>&1 | head
# 会输出 "vectorized loop" 或 "loop not vectorized: <原因>"

# ② 看汇编里有没有 SIMD 指令（ARM）
clang++ -std=c++17 -O2 -S mydsp.cpp -o - | grep -E "fmla|fmul.*v[0-9]|ld1|ldp" | head

# ③ 实测加速比
clang++ -std=c++17 -O2 -march=native bench.cpp -o b && ./b
```

> [!tip] `-Rpass=loop-vectorize` 是最有用的诊断
> 它会**明确告诉你为什么没向量化**：
> ```
> remark: loop not vectorized: cannot prove it is safe to reorder memory operations
> remark: loop not vectorized: control flow in loop
> ```
> **这比猜有效得多。**

> [!important] 但一定要验证"结果没变"
> 向量化会改变浮点运算顺序 → 结果可能不同（见 [[浮点确定性与可复现性]]）。
> **改完必须做 null test。**
