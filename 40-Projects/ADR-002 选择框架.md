# ADR-002: 选择框架

> [!warning] 待决策
> 需要你回答 [[_meta/open-questions|Q2（C++ 水平）]] 后才能定。

## 背景

从零写插件框架不现实（格式的样板代码极多）。需要选一个框架。

## 选项

| 选项 | 语言 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **JUCE** | C++ | 生态最大、教程最多、AI 训练数据多 | 体积大、许可需注意（AGPL/商业） | 大多数人 |
| **iPlug2** | C++ | 轻量、图形性能好 | 社区小、文档少 | 有经验者 |
| **DPF** | C++ | 极轻量、开源友好 | 功能少，GUI 要自己搞 | 极简主义者 |
| **nih-plug** | Rust | 内存安全、现代设计 | Rust 生态小、AI 帮助少 | Rust 用户 |
| **Faust** | Faust→C++ | DSP 描述极简洁，可导出多目标 | 复杂逻辑受限，需学新语言 | DSP 原型 |
| **手写 SDK** | C++ | 完全控制、体积最小 | 开发极慢 | 学习目的 |

## 决定

**倾向：JUCE**（理由见下），但等你确认 C++ 水平后定稿。

## 理由

1. **AI 辅助效果最好** — JUCE 是开源 C++ 音频领域训练数据最多的框架。你用 Agent 写代码时，它见过的 JUCE 代码远多于 iPlug2/DPF。
2. **一套代码出多格式** — VST3/AU/CLAP/Standalone 一次构建。
3. **社区大** — 遇到问题能搜到答案。
4. **`juce_dsp` 模块** — 提供了不少现成的 DSP 组件（虽然建议初期自己写）。

> [!warning] JUCE 的代价
> - 二进制体积大（几 MB 到几十 MB）
> - 许可：AGPLv3（开源）或商业授权（闭源）
> - 抽象层厚，初学时会掩盖底层细节 → **所以路线图建议先用纯 C++ 写 DSP**

## 什么情况下应该重新考虑

- 如果 JUCE 的商业授权成本不可接受 → iPlug2 / DPF
- 如果你要做的插件 GUI 极重（如复杂可视化）→ iPlug2 的图形性能更好
- 如果 C++ 水平是 L1 → 先别选框架，先写纯 C++ DSP
