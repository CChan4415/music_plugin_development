# 延迟与回声的原理

> [!important] 这一页解决什么问题
> 你在 DAW 里拧 delay 的 time 旋钮时，脑子里想的是"空间""节奏""厚度"；
> 代码里看到的只是一个环形缓冲区的读指针偏移量。
> **这一页把这两件事接起来**：同一个数学结构，为什么在 3ms 时听起来像"变薄了"，
> 在 300ms 时听起来像"在山谷里"，以及——为什么你调 time 旋钮时它会"哇"一声。
>
> 更重要的是：**混响就是"很多个延迟"**。这一页想清楚了，混响页会变得几乎不需要解释。

## 一个数学结构，四种听感

延迟线（delay line）本身没有任何"效果"。它就是 `y[n] = x[n − D]`。
所有听觉差异都来自 **D 的大小**、**反馈量**、以及**环路里放了什么**。

```
                    ┌──────────────┐
        ┌──────────►│  delay  D    ├──┬──► 输出
        │           └──────────────┘  │
        │                               │
        └───── g ◄── [ 环路处理 ] ◄─────┘
                 （低通 / 饱和 / 调制）
```

> [!note] 记住这张图
> - 去掉反馈环 → 单次延迟（echo）
> - 反馈环里放一个低通 → 每次回声更暗（磁带感）
> - 反馈环里放一个调制 → 合唱 / 镶边 / 磁带抖晃
> - **并联很多条、长度互质的延迟线，再把它们互相反馈 → 混响**
>
> 所以 [[Schroeder 混响]] 和 [[反馈延迟网络 FDN]] 不是"另一类算法"，
> 它们是这张图的放大版。见 [[梳状滤波器 comb filter]]。

## 1. 心理声学基础：多少毫秒才算"回声"

人耳对"第二个到达的声音"有两种处理方式：

| 延迟量 | 听觉系统怎么处理 | 你听到的 |
|---|---|---|
| 极短 | 与直达声**融合**，无法分离 | 音色变了（滤波） |
| 中等 | 融合，但**定位被先到的那个支配** | 声音变宽/变厚，但仍是"一个声音" |
| 较长 | **分离**成两个事件 | 明确的回声 |

**优先效应（precedence effect）/ Haas 效应**说的是第二行：两个相似的声音在很短的时间窗内到达时，
听觉系统把它们当成一个事件，而且**声源定位由先到达的那个决定**——即使后到的那个更响。

**回声阈值（echo threshold）**说的是第三行：超过它，你就听到两个声音了。

> [!warning] 待验证：阈值不是一个数字
> "30 ms" 是工程上最常引用的分界，但它**强烈依赖信号类型和相对电平**：
> - 瞬态类信号（拍手、click）的阈值短得多——个位数毫秒就能听出两个事件
> - 语音大约在几十毫秒量级
> - 连续的音乐/噪声阈值更长
> - 后到的声音**越响**，越容易被听成独立事件；很轻的反射即使晚 20 ms 也仍被融合
>
> 上面这些量级是心理声学里广泛引用的常识，但我没有在 `10-Sources/` 留档，
> **具体数字请在你自己做插件时用听感测试确认**（见文末「怎么验证」）。

> [!important] 这直接决定 pre-delay 的设计
> 混响的 **pre-delay**（预延迟）旋钮不是"延迟时间"，它是一个**融合/分离开关**：
>
> | pre-delay | 音乐人听到的 | 什么时候用 |
> |---|---|---|
> | 0–10 ms | 完全融合，只是"声音变大了" | 想要"贴脸"的短混响、想要不改变音头 |
> | 10–30 ms | 融合但开始有空间轮廓 | **最常用**：既保留清晰度又不显得干 |
> | 30–60 ms | 开始被听成独立的空间 | 大空间、想要"这个声音在一个房间里" |
> | > 60 ms | 明确的"先声后混响" | 特殊效果；人声上很容易听起来像没对上拍 |
>
> **推论**：pre-delay 的 UI 不该用线性刻度。0–30 ms 之间的感知变化远大于 60–200 ms 之间。
> 见 [[MOC - UI & UX]] 关于参数曲线的部分。

## 2. 四种听觉形态与音乐用途

| 区间 | 听感 | 音乐用途 | 工程要点 |
|---|---|---|---|
| **< 10 ms** | **梳状滤波（comb filtering）**：不是回声，是"音色" | 加厚、镶边（flanger）、"立体声加宽" | 峰值在 `f = k/D`，零点在 `f = (2k+1)/(2D)`。**单声道兼容性杀手** |
| **10–30 ms** | 加厚 / 拍频，Haas 区 | 双轨加倍（doubling）、宽度、去相关 | 左右轻微不同的延迟 → 感知变宽；sum 到 mono 会掉 |
| **30–100 ms** | **slapback**（拍背回声） | 人声厚度、吉他 rockabilly、鼓的"房间" | 通常**不带反馈**或反馈极低，一次就够 |
| **> 100 ms** | 明确的**回声** | 节奏性 delay、Dub、空间感 | 需要节拍同步 + 反馈 + 环路滤波 |

> [!tip] 为什么 < 10 ms 是"滤波"不是"回声"
> 一个延迟 D 秒的信号与原始信号相加，得到的是传递函数 `H(f) = 1 + g·e^(−j2πfD)`，
> 这是一个**梳状滤波器**：某些频率被加倍（+6 dB），某些被抵消（−∞ dB）。
> 听觉系统无法把它解析成两个事件，只能报告"频谱变了"——也就是音色变了。
>
> **这就是为什么 flanger 和 chorus 是延迟效果器**：它们的本质是把 D 调到 1–20 ms 并让它动起来。
> 详见 [[调制效果]]、[[梳状滤波器 comb filter]]。

> [!warning] 立体声加宽的代价
> 用 10–30 ms 的左右延迟差做"宽度"，在单声道回放时：
> 两个信号相加 → 梳状滤波 → 某些频率被抵消 → **声音变薄甚至消失**。
> 这是"混音在耳机里很宽、在手机喇叭上塌掉"的最常见原因。
> 见 [[立体声感知]]。

## 3. 节拍同步的数学

音乐人想的是"1/8 附点"，代码要的是**采样数**。中间隔着一个 BPM。

$$\text{delayMs} = \frac{60000}{\text{BPM}} \times \text{beats}$$

其中 `beats` 是音符时值折算成的拍数：

| 音符 | beats | 附点（×1.5） | 三连音（×2/3） |
|---|---|---|---|
| 全音符 | 4 | — | — |
| 二分音符 | 2 | 3 | 4/3 |
| 四分音符 | 1 | 1.5 | 2/3 |
| 八分音符 | 0.5 | 0.75 | 1/3 |
| 十六分音符 | 0.25 | 0.375 | 1/6 |

**120 BPM 下的实际数值**（`60000/120 = 500 ms` 一个四分音符）：

| 时值 | ms | 采样数 @48 kHz | 典型用途 |
|---|---|---|---|
| 1/4（四分） | **500.0** | 24000 | 慢速氛围、长尾 |
| 1/4 附点 | 750.0 | 36000 | 跨拍回声、U2 式 |
| 1/8（八分） | **250.0** | 12000 | 最通用 |
| 1/8 附点 | **375.0** | 18000 | **最常用**：不会和主节奏打架 |
| 1/8 三连音 | 166.67 | 8000 | 摇摆感、shuffle |
| 1/16（十六分） | 125.0 | 6000 | 密集的"颗粒"感 |
| 1/16 附点 | 187.5 | 9000 | 切分 |
| 1/16 三连音 | 83.33 | 4000 | 快速颤音感 |

> [!note] 为什么 1/8 附点最常用
> 附点 1/8 = 3/16 拍。它和 1/4、1/8 都不重合，所以回声**不会和下一个正拍的音符叠在一起**，
> 既填满了空隙又不破坏节奏的清晰度。这是混音惯例，不是数学必然。

```cpp
// BPM + 音符时值 -> 毫秒
// noteBeats: 全音符=4, 二分=2, 四分=1, 八分=0.5, 十六分=0.25
inline float beatsToMs (double bpm, double noteBeats, bool dotted, bool triplet)
{
    if (bpm <= 0.0) return 0.0f;          // 宿主没给 BPM 时要能兜住
    double beats = noteBeats;
    if (dotted)  beats *= 1.5;
    if (triplet) beats *= 2.0 / 3.0;
    return (float) (60000.0 / bpm * beats);
}

// 毫秒 -> 采样数（分数延迟，不取整）
inline float msToSamples (float ms, double sampleRate)
{
    return ms * 0.001f * (float) sampleRate;
}
```

> [!warning] 不要自己数拍子
> **必须从宿主取 transport 信息**（JUCE 里是 `getPlayHead()->getPosition()`），
> 不要自己维护一个计数器。原因：
> - 用户会在播放中改 BPM
> - 用户会 locate（跳到某个位置）、开循环
> - 用户会从中间开始播放
>
> 宿主跳转时，延迟线里残留的旧内容会和新位置错位。
> 常见做法是在检测到播放位置**不连续跳变**时清空延迟线（或快速淡出）。
> 这个判断必须能在音频线程里做（只读原子量，不加锁）——见 [[实时音频线程契约]]。

## 4. 反馈与衰减：回声会响几次

设每次回声的增益为 $g$（0 < g < 1），第 $n$ 次回声的幅度是 $g^n$。
设可闻阈值（比如 −60 dB，即 0.001 倍幅度），回声次数：

$$g^n = \text{threshold} \quad\Longrightarrow\quad \boxed{n \approx \frac{\ln(\text{threshold})}{\ln g}}$$

**在 120 BPM、1/4 音符（500 ms）延迟下：**

| 反馈 $g$ | 折算 dB | 到 −60 dB 的回声次数 | 总衰减时间 |
|---|---|---|---|
| 0.3 | −10.5 dB | 5.7 | 2.9 s |
| 0.5 | −6.0 dB | **10.0** | 5.0 s |
| 0.7 | −3.1 dB | 19.4 | 9.7 s |
| 0.8 | −1.9 dB | 31.0 | 15.5 s |
| 0.9 | −0.9 dB | **65.6** | 32.8 s |
| 0.99 | −0.09 dB | 687 | 344 s |

> [!important] 为什么反馈接近 1 会失控
> 带反馈的延迟线是一个 IIR：$H(z) = \dfrac{1}{1 - g\,z^{-N}}$。
> 在它的谐振频率上（`f = k / D`，也就是"所有和延迟周期成整数倍的频率"），
> 幅频响应的峰值是：
> $$\left|H\right|_{\max} = \frac{1}{1 - g}$$
>
> - $g = 0.5$ → 峰值 +6 dB
> - $g = 0.9$ → 峰值 **+20 dB**
> - $g = 0.99$ → 峰值 **+40 dB**
>
> 也就是说，反馈旋钮拧到 99% 时，你其实是在延迟线的谐振频率上挂了 **+40 dB 的增益**。
> 任何宽带成分（噪声、DC 偏置、前级的微小直流）都会被指数放大 → 听起来就是"炸了"。
> **$g \ge 1$ 时系统不稳定，数学上必然发散。**

**实践上的三条防线**：

```cpp
// 1. 限制反馈上限（不要允许 1.0）
feedback = std::min (feedback, 0.95f);

// 2. 环路里放一个低通：高频每次绕一圈就衰减一点
//    这既让声音自然，又保证环路总增益 < 1
const float damped = lp.process (delayedOut);   // 一阶低通
delay.write (input + damped * feedback);

// 3. 环路末端加软饱和，作为最后的安全网（同时也更好听）
delay.write (input + std::tanh (damped * feedback));
```

> [!warning] 反馈旋钮的刻度不要线性
> 把 UI 的 0–100% 线性映射到 $g$，会让 0–50% 之间几乎没变化（+6 dB 到 0 dB），
> 而 90–100% 之间变化剧烈（+20 dB 到 +40 dB）。用户会觉得"这个旋钮前面是死的，后面是疯子"。
> **做法**：让旋钮映射到 dB，再转回线性增益。
> ```cpp
> // 旋钮 0..1 -> -60 dB .. -0.5 dB
> const float g = std::pow (10.0f, juce::jmap (knob, 0.0f, 1.0f, -60.0f, -0.5f) / 20.0f);
> ```

## 5. 磁带延迟 vs 数字延迟：为什么磁带听起来"温暖"

"温暖"不是一个玄学词，它是一组**具体的、可实现的**物理缺陷。

| 磁带的物理现象 | 听感 | 工程实现 |
|---|---|---|
| **抖晃（wow / flutter）** | 音高轻微游移，声音"活"、"不呆" | 用 LFO 调制延迟时间（分数延迟读指针） |
| **频响损失**（录音/放音头、磁带本身） | 高频变暗、低频略薄 | 环路里放低通 + 高通 |
| **每次反馈都更暗** | 回声逐渐"沉下去" | **环路内**的低通（不是输出后的） |
| **磁带饱和** | 大声时被压扁、产生偶次谐波 | 环路里的 `tanh` / 软削波 |
| **本底噪声** | 每次反馈都叠一点噪声，尾巴"有质感" | 环路里加极低电平的噪声 |
| **磁头碰撞 / 走带不均** | 轻微的周期性起伏 | 慢速随机调制 |

**wow 与 flutter 的区别**（两者都是速度不稳，区别在**变化速率**）：

- **wow**：慢的，亚赫兹到几赫兹量级 → 听成"音高在飘"
- **flutter**：快的，十几赫兹到更高 → 听成"声音毛糙"、有颗粒

> [!warning] 待验证：wow / flutter 的具体频率划分
> 上面的量级是磁带机领域的常见说法，但不同资料给出的分界频率不一致（6 Hz？10 Hz？）。
> 做插件时**不要照抄某个数字**，用两个独立的 LFO 分别覆盖"慢"和"快"两档，靠听感调。
> 待补：找一份权威的磁带机规格资料放进 `10-Sources/`。

```cpp
// 磁带延迟的三件套：环路低通 + 环路饱和 + 读指针调制
class TapeDelay
{
public:
    void prepare (double sr, float maxMs)
    {
        sampleRate = (float) sr;
        line.prepare (sr, maxMs);
        // 一阶低通系数：截止频率越高，"磁带"越新
        lpCoeff = 1.0f - std::exp (-2.0f * float_Pi * 4000.0f / sampleRate);
        wowInc     = 2.0f * float_Pi * 0.7f / sampleRate;   // 0.7 Hz：慢，听成音高在飘
        flutterInc = 2.0f * float_Pi * 9.0f / sampleRate;   // 9 Hz：快，听成声音毛糙
    }

    float process (float x, float delaySamples, float feedback, float depth)
    {
        // ---- 1. 调制读指针（wow + flutter）----
        wowPhase     += wowInc;      if (wowPhase     > 2.0f * float_Pi) wowPhase     -= 2.0f * float_Pi;
        flutterPhase += flutterInc;  if (flutterPhase > 2.0f * float_Pi) flutterPhase -= 2.0f * float_Pi;

        const float modulated = delaySamples
                              + depth * (6.0f * std::sin (wowPhase)      // 深度单位：采样数
                                       + 1.5f * std::sin (flutterPhase));

        // ---- 2. 先读后写（顺序不能反！见「常见坑」）----
        const float delayed = line.read (modulated);   // 分数延迟读取，见 [[插值]]

        // ---- 3. 环路处理：低通 → 饱和 ----
        lpState += lpCoeff * (delayed - lpState);      // 每次绕环，高频损失一点
        const float saturated = std::tanh (lpState * 0.8f);

        // ---- 4. 写回：输入 + 反馈 ----
        line.write (x + saturated * feedback);
        return delayed;
    }

private:
    DelayLine line;
    float sampleRate = 48000.0f, lpCoeff = 0.1f, lpState = 0.0f;
    float wowPhase = 0.0f, flutterPhase = 0.0f, wowInc = 0.0f, flutterInc = 0.0f;
};
```

> [!important] 注意上面的处理顺序
> **先读后写**，而且**环路处理（低通 + 饱和）在写回之前**。
> 如果把低通放在输出之后（而不是环路之内），那么只有"最后一次"回声会变暗，
> 前面的回声不会——听起来就不像磁带了。
> **"每次反馈都更暗"必须发生在环路里面。**

## 6. 为什么延迟时间不能直接平滑（新手必踩）

这是新手做 delay 插件时**最常见的一个 bug**，而且它的症状很有迷惑性：
**用户一拧 time 旋钮，声音就"哇——"地滑上去。**

**原因**：延迟时间 $D$ 就是读指针相对写指针的距离。
如果每采样把 $D$ 增加一点点，读指针就在缓冲区里**连续移动**——
这等价于**改变播放速度**，也就是**改变音高**（多普勒效应）。

$$\text{音高偏移比例} \approx 1 - \frac{dD/dt}{1}$$

读指针移动得越快，变调越明显。从 100 ms 平滑到 200 ms 用了 100 ms，
读指针速度就是 $0.5\times$ 实时 → 音高掉一个八度。

> [!important] 关键区分：你是**故意**要变调，还是**不小心**变调了
>
> | 场景 | 该怎么做 |
> |---|---|
> | chorus / flanger / 磁带抖晃 | **故意**平滑——多普勒就是效果本身 |
> | 用户拧 delay time 旋钮 | **不能**平滑——用交叉淡化（crossfade） |
> | 节拍同步的 delay（BPM 变了） | 交叉淡化；或者在拍点附近快速切换 |
>
> 这与 [[参数平滑 parameter smoothing]] 的结论一致，但延迟时间是那一页里**唯一**的例外。

### 正确做法：两条读指针 + 交叉淡化

```cpp
class CrossfadingDelay
{
public:
    void prepare (double sr, float maxMs)
    {
        sampleRate = sr;
        line.prepare (sr, maxMs);
        currentSamples = targetSamples = 0.5f * (float) sr;  // 默认 500 ms
        fromSamples    = currentSamples;
        xfade = 1.0f;                                        // 1 = 淡化已完成
    }

    void setDelayMs (float ms)
    {
        const float s = std::clamp (ms * 0.001f * (float) sampleRate,
                                    1.0f, line.maxDelaySamples() - 2.0f);
        if (std::abs (s - targetSamples) < 0.5f) return;      // 变化太小，不值得淡化

        // 把"正在响的"固化成旧指针，新指针从当前位置开始淡入
        fromSamples    = currentSamples;
        targetSamples  = s;
        xfade          = 0.0f;
        xfadeInc       = 1.0f / (0.030f * (float) sampleRate); // 30 ms 完成
    }

    float process (float x)
    {
        line.write (x);                          // 先写
        const float a = line.read (fromSamples); // 旧延迟
        const float b = line.read (targetSamples);// 新延迟

        if (xfade < 1.0f)
        {
            xfade = std::min (1.0f, xfade + xfadeInc);
            if (xfade >= 1.0f) currentSamples = targetSamples;  // 淡化完成，固化
        }

        // ⚠️ 用线性（等增益）淡化，不是等功率
        return a * (1.0f - xfade) + b * xfade;
    }

private:
    DelayLine line;
    double sampleRate = 48000.0;
    float currentSamples = 0.0f, targetSamples = 0.0f, fromSamples = 0.0f;
    float xfade = 1.0f, xfadeInc = 0.0f;
};
```

> [!warning] 等增益 vs 等功率淡化
> 一般做淡化时用**等功率**（`cos/sin` 曲线）以避免中点掉 3 dB——那是对**不相关**信号。
> 延迟线的两条读指针输出**高度相关**（同一个源，只差一点时间），
> 用等功率淡化会在中点**凸起 +3 dB**，听成"咔"的一下。
> **相关信号用线性淡化，不相关信号用等功率淡化。**

> [!note] 淡化期间的两个读指针
> 上面只做了"旧→新"的一次淡化。如果用户在 30 ms 内连续拧旋钮，
> 第二次调用 `setDelayMs` 会覆盖 `fromSamples`，造成跳变。
> 稳妥做法：把 `fromSamples` 保持在**上一次完成淡化的值**，
> 并给淡化加一个最短间隔（比如 50 ms 内忽略新的改动）。

## 设计决策表

| 音乐人想要的 | 算法上要实现什么 |
|---|---|
| "让这个声音变厚，但还是一遍" | D = 10–30 ms，无反馈，干湿 50/50；左右不同 D → 变宽 |
| "加一点空间，但不要听到回声" | D < 30 ms 或 pre-delay < 30 ms，短反馈，环路强低通 |
| "slapback，摇滚那种" | D = 60–120 ms，反馈 0 或极低，环路低通较暗 |
| "跟着节拍来的回声" | 从宿主取 BPM + 取 transport 位置；1/8 附点为默认值 |
| "回声越来越远/越来越暗" | 环路内低通（不是输出后）+ 反馈 0.6–0.8 |
| "磁带味" | 读指针 LFO 调制（慢 + 快两个 LFO）+ 环路低通 + 环路 `tanh` + 少量噪声 |
| "不要变调，我拧旋钮时别哇哇叫" | 交叉淡化（30 ms，线性），绝不直接平滑读指针 |
| "一直响下去，快自激" | $g$ 上限钳到 0.95，环路里必须有低通 + 饱和，denormal 处理 |
| "立体声要宽" | 左右不同 D（10–30 ms）+ 轻微反馈交叉；**必须检查 mono 兼容性** |
| "和宿主同步，我跳到哪它就跟到哪" | 检测 transport 不连续跳变 → 清空/淡出延迟线 |

## 常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| 拧 time 旋钮时"哇"一声滑音 | 直接平滑了读指针（多普勒） | 交叉淡化；只有 chorus/tape 模式才允许平滑 |
| 反馈一开大就爆音/自激 | 环路增益 ≥ 1；峰值增益 $1/(1-g)$ 太高 | $g$ 钳到 0.95；环路内加低通 + `tanh` |
| 静音后 CPU 突然飙升 | 反馈尾巴进入 denormal | 见 [[denormal 数处理]] |
| 交叉淡化时有"咔"的凸起 | 用了等功率淡化，但两路信号相关 | 改用线性（等增益）淡化 |
| 回声里混进了"上一个音符" | 延迟线没有随 transport 跳转清空 | 检测播放位置跳变 → 清空或快速淡出 |
| 分数延迟听起来闷、高频少 | 线性插值本身是低通 | 用全通插值或更高阶插值，见 [[插值]] |
| 立体声左右串音 | 左右共用一条延迟线 | 每声道一条独立的延迟线实例 |
| 反馈调到 0 仍有"尾巴" | 环路里还有残余状态 | `reset()` 要真的清空缓冲区，见 [[旁路 bypass 的正确实现]] |
| 延迟读出来少一个采样 / 反馈变成零延迟 | **先写后读**，`D=0` 时读到自己 | **先读后写**，或强制 `D ≥ 1` 采样 |
| 同步的延迟和节拍错位 | 自己数拍子 / 用了整数 BPM 近似 | 从宿主 transport 取 BPM 和播放位置 |

> [!warning] 最后一个坑最隐蔽
> 反馈环路里**至少要有一个采样的延迟**，否则你会得到一个代数环
> （$y[n]$ 依赖 $y[n]$），要么算出错误结果，要么必须解方程。
> 环形缓冲区的"先读后写"顺序天然提供了这个延迟——
> **顺序写反了，反馈就会在一个采样内闭合。**

## 怎么验证

### 听感测试

1. **四个区间**：用拍手声或短脉冲作源，把 D 从 1 ms 扫到 500 ms，确认听到
   "音色变化 → 加厚 → slapback → 明确回声"四段变化。听不出来说明你的干湿混合有问题。
2. **变调测试**：播放持续正弦，**慢慢**拧 time 旋钮。
   听到音高滑动 = 你直接平滑了读指针（bug）；听到平滑过渡 = 交叉淡化正确。
3. **反馈上限**：把反馈拧到最大，喂白噪声。应该在几秒内**稳定在一个电平**，不是无限增长。
4. **磁带模式**：A/B 对比环路有无低通。有低通的版本每次回声应该明显更暗。

### 数值测试（更可靠）

```cpp
// 测试 1：脉冲响应 —— 回声间隔必须精确等于 D
// 喂一个单位脉冲，找输出的所有峰值位置
// 期望：峰值出现在 D, 2D, 3D, ... （采样数）
// 容差：±1 采样（分数延迟插值会带来不到 1 采样的误差）

// 测试 2：衰减必须符合 g^n
// 第 n 个峰值的幅度应该 ≈ g^n
// 注意：如果环路里有低通，每次回声的峰值会额外衰减 → 用低频正弦测

// 测试 3：交叉淡化期间不能有不连续
// 喂直流 1.0，让 D 从 100 ms 跳到 300 ms
// 输出的绝对值的一阶差分最大值应该小于阈值
// （与 [[参数平滑 parameter smoothing]] 的验证方法一致）

// 测试 4：环路稳定性
// 喂白噪声 10 秒，反馈设为最大值
// 断言：输出峰值不超过输入峰值的 1/(1-g) 的合理倍数，且不发散
```

> [!tip] 用你的耳朵发现问题，用数值测试锁住它
> 你能听出"这个 delay 一拧旋钮就哇哇叫"是优势。
> 但只有把它变成"一阶差分超过 X 就 fail"的自动化断言，
> 才能防止你（或 AI）在三个月后改代码时重新引入这个 bug。
> 见 [[AI 生成音频测试]]。
