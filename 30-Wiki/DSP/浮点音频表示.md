# 浮点音频表示

> [!important] 一句话
> 插件内部用 **32-bit float**，不是为了"更多位深"，而是为了**巨大的 headroom**——
> 超过 ±1.0 只是损失精度，**不丢数据**。
> 代价是三个必须处理的坑：**精度只有 6 位十进制**、**NaN/Inf 会永久污染信号链**、
> **denormal 会让 CPU 在安静时飙升**。

## 为什么这一页重要

| 你可能的误解 | 事实 |
|---|---|
| "32-bit float = 32 位精度" | ❌ 尾数只有 **23 位**（≈24-bit 定点），另外 8 位是指数 |
| "float 有 1500 dB 动态范围，所以不会削波" | ⚠️ 技术上对，但**有效精度**在 ±1.0 附近只有 **138.5 dB** |
| "超过 1.0 就削波了" | ❌ 浮点超 1.0 只是**损失精度**，值本身完好 |
| "NaN 只是个小问题" | ❌ 一个 NaN 会**永久污染** IIR 状态，永不自愈（实测 100% 污染） |

## 一、IEEE 754 的位结构

**32-bit float** 的位布局：

```
 31        30────────23 22────────────────────────0
┌───┬──────────────────┬────────────────────────────┐
│ s │   e (8 bits)     │      f (23 bits)           │
└───┴──────────────────┴────────────────────────────┘
符号   指数（偏置 127）        尾数（隐含前导 1）
```

$$x = (-1)^s \times 1.f \times 2^{\,e-127}$$

**实测解包**（本库，`struct.unpack('<I', struct.pack('<f', v))`）：

| 值 | 十六进制 | s | e | 尾数 | 真实指数 |
|---|---|---|---|---|---|
| 1.0 | `0x3F800000` | 0 | 127 | 0 | 0 |
| -1.0 | `0xBF800000` | 1 | 127 | 0 | 0 |
| 0.5 | `0x3F000000` | 0 | 126 | 0 | -1 |
| 1.5 | `0x3FC00000` | 0 | 127 | 4194304 | 0 |
| 2.0 | `0x40000000` | 0 | 128 | 0 | 1 |
| 0.1 | `0x3DCCCCCD` | 0 | 123 | 5033165 | -4 |
| π | `0x40490FDB` | 0 | 128 | 4788187 | 1 |
| 1e+38 | `0x7E967699` | 0 | 253 | 1472153 | 126 |

<!-- derived: 50-Playground/exp-004-dynamics-math/exp_float.py §1，2026-10-15 实测 -->

> [!tip] 三个可以直接手算的例子
> - **1.0 = `0x3F800000`**：$e=127 \Rightarrow 2^0$，尾数 $0 \Rightarrow 1.0$。
>   所以 `0x3F800000` 是浮点的"1.0 基准点"——调试时很有用。
> - **1.5 = `0x3FC00000`**：尾数 `0x400000` $= 2^{22}$，$1 + 2^{22}/2^{23} = 1.5$。
> - **0.1 不能精确表示**：`0x3DCCCCCD` 是 0.100000001490116…，
>   所以 `0.1f + 0.2f != 0.3f`。**永远不要用 `==` 比较浮点。**

**float64** 只是把指数扩到 11 位、尾数扩到 52 位，结构完全相同。

## 二、float32 vs float64：有效精度

| 量 | float32 | float64 |
|---|---|---|
| 尾数位 | 23 | 52 |
| 机器 epsilon | 1.192093e-07 | 2.220446e-16 |
| **十进制有效位数** | **6** | **15** |
| 最小规格化正数 | 1.175494e-38 | 2.225074e-308 |
| 最大有限值 | 3.402823e+38 | 1.797693e+308 |

<!-- derived: exp_float.py §2，2026-10-15 实测 -->

### 音频幅度范围内的**绝对**量化步长

| 幅度 | float32 步长 | 等效 dBFS | float64 步长 |
|---|---|---|---|
| 1.0 | 1.192e-07 | **-138.5** | 2.220e-16 |
| 0.5 | 5.960e-08 | -144.5 | 1.110e-16 |
| 0.1 | 7.451e-09 | -162.6 | 1.388e-17 |
| 0.01 | 9.313e-10 | -180.6 | 1.735e-18 |
| 1e-4 | 7.276e-12 | -222.8 | 1.355e-20 |

<!-- derived: exp_float.py §2，2026-10-15 实测 -->

> [!important] 浮点的精度是**相对**的，定点的精度是**绝对**的
> 注意上表：幅度**越小**，绝对步长越小，**等效 dBFS 越低**（越精确）。
> 这正是浮点的优点——**每个数量级都保持 6 位有效数字**。
>
> 定点（int24）则相反：无论信号多小，LSB 永远是满刻度的 $2^{-23}$。
> **所以浮点在小信号上的精度优势是"免费"的。**
>
> ⚠️ 但推论是：**超过 0 dBFS 后，每翻一倍，绝对精度就粗一倍。**
> 实测：+6 dBFS 处步长 2.384e-07（等效 -132.5 dBFS），
> +48 dBFS 处步长 3.052e-05（等效 **-90.5 dBFS**）。
> **所以"浮点不会削波"是真的，但"可以随便超 0 dBFS"是错的。**

## 三、为什么音频内部用浮点而不是定点

| | 定点（int24） | 浮点（float32） |
|---|---|---|
| 精度分布 | 均匀（绝对） | 相对（每数量级 6 位） |
| 超出满刻度 | **硬削波**（回绕或截断） | 只是损失精度 |
| 动态范围 | 144.5 dB（固定） | 1529.2 dB（有效精度 138.5 dB @ ±1.0） |
| 乘法累加 | 需注意定标（Q 格式） | 自动定标 |
| 与硬件接口 | **原生**（ADC/DAC 是整数） | 需转换 |
| SIMD | 整数 SIMD 与浮点 SIMD 性能相近 | 现代 CPU 浮点吞吐更高 |

> [!important] 决定性理由：**中间结果会超出 ±1.0**
> 一个滤波器、一次求和、一次增益提升，都可能让中间值超过 1.0。
> - **定点**：立刻削波，不可逆 → 你必须手工管理定标（headroom、Q 格式），极易出错
> - **浮点**：值完好，只是精度粗一点 → 后面衰减回来就完全恢复
>
> **这就是"插件内部必须用 float"的全部理由。** 不是精度更高，是**不会因中间过载而毁掉信号**。

> [!warning] 但**边界**仍然是定点：ADC/DAC 和文件格式
> 真实硬件是整数。所以：
> - **输入**：int → float（除以满刻度），此后全程 float
> - **输出**：float → int（乘回满刻度 + 钳制 + dither），见 [[抖动 dither]]
> - **归一化约定**：int16 除以 32768 还是 32767？→ 见 [[采样与量化]] §5
>
> **约定不一致是 null test 失败的常见原因**（实测会停在 -90 dB 而不是 -∞）。

## 四、±1.0 归一化的约定

**行业约定**：数字满刻度（0 dBFS）对应浮点幅度 **1.0**。

$$x_{\text{dBFS}} = 20\log_{10}|x|$$

| 浮点值 | dBFS | 常见含义 |
|---|---|---|
| 1.0 | 0.0 | 满刻度（不可超过的"约定"上限） |
| 0.5 | -6.02 | 半幅 |
| 0.1 | -20.0 | 十分之一 |
| 3.162e-2 | -30.0 | |
| 1e-3 | -60.0 | |
| 1.192e-7 | -138.5 | float32 在 ±1.0 处的步长 |

> [!danger] AI 最常搞错的三个归一化问题
> | 错误 | 后果 | 正确 |
> |---|---|---|
> | `log10` 而不是 `20*log10` | 增益全部差一倍 | 幅度用 20，功率用 10 |
> | int16 除以 32767 读、乘以 32768 写 | round-trip 有偏差 | 读写用**同一个**约定 |
> | 认为"0 dBFS = 1.0 = 最大值" | 在中间级错误地钳制到 ±1.0 | **中间级不要钳制**，只在输出端钳制 |
>
> **第三条尤其重要**：如果你在每一级之后都 `clamp(x, -1, 1)`，
> 你就把浮点退化成了定点，白白丢掉了 headroom。

## 五、headroom：float32 到底有多少

| 量 | 值 | 折合 dBFS |
|---|---|---|
| 最大有限值 | 3.402823e+38 | **+770.6** |
| 最小规格化正数 | 1.175494e-38 | **-758.6** |
| 最小 denormal | 1.401298e-45 | -897.1 |
| **规格化范围** | — | **1529.2 dB** |
| 含 denormal 的总范围 | — | 1667.7 dB |

<!-- derived: exp_float.py §3–4，2026-10-15 实测 -->

> [!warning] "float32 有 1500 dB 动态范围"——**技术上对，工程上误导**
> 那是"最大可表示 ÷ 最小可表示"的比值，**不是"同时可用的精度"**。
> 真实可用的精度是**尾数的 23 位**，在 ±1.0 附近 = **138.5 dB**。
>
> **正确的说法**：float32 有 **~770 dB 的向上 headroom**，
> 而**精度**约等于 24-bit 定点（138.5 dB @ 满刻度）。

### 与整数位深的对比

| 格式 | 理论动态范围 | 满刻度 LSB | 超范围行为 |
|---|---|---|---|
| int16 | 96.3 dB | -90.31 dBFS | **硬削波/回绕** |
| int24 | 144.5 dB | -138.47 dBFS | **硬削波/回绕** |
| int32 | 192.6 dB | -186.64 dBFS | **硬削波/回绕** |
| **float32** | 1529.2 dB | -138.47 dBFS（@ ±1.0） | **只是损失精度** |

<!-- derived: exp_float.py §4，2026-10-15 实测 -->

> [!tip] 为什么"32-bit float 录音几乎不可能削波"
> 录音时如果电平超了 0 dBFS，**定点**会永久削平（不可逆），
> **浮点**只是把值记成 1.4、2.7…，精度粗一点但**波形完好**，
> 后期衰减回来就完全恢复。
>
> 注意：这只在**录音链路全程浮点**时成立。
> 如果 ADC 之前的前级模拟电路过载了，浮点也救不回来。

## 六、NaN / Inf：产生与**永久传播**

### 产生

| 运算 | 结果 |
|---|---|
| `1.0f / 0.0f` | `+Inf`（有符号） |
| `0.0f / 0.0f` | `NaN` |
| `log(0)` | `-Inf` |
| `sqrt(-1)` | `NaN` |
| `Inf - Inf` | `NaN` |
| `Inf * 0` | `NaN` |

<!-- derived: exp_float.py §5，2026-10-15 实测 -->

### 传播：这是最致命的部分

**实测**：把一个 NaN 注入 8 级串联的一阶低通（`y += c*(x-y)`），
输入 2000 个样本、在样本 100 处注入：

| 指标 | 结果 |
|---|---|
| 输出 NaN 数 | **1900 / 2000** |
| 注入点之后的样本 | **1900 个，其中 NaN = 1900（100.0%）** |
| 结论 | **无一幸存** |

<!-- derived: exp_float.py §5，2026-10-15 实测 -->

同样注入 `Inf`：输出 NaN 数 1899，Inf 数 1
——**Inf 经过 IIR 的反馈运算会变成 NaN**（`Inf - Inf`），同样永久污染。

> [!danger] 为什么 NaN 在 IIR 里"永不自愈"
> 因为 **IIR 有状态**。一旦 `y1` 或 `y2` 变成 NaN：
> - `y[n] = b0*x + ... - a1*y1 - a2*y2` → 任何含 NaN 的算术结果都是 NaN
> - NaN 写回状态 → **下一轮又是 NaN**
>
> **信号链上游的一个 NaN，会让下游所有 IIR 永远输出 NaN，
> 即使输入已经恢复正常。** 用户听到的是"插件突然彻底静音/爆响，必须重开"。
>
> **而反馈结构（混响、延迟、滤波器、包络跟随器）全都是 IIR。**

### 防御

```cpp
#include <cmath>

// 方案 1：逐样本检测（最直接，但每个样本一个分支）
inline float sanitizeSample (float x) noexcept
{
    return std::isfinite (x) ? x : 0.0f;
}

// 方案 2：每个 block 检查一次（推荐 —— 分支几乎 100% 预测正确）
// 返回 true 表示发现了坏值并已复位
inline bool sanitizeBlock (float* data, int n) noexcept
{
    for (int i = 0; i < n; ++i)
        if (! std::isfinite (data[i]))
        {
            for (int j = 0; j < n; ++j) data[j] = 0.0f;   // 整个 block 清零
            return true;                                   // 调用方应 reset() 所有 IIR 状态
        }
    return false;
}
```

```cpp
void processBlock (juce::AudioBuffer<float>& buffer, juce::MidiBuffer&) override
{
    // ... 处理 ...

    for (int ch = 0; ch < buffer.getNumChannels(); ++ch)
    {
        if (sanitizeBlock (buffer.getWritePointer (ch), buffer.getNumSamples()))
        {
            resetAllIirState();      // ⚠️ 关键：光清音频不够，状态也得复位
            return;
        }
    }
}
```

> [!warning] 只清音频、不清状态 = 白做
> NaN 在**状态变量**里，不在输出里。
> 你必须把 `y1/y2/env/meanSq/...` 全部复位，否则下一个 block 立刻又是 NaN。
> **这是 AI 最常漏的一条。**
>
> **更根本的做法**：从源头防住。检查每个除法、每个 `log`/`sqrt` 的输入、
> 每个反馈增益是否被钳制（`|feedback| < 1`）。

## 七、denormal 与 FTZ

当数值小到约 $10^{-38}$ 以下，float32 进入 **denormal（非规格化）** 区间。

| 名称 | 值 | 折合 dBFS |
|---|---|---|
| `FLT_MIN`（最小规格化） | 1.175494e-38 | -758.6 |
| `FLT_TRUE_MIN`（最小 denormal） | 1.401298e-45 | -897.1 |
| 中间的 denormal 个数 | **8388607**（$2^{23}-1$） | — |

<!-- derived: exp_float.py §6，2026-10-15 实测 -->

**它在音频里由反馈路径天然产生**（混响尾音、IIR 状态、包络平滑器），
**只在安静时发作**，且**本库实测尾音不会自己归零**。

> [!important] 完整内容在 [[denormal 数处理]]
> 那一页有：x86 vs ARM 的 FTZ/DAZ 位掩码差异、RAII 实现、
> "尾音卡在 denormal 不归零"的实测、跨平台注意事项。
> **本页只强调一点**：这是**必须处理**的，不是优化项。

**一行快速检查**：

```cpp
// 尾音应该精确为 0。不是 0 就说明反馈环里有 denormal 在循环。
bool isTailTrulySilent (const float* buffer, int size) noexcept
{
    for (int i = 0; i < size; ++i)
        if (buffer[i] != 0.0f) return false;
    return true;
}
```

## 八、精度陷阱：累加与灾难性抵消

**实测**（float32，100000 个 $\mathcal{N}(0, 0.1)$ 样本求和）：

| 方法 | 结果 | 误差 |
|---|---|---|
| float32 顺序累加 | -42.329319 | 1.707e-05（**-127.9 dB** 相对） |
| float64 累加（参考） | -42.329302 | — |

<!-- derived: exp_float.py §7，2026-10-15 实测 -->

### 灾难性抵消：大数 + 小数

```python
float32: 1.0 + 1e-9 = 1.0            # 1e-9 被完全吞掉
1.0 累加 1000 次 1e-9 = 1.0          # 理论 1.000001，误差 0.0001%
```

<!-- derived: exp_float.py §7，2026-10-15 实测 -->

> [!warning] 音频里的具体后果
> **包络跟随器的状态变量是"大数 + 小数"的典型场景。**
> release 很慢时，`env` 在接近目标值处每次只变化极小量：
> `env += coeff * (target - env)`，当 `target - env` 已经很小时，
> **这个增量可能小于 `env` 的步长 → 完全丢失 → 包络"卡住"不再下降**。
>
> 这与 [[denormal 数处理]] 的"尾音卡住不归零"是**同一类现象的不同表现**。
>
> **实用对策**：
> - 累加**大量**样本（如计算 block 的 RMS/能量）时用 **double**
> - 反馈/平滑状态用 float 没问题（它只做一次乘加，不累积）
> - 需要长期累加的量（总能量、平均值）用 **Kahan 求和**或 double

```cpp
// Kahan 补偿求和：用一次额外加法换回精度
class KahanSum
{
public:
    void add (float v) noexcept
    {
        const float y = v - c;
        const float t = sum + y;
        c = (t - sum) - y;      // 丢失的低位
        sum = t;
    }
    float value() const noexcept { return sum; }
    void reset() noexcept { sum = 0.0f; c = 0.0f; }
private:
    float sum = 0.0f, c = 0.0f;
};
```

**实测收益**（100000 个 $\mathcal{N}(0,0.1)$ 样本，对比 float64 参考值）：

| 方法 | 结果 | 误差 | 相对参考 |
|---|---|---|---|
| 朴素 float32 顺序累加 | -42.329319000 | 1.707e-05 | — |
| **Kahan 补偿** | -42.329303741 | **1.811e-06** | **精度改善 19.5 dB** |

<!-- derived: 本库 2026-10-15 实测，KahanSum 逐字复制自上方代码 -->

> [!note] Kahan 值不值得用
> 换来 **19.5 dB** 精度，代价是**每次加法多 3 次浮点运算**。
> - **值得**：长时间累加的总能量、RMS、平均值、统计量
> - **不值得**：每个样本的反馈/平滑状态（那只是单次乘加，不累积误差）
>
> ⚠️ Kahan 也有极限：它假设累加器远大于被加项。极端情况下
> （如 1e10 累加 1e-10 共 10¹⁰ 次）它也会失效。**需要极致精度就用 double。**

### 常数精度（不是问题）

| 常数 | float64 | float32 | 相对误差 |
|---|---|---|---|
| π | 3.141592653589793 | 3.141592741 | 2.78e-08 |
| 1/√2 | 0.707106781186547 | 0.707106769 | 1.71e-08 |
| $\ln(10)/20$ | 0.115129254649702 | 0.115129255 | 9.44e-10 |
| $2^{1/12}$ | 1.059463094359295 | 1.059463143 | 4.62e-08 |

<!-- derived: exp_float.py §8，2026-10-15 实测 -->

> [!tip] 常数误差 1e-8 对音频完全够用
> **真正的问题从来不是常数精度，而是累加和反馈的误差累积。**
> 不要为了"更准"把所有常数写成 double——那只会让你失去 SIMD 和缓存优势。

| 0.5 | 1.000000000 | 0.00e+00 |

| 0.005 | 0.999994040 | 5.96e-06 |

## 九、AI 会怎么写错

| # | AI 常写 | 为什么错 | 怎么查 |
|---|---|---|---|
| 1 | **在中间级 `clamp(x, -1, 1)`** | 把浮点退化成定点，丢掉全部 headroom | 数 `clamp`/`jlimit` 出现在哪几级 |
| 2 | **`NaN` 检测后只清音频不清状态** | 下一个 block 立刻又 NaN | 查是否调用了 `reset()` |
| 3 | **完全没有 NaN/Inf 防护** | 一个 NaN 永久污染整条链（实测 100% 污染） | grep `isfinite` |
| 4 | **`log10(0)` / `sqrt(负数)`** | 产生 -Inf / NaN | 查是否有 `+1e-9` 或 `max(0, ...)` |
| 5 | **反馈增益不钳制 `\|g\| < 1`** | 发散到 Inf → NaN | 查 `std::clamp(g, -0.999f, 0.999f)` |
| 6 | **以为"float32 有 1500 dB 精度"** | 概念错误 → 错误设计 | 记住精度是 23 位尾数 |
| 7 | **用 `==` 比较浮点** | `0.1f+0.2f != 0.3f` | 改用 `std::abs(a-b) < eps` |
| 8 | **float 累加大量和** | 误差累积（实测 -127.9 dB） | 需要精确时用 double 或 Kahan |
| 9 | **反馈状态不防 denormal** | 安静时 CPU 飙升 | 见 [[denormal 数处理]] |
| 10 | **在音频线程 `printf("%f", x)`** | IO + 可能分配，违反实时契约 | grep `printf`/`std::cout` |
| 11 | **`float` 与 `double` 混用不转换** | 隐式提升，性能与精度都受损 | 编译加 `-Wconversion` |
| 12 | **`-ffast-math` 当优化手段** | 静默删掉 NaN 检测，破坏 IEEE 语义 | 查 CMakeLists |
| 13 | **int16 读用 32767、写用 32768** | round-trip 有偏差 | 统一约定 |
| 14 | **`pow(10, x/20)` 用 `float` 精度不够** | 大范围 dB 转换误差 | 用 `std::pow(10.0f, ...)` 即可，但注意范围 |

> [!tip] 第 1 条和第 6 条是同一个认知缺口
> AI 的心智模型是"±1.0 是音频的边界，所以要钳制"。
> **真实情况是：±1.0 只是"输出到硬件时的约定"，插件内部可以远超。**
> 你只要在 prompt 里说"内部处理不要钳制到 ±1.0，只在最终输出端钳制"，
> AI 就会写对。

## 十、常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| 插件"突然彻底静音，要重开" | NaN 污染了 IIR 状态 | 加 `isfinite` 检查 + `reset()` |
| 输出爆响/尖叫 | 反馈发散到 Inf | 钳制反馈增益 |
| 安静时 CPU 飙升 | denormal | 见 [[denormal 数处理]] |
| null test 停在 -90 dB | 归一化约定不一致 | 统一 32767/32768 |
| 大信号后小信号"脏" | 精度被大信号占用（相对精度） | 正常；必要时降增益 |
| 和别的插件数值对不上 | 中间级钳制 / 累加精度 | 检查是否钳制、是否用 double |
| 包络在尾部"卡住"不下降 | 增量小于 float 步长 | 用 double 累加，或显式清零 |
| 参数在小值处跳动 | float 精度 + 未平滑 | 见 [[参数平滑 parameter smoothing]] |
| `-ffast-math` 后 NaN 检测失效 | 编译器假设无 NaN | 去掉 `-ffast-math` |

## 十一、怎么验证

> [!important] 数值验证优先于听感
> 精度问题**听不出来**，但可以用断言精确抓住。

| # | 验证什么 | 方法 | 通过标准 |
|---|---|---|---|
| 1 | **NaN/Inf 防护** | 注入一个 NaN 到输入端 | 输出在 1 个 block 内恢复为有限值 |
| 2 | **IIR 状态被复位** | 同上，然后喂正常信号 | 输出正常（不是 NaN） |
| 3 | **无中间钳制** | 喂 0 dBFS 信号并提升 +20 dB | 中间值达 10.0，不被削到 1.0 |
| 4 | **denormal 不出现** | 喂脉冲，跑 60 秒，检查尾音 | `np.all(tail == 0.0)` |
| 5 | **位模式正确** | 检查 1.0 的位模式 | `0x3F800000` |
| 6 | **归一化一致** | int → float → int round-trip | 完全一致 |
| 7 | **累加精度** | 对比 float32 顺序和 vs float64 | 差异 $< -120$ dB 相对 |
| 8 | **输出钳制只在最后** | 检查 `processBlock` 的 clamp 位置 | 只在写回 buffer 前 |

```python
import numpy as np, struct

# ① 位结构验证
def bits32(x): return struct.unpack('<I', struct.pack('<f', np.float32(x)))[0]
assert bits32(1.0)  == 0x3F800000, "1.0 的位模式错误"
assert bits32(-1.0) == 0xBF800000
assert bits32(0.5)  == 0x3F000000
print("✅ 位结构：1.0=0x3F800000, -1.0=0xBF800000, 0.5=0x3F000000")

# ② float32 在 ±1.0 处的步长 = -138.5 dBFS（等于 int24 的 LSB）
step = float(np.spacing(np.float32(1.0)))
assert abs(20*np.log10(step) - (-138.47)) < 0.01, f"步长 {20*np.log10(step)}"
print(f"✅ float32 @ ±1.0 步长 = {step:.6e} = {20*np.log10(step):.2f} dBFS")

# ③ NaN 永久传播（IIR）
def onepole(x, c):
    y = np.empty(len(x), dtype=np.float32); a = np.float32(0)
    for i in range(len(x)):
        a = np.float32(a + np.float32(c*np.float32(x[i]-a))); y[i] = a
    return y
sig = np.ones(2000, dtype=np.float32); sig[100] = np.nan
out = sig.copy()
for _ in range(8): out = onepole(out, np.float32(0.05))
n_after = int(np.sum(np.isnan(out[100:])))
assert n_after == 2000-100, f"预期全部污染，实测 {n_after}/{2000-100}"
print(f"✅ NaN 永久传播：注入点之后 {n_after}/{2000-100} 个样本全是 NaN（100%）")

# ④ 灾难性抵消
assert np.float32(1.0) + np.float32(1e-9) == np.float32(1.0)
print("✅ 灾难性抵消：float32 的 1.0 + 1e-9 == 1.0（增量被吞掉）")

# ⑤ 常数精度足够
for name, v in [("pi", np.pi), ("1/sqrt2", 1/np.sqrt(2)), ("2^(1/12)", 2**(1/12))]:
    rel = abs(float(np.float32(v)) - v) / v
    assert rel < 1e-6, f"{name} 相对误差 {rel}"
print("✅ 常数精度：float32 相对误差均 < 1e-6（音频完全够用）")

print("\n✅ 全部通过")
```
